    Chapter 01concept

    Linux কী?

    "Linux" শব্দটা মানুষ তিন-চার রকম অর্থে ব্যবহার করে, আর এখান থেকেই beginner-দের প্রথম confusion শুরু হয়। এই chapter-এ শব্দগুলো আলাদা করে নেব — Kernel, Linux, Distribution, Ubuntu।

    কেন এই chapter দরকার

    "আমি Ubuntu use করি" আর "আমি Linux use করি" — দুটো কথাই ঠিক, কিন্তু দুটো ভিন্ন জিনিস বোঝায়। এই পার্থক্যটা এখনই পরিষ্কার না হলে পরে যখন CentOS, Debian, Alpine, Docker image এসব সামনে আসবে, তখন মনে হবে সব আলাদা আলাদা OS। আসলে না।

    Operating System কী?

    Computer-এ hardware আছে — CPU, RAM, disk, network card। আর আছে তোমার programs — browser, VS Code, Node.js server। এখন সমস্যা হলো, একই সময়ে ২০টা program চলছে, সবাই CPU চায়, সবাই RAM চায়, সবাই disk-এ লিখতে চায়।

    কেউ একজনকে মাঝখানে দাঁড়িয়ে সব সামলাতে হয় — কে কতটুকু CPU পাবে, কার data কোথায় থাকবে, একটা program যেন অন্য program-এর memory-তে হাত না দেয়। এই সামলানোর কাজটাই Operating System-এর কাজ।

    মূলত OS চারটা resource manage করে: CPU (কে কখন চলবে), Memory (কার কতটুকু RAM), Storage (file কোথায়, কে পড়তে পারবে), Devices (keyboard, network card, screen)।

    Kernel কী?

    Kernel হলো OS-এর একেবারে core software layer — যেটা hardware আর running programs-এর মাঝখানে বসে সব কিছু নিয়ন্ত্রণ করে। উপরের চারটা কাজ আসলে kernel-ই করে।

    গুরুত্বপূর্ণ কথা: তোমার কোনো program সরাসরি hardware ছুঁতে পারে না। তোমার Node.js server চাইলেই disk-এ গিয়ে data লিখে দিতে পারে না। তাকে kernel-কে অনুরোধ করতে হয় — "এই file টা open করে দাও", "এই bytes গুলো লিখে দাও"। এই অনুরোধ করার নিয়মমাফিক পদ্ধতির নাম System Call।

        আমার program (Node.js, browser, ls)
              │
              │  system call  →  "file টা open করো"
              ▼
    ┌───────────────────────┐
    │        KERNEL         │   ← একমাত্র এই layer-টার
    │  process, memory,     │     hardware access আছে
    │  filesystem, network  │
    └───────────────────────┘
              │
              ▼
       CPU · RAM · Disk · NIC
    Analogy

    Kernel হলো ব্যাংকের ক্যাশ counter-এর ওপাশটা। তুমি vault-এ ঢুকে নিজে টাকা তুলতে পারবে না — form পূরণ করে counter-এ জমা দিতে হবে। form টাই system call, আর counter-এর পিছনের নিয়ন্ত্রিত জায়গাটাই kernel space।

    তাহলে "Linux" মানে কী?

    কঠিন অর্থে — Linux শুধুমাত্র kernel-টার নাম। Linus Torvalds ১৯৯১ সালে যেটা লেখা শুরু করেছিলেন। ব্যস, এটুকুই। কোনো terminal নেই, কোনো ls command নেই, কোনো text editor নেই।

    কিন্তু শুধু kernel দিয়ে তো কাজ করা যায় না। দরকার হয় — একটা shell (command চালানোর জন্য), কিছু basic utility (ls, cp, grep), একটা package manager, একটা init system, library গুলো। এই সবগুলো আলাদা আলাদা project, ভিন্ন ভিন্ন লোক লিখেছে।

    এই সব জিনিস একসাথে জোড়া দিয়ে, install করার মতো একটা complete system বানিয়ে দিলে — সেটার নাম Linux distribution বা distro।

    Linux distribution = Linux kernel
                   + shell (bash/zsh)
                   + core utilities (ls, cp, grep, ...)
                   + package manager (apt/dnf/pacman)
                   + init system (systemd)
                   + libraries, config, defaults

    Ubuntu কী?

    Ubuntu একটা Linux distribution। Canonical নামে একটা কোম্পানি এটা maintain করে। Ubuntu নিজে Debian নামে আরেকটা distribution-এর উপর ভিত্তি করে বানানো, তাই Debian-এর apt package manager Ubuntu-তেও আছে।

    Ubuntu কী দেয়? Linux kernel (তারা নিজেরা লেখেনি), GNU utilities (তারা লেখেনি), systemd (তারা লেখেনি) — সব একসাথে গুছিয়ে, test করে, একটা installer বানিয়ে, security update-এর দায়িত্ব নিয়ে দেয়। মূল value টা এই integration আর maintenance-এ।

    শব্দআসলে কী
    LinuxKernel। একটা software project।
    Linux distributionKernel + বাকি সব software মিলিয়ে ব্যবহারযোগ্য একটা complete system।
    Ubuntu / Debian / Fedora / Alpineএক একটা distribution। সবাই একই Linux kernel ব্যবহার করে।
    যেখানে beginner আটকায়

    "Ubuntu আর Linux কি আলাদা OS?" — না। Ubuntu হলো Linux-এর একটা প্যাকেজিং। Ubuntu, Fedora, Alpine — তিনটাতেই একই kernel চলছে।

    "তাহলে distro গুলোর পার্থক্য কোথায়?" — মূলত তিন জায়গায়: (১) package manager (apt না dnf না apk), (২) default হিসেবে কোন software দেওয়া আছে, (৩) release policy — নতুন version কত তাড়াতাড়ি আসে, কতদিন support দেওয়া হয়।

    Kernel-level concept — process, permission, filesystem, pipe — সব distro-তে হুবহু এক। তাই এই বই যেকোনো distro-তে কাজে লাগবে।

    Linux কেন server আর development-এ এত গুরুত্বপূর্ণ

    • GUI ছাড়াই পুরোপুরি চলে। Server-এ কেউ মনিটর লাগিয়ে বসে থাকে না। Linux পুরোটাই text দিয়ে চালানো যায়, তাই remote থেকে SSH দিয়ে সব করা যায়।
    • Scriptable। যা terminal-এ হাতে করা যায়, ঠিক সেটাই একটা file-এ লিখে automate করা যায়। CI/CD পুরোটাই এই ধারণার উপর দাঁড়ানো।
    • Container-এর ভিত্তি। Docker আসলে Linux kernel-এর namespace আর cgroup feature-এর উপর বানানো। Linux না বুঝে Docker বোঝা মানে ধারদেনা করে চালানো।
    • যেখানেই deploy করবে, সেখানেই Linux। AWS EC2, Vercel-এর ভেতরের runtime, GitHub Actions runner — প্রায় সবই Linux।
    Hands-on

    নিজের system-কে জিজ্ঞেস করো সে কে

    bash
    $ uname -s      # কোন kernel চলছে
$ uname -r      # kernel-এর version
$ cat /etc/os-release   # কোন distribution

    uname -s লিখবে Linux — এটা kernel-এর নাম। কিন্তু /etc/os-release লিখবে Ubuntu 24.04 বা যেটাই তোমার distro। এই দুই output-এর পার্থক্যটাই এই পুরো chapter-এর সারাংশ — একটা kernel, আরেকটা distribution।

    macOS-এ uname -s লিখবে Darwin — কারণ macOS-এর kernel Linux না।

    Recap
    • OS = CPU, memory, storage, device — এই চারটা resource-এর manager।
    • Kernel = OS-এর core; hardware-এ একমাত্র তারই সরাসরি access আছে।
    • Program kernel-এর সাথে কথা বলে system call দিয়ে।
    • Linux = শুধু kernel-টার নাম।
    • Distribution = kernel + shell + utilities + package manager, একসাথে গোছানো।
    • Ubuntu = একটা distribution, Debian-ভিত্তিক।

    Chapter 02shell

    Terminal, Shell এবং Command

    কালো screen-এ লেখা টাইপ করলে কাজ হয় — কিন্তু ঠিক কে কাজটা করছে? Terminal, না Shell? দুটো সম্পূর্ণ আলাদা জিনিস, আর এই পার্থক্য না জানলে অনেক কিছু ধোঁয়াশা থেকে যায়।

    Terminal কী?

    Terminal (পুরো নাম terminal emulator) হলো শুধুমাত্র একটা window-র মতো program। এর কাজ দুটো:

    1. Keyboard থেকে তোমার টাইপ করা character গুলো নেওয়া।
    2. যে text ফেরত আসছে, সেটা screen-এ এঁকে দেওয়া।

    ব্যস। Terminal ls মানে কী জানে না। cd কীভাবে কাজ করে, তার কোনো ধারণা নেই। সে শুধু character আদান-প্রদান করে।

    GNOME Terminal, iTerm2, Windows Terminal, Alacritty, VS Code-এর ভেতরের terminal panel — এগুলো সব terminal emulator। এগুলো বদলালে তোমার command-এর behaviour বদলায় না, শুধু font আর রঙ বদলায়।

    Shell কী?

    Shell হলো সেই program যেটা তোমার লেখা command পড়ে, বোঝে, এবং সেই অনুযায়ী কাজ করে। মানে আসল বুদ্ধিটা shell-এর।

    Shell যা যা করে: prompt দেখানো, তোমার লেখা line টা parse করা, ভেতরের variable আর wildcard গুলো expand করা, ঠিক কোন program চালাতে হবে সেটা খুঁজে বের করা, program চালানো, শেষ হওয়ার জন্য অপেক্ষা করা, তারপর আবার prompt দেখানো।

    তুমি টাইপ করলে "ls -l"

       ▼
┌──────────────┐   character গুলো পাঠায়
│   TERMINAL   │ ─────────────────────────►┐
│ (শুধু window)│                            │
└──────────────┘                            ▼
       ▲                            ┌──────────────┐
       │   output text ফেরত আসে      │    SHELL     │
       └────────────────────────────│    (bash)    │
                                    └──────────────┘
                                            │ ls program টা চালায়
                                            ▼
                                        [ Process ]
    Analogy

    Terminal হলো telephone handset — কথা যাওয়া-আসার যন্ত্র মাত্র। Shell হলো ওপাশের মানুষটা, যে তোমার কথা বুঝে কাজ করে। Handset বদলালে ওপাশের মানুষ বদলায় না।

    Bash কী?

    Bash (Bourne Again Shell) একটা shell-এর নাম। মানে shell একটা category, bash সেই category-র একটা implementation। আরও আছে zsh, fish, dash, sh।

    Ubuntu-তে default হিসেবে bash থাকে। macOS-এ এখন zsh default। বেশিরভাগ basic command দুটোতেই একইভাবে চলে, পার্থক্য মূলত scripting আর config file-এ।

    Hands-on

    তোমার shell আসলে কোনটা?

    bash
    $ echo $SHELL      # login shell কোনটা set করা আছে
$ ps -p $$         # এই মুহূর্তে আসলে কোন shell চলছে

    এখানে $$ মানে "বর্তমানে চলতে থাকা shell-এর process ID"। মানে shell নিজেও একটা চলমান program — একটা process। এই কথাটা Chapter 7-এ আবার লাগবে।

    Command কী?

    Command তিন রকমের হতে পারে, আর beginner-দের এখানে ভুল ধারণা হয় যে সবগুলোই আলাদা আলাদা file:

    1. External command — disk-এ পড়ে থাকা একটা executable file। যেমন ls আসলে /usr/bin/ls নামে একটা file। Shell এটাকে খুঁজে বের করে চালায়।
    2. Shell builtin — shell-এর নিজের ভেতরে লেখা, কোনো আলাদা file নেই। যেমন cd, echo, export।
    3. Alias / function — তুমি বা তোমার distro নিজে বানিয়ে রাখা shortcut।
    কেন cd builtin হতেই হবে

    Shell যখন একটা external program চালায়, সেটা একটা আলাদা process হিসেবে চলে। আলাদা process নিজের directory বদলালে parent shell-এর কিছুই বদলায় না। তাই cd যদি external program হতো, সেটা চলে শেষ হয়ে যেত আর তোমার shell একই জায়গায় দাঁড়িয়ে থাকতো। তাই cd-কে shell-এর ভেতরেই থাকতে হয়। এই যুক্তিটা মনে রাখো — Chapter 7-এ process বোঝার সময় কাজে লাগবে।

    Hands-on

    একটা command কোন ধরনের, সেটা জিজ্ঞেস করো

    bash
    $ type ls
$ type cd
$ type echo
$ which ls

    type cd বলবে এটা shell builtin। type ls বলবে এটা কোন path-এর file (অথবা Ubuntu-তে হয়তো একটা alias, কারণ distro নিজে ls-কে রঙিন করার জন্য alias করে রাখে)।

    একটা command চালালে ঠিক কী ঘটে

    এই sequence টা মনে রাখো — পুরো বইতে বারবার এটার টুকরো টুকরো অংশ ব্যাখ্যা করা হবে, আর Chapter 14-এ পুরোটা একসাথে জোড়া লাগবে।

    1. Shell prompt দেখায়        →  user@host:~$
2. তুমি লাইন লিখে Enter চাপো
3. Shell লাইনটা ভাগ করে       →  ["ls", "-l", "/etc"]
4. প্রথম শব্দ কী তা ঠিক করে   →  builtin? alias? নাকি file?
5. file হলে PATH-এ খোঁজে      →  /usr/bin/ls পাওয়া গেল
6. Shell নিজের একটা copy বানায়  →  fork()
7. সেই copy নিজেকে ls বানিয়ে ফেলে →  exec()
8. ls চলে, output লেখে
9. ls শেষ হয়, একটা exit status ফেরত দেয়
10. Shell আবার prompt দেখায়

    stdout, stderr, stdin

    প্রতিটা process চালু হওয়ার সময় Linux তাকে তিনটা খোলা চ্যানেল ধরিয়ে দেয়। এগুলো number দিয়ে চেনা হয়:

    নামNumberকাজ
    stdin0input আসে এখান দিয়ে (default: keyboard)
    stdout1স্বাভাবিক output যায় এখান দিয়ে (default: screen)
    stderr2error message যায় এখান দিয়ে (default: screen)

    Output আর error আলাদা চ্যানেলে কেন? কারণ তাহলে আসল result টা file-এ পাঠিয়ে দিয়েও error গুলো screen-এ দেখা যায়। Chapter 9-এ এটা নিয়ে বিস্তারিত কাজ করব।

    Hands-on

    দুটো চ্যানেল সত্যিই আলাদা কি না দেখো

    bash
    $ ls /etc /nosuchplace
# দুটো জিনিসই screen-এ আসছে: error আর listing

$ ls /etc /nosuchplace > out.txt
# এখন শুধু error টা screen-এ, listing চলে গেছে file-এ

$ cat out.txt

    দ্বিতীয় command-এ > শুধু stdout কে file-এ পাঠিয়েছে। stderr আলাদা চ্যানেল বলে সে screen-এই রয়ে গেছে। এটাই প্রমাণ যে দুটো সত্যিই আলাদা।

    Exit status

    প্রতিটা program শেষ হওয়ার সময় একটা number ফেরত দেয় — exit status বা exit code। নিয়ম উল্টো মনে হতে পারে:

    • 0 = সফল হয়েছে
    • 0 ছাড়া অন্য যেকোনো number = কোনো না কোনো সমস্যা হয়েছে

    0-কে success ধরা হয় কারণ ব্যর্থ হওয়ার কারণ অনেক রকম হতে পারে (1, 2, 127, 130...), কিন্তু সফল হওয়ার মানে একটাই।

    bash
    $ ls /etc
$ echo $?        # 0

$ ls /nosuchplace
$ echo $?        # 2 — ব্যর্থ

    এটা কেন গুরুত্বপূর্ণ? কারণ CI/CD pipeline ঠিক এই number টা দেখেই সিদ্ধান্ত নেয় build pass করেছে না fail। তোমার test command যদি 0 ছাড়া কিছু ফেরত দেয়, pipeline লাল হয়ে যায়।

    যেখানে beginner আটকায়

    "Terminal আর Shell কি এক?" — না। Terminal window, Shell ভেতরের program। এক terminal window-এ তুমি zsh লিখে অন্য shell-এ ঢুকে যেতে পারো, window একই থাকবে।

    "Bash আর Shell কি এক?" — Shell একটা ধরন, Bash সেই ধরনের একটা নির্দিষ্ট program।

    "exit status 0 মানে কিছু হয়নি?" — উল্টো। 0 মানেই সব ঠিকঠাক হয়েছে।

    Recap
    • Terminal = text দেখানো আর keyboard input নেওয়ার window। কোনো বুদ্ধি নেই।
    • Shell = command পড়ে বুঝে program চালানোর program। Bash একটা shell।
    • Command তিন রকম: external file, shell builtin, alias।
    • cd builtin হতেই হয়, কারণ আলাদা process directory বদলালে shell-এর কিছু বদলায় না।
    • প্রতিটা process পায় stdin(0), stdout(1), stderr(2)।
    • Exit status 0 = সফল, বাকি সব = ব্যর্থ।
    Chapter 03filesystem

    Linux Filesystem

    Windows থেকে আসা প্রায় সবাই এখানে হোঁচট খায় — C: drive কোথায়? D: drive কোথায়? Linux-এর উত্তর হলো, ওরকম কিছু নেই। পুরো system একটাই গাছ।

    কেন এই chapter সবচেয়ে গুরুত্বপূর্ণ

    Linux-এ প্রায় সব কিছুই file হিসেবে দেখা যায় — config, log, device, এমনকি চলমান process-এর তথ্য পর্যন্ত। তাই filesystem-এর structure যত পরিষ্কার হবে, Linux-এর বাকি অংশ তত সহজ লাগবে। Docker-এ volume mount, server-এ config খোঁজা, log পড়া — সব এখান থেকেই আসে।

    Windows model বনাম Linux model

    Windows-এ প্রতিটা storage device নিজের একটা আলাদা গাছ পায় — C:\ একটা গাছ, D:\ আরেকটা। দুটোর মধ্যে কোনো সম্পর্ক নেই।

    Linux-এ একটাই গাছ, যার গোড়া /। নতুন disk লাগালে সেটার জন্য নতুন কোনো letter আসে না — বরং গাছের কোনো একটা ডালে সেটাকে mount করা হয়, মানে ঐ directory-তে ঢুকলে নতুন disk-এর content দেখা যাবে।

    Windows:                    Linux:

C:\                              /
├── Windows                      ├── home
└── Users                        │   └── mostofa   ← হয়তো এটা অন্য একটা disk
                                 ├── etc
D:\           (আলাদা গাছ)         ├── var
└── Projects                     └── mnt
                                     └── data     ← এখানে দ্বিতীয় disk mount করা

    এই design-এর সুবিধা: program-কে কখনো জানতে হয় না data কোন physical disk-এ আছে। সে শুধু path জানে। Disk বদলে গেলেও path একই থাকতে পারে। এই কারণেই Docker-এ -v /host/path:/container/path এত সহজে কাজ করে।

    Analogy

    Linux filesystem একটা অফিস building। / হলো building টা নিজে। /home কর্মীদের ব্যক্তিগত ডেস্কের ফ্লোর, /etc হলো নিয়মকানুনের ফাইল রুম, /var হলো যেখানে প্রতিদিনের কাগজপত্র জমতে থাকে, /tmp হলো ডাস্টবিনের পাশের টেবিল — রাতে সব পরিষ্কার হয়ে যায়।

    গুরুত্বপূর্ণ directory গুলো

    Linux-এ শত শত directory আছে, কিন্তু mental model তৈরির জন্য এই কয়টাই যথেষ্ট।

    / — root directory

    গাছের গোড়া। সব path এখান থেকেই শুরু হয়। মনে রাখবে, এটা root user নয় — নাম এক হলেও দুটো সম্পূর্ণ আলাদা জিনিস। root user হলো একজন user (Chapter 6), / হলো একটা directory।

    /home — user-দের ব্যক্তিগত জায়গা

    প্রতিটা normal user একটা করে directory পায়: /home/mostofa। তোমার code, download, config — সব এখানে। এটাই একমাত্র জায়গা যেখানে তুমি sudo ছাড়া অবাধে লিখতে পারো। ~ চিহ্নটা এই directory-রই shortcut।

    /etc — system-wide configuration

    System আর installed software-এর config file গুলো এখানে থাকে, প্রায় সবই plain text। Nginx-এর config /etc/nginx/, user list /etc/passwd, DNS setting /etc/resolv.conf।

    Config text file হওয়ার একটা বড় সুবিধা আছে — git-এ রাখা যায়, script দিয়ে বদলানো যায়, diff করা যায়। Registry-র মতো binary blob-এ এসব করা কঠিন।

    /var — যে data সময়ের সাথে বাড়ে

    "variable" থেকে var। Log file (/var/log/), database-এর data, mail queue, cache — যা কিছু চলার সময় জমতে থাকে। Server-এ disk ভরে গেলে সবার আগে /var/log দেখা হয়।

    /tmp — অস্থায়ী file

    যেকোনো program এখানে অস্থায়ী file বানাতে পারে। Reboot করলে (বা নির্দিষ্ট সময় পরে) মুছে যায়। এখানে গুরুত্বপূর্ণ কিছু রেখো না।

    /usr — installed software

    নাম দেখে মনে হয় "user", কিন্তু আসলে এটা Unix System Resources। তোমার install করা প্রায় সব program-এর executable আর library এখানে: /usr/bin, /usr/lib, /usr/share।

    /bin, /sbin — এবং modern Linux-এ এদের অবস্থা

    আগে /bin-এ থাকতো একদম essential command গুলো, আর /usr/bin-এ বাকিগুলো। এই ভাগটা একটা পুরনো technical কারণে হয়েছিল যেটা আজকাল আর প্রাসঙ্গিক না।

    আধুনিক Ubuntu-তে /bin এখন আসলে /usr/bin-এরই একটা symbolic link — মানে দুটো path একই জায়গায় নিয়ে যায়। একে বলে "usr-merge"। তাই /bin/ls আর /usr/bin/ls একই file।

    /sbin-এ থাকে সেসব command যেগুলো মূলত admin-এর কাজে লাগে।

    /dev — device file

    Hardware device গুলো এখানে file হিসেবে দেখা যায়: /dev/sda (disk), /dev/null, /dev/random। এগুলো disk-এ পড়ে থাকা সত্যিকারের file নয় — kernel এগুলো তৈরি করে দেয়। বিস্তারিত Chapter 5-এ।

    /proc — kernel-এর জানালা

    এখানে চলমান system-এর তথ্য file আকারে পাওয়া যায়। প্রতিটা চলমান process-এর জন্য একটা করে directory থাকে, নাম হয় তার PID। /proc/cpuinfo পড়লে CPU-র তথ্য পাবে।

    এগুলোও disk-এ নেই। তুমি যখন file টা পড়তে চাও, kernel তখনই তথ্যটা বানিয়ে দেয়। এই কারণেই /proc-এর file গুলোর size প্রায়ই 0 দেখায়, অথচ ভেতরে content আছে।

    /root — root user-এর home

    root user-এর ব্যক্তিগত directory। normal user-দের home /home/-এ, কিন্তু root-এর আলাদা।

    তিনটা "root" — গুলিয়ে ফেলো না
    • / → root directory, filesystem-এর গোড়া।
    • root → সর্বময় ক্ষমতাসম্পন্ন user।
    • /root → সেই user-এর home directory।
    Hands-on

    গাছটা নিজের চোখে দেখো

    bash
    $ ls /
$ ls /etc | head -20
$ ls -l /bin       # symlink কিনা লক্ষ্য করো
$ ls /proc | head
$ cat /proc/cpuinfo | head -15
$ df -h            # কোন disk কোথায় mount করা

    ls -l /bin-এর output-এ যদি bin -> usr/bin দেখো, তার মানে তোমার system usr-merged। df -h-এর output-এ দেখো একাধিক device আলাদা আলাদা path-এ mount করা আছে — কিন্তু সবগুলোই একই গাছের অংশ।

    হাতে-কলমে দেখো

    → Path Resolution simulator — গাছে হেঁটে দেখো — absolute আর relative path কীভাবে resolve হয়, প্রতিটা ধাপ আলাদা করে।

    Recap
    • Linux-এ একটাই গাছ, গোড়া /। Drive letter নেই।
    • নতুন disk গাছের কোনো ডালে mount হয়।
    • /home তোমার, /etc config, /var বাড়তে থাকা data, /tmp অস্থায়ী, /usr installed software।
    • /dev আর /proc disk-এ নেই — kernel বানিয়ে দেখায়।
    • /, root, /root — তিনটা আলাদা জিনিস।

    Files, Directories এবং Paths

    এই chapter-এ কিছু command শিখবে, কিন্তু আসল লক্ষ্য command না — লক্ষ্য হলো প্রতিটা command দিয়ে filesystem-এর কোন ধারণাটা পরিষ্কার হচ্ছে সেটা ধরা।

    File আসলে কী?

    Linux-এ file হলো bytes-এর একটা ধারা, যার একটা নাম আছে। এর বেশি কিছু না। Linux file-এর ভেতরে কী আছে তা নিয়ে মাথা ঘামায় না — image, text, executable — সব তার কাছে শুধু bytes।

    এখান থেকে দুটো ব্যাপার বেরিয়ে আসে যেগুলো Windows থেকে আসা লোকজনকে অবাক করে:

    • Extension-এর কোনো ক্ষমতা নেই। .txt লেখা থাকলেও সেটা image হতে পারে। Extension শুধু মানুষের সুবিধার জন্য একটা convention।
    • নামে case-এর পার্থক্য আছে। Notes.txt আর notes.txt দুটো সম্পূর্ণ আলাদা file।

    Hidden file

    যে file-এর নাম . দিয়ে শুরু, সেটা default-এ ls-এ দেখা যায় না। যেমন .bashrc, .env, .git। এটা কোনো security feature না — শুধু config file গুলো চোখের সামনে থেকে সরিয়ে রাখার একটা নিয়ম। ls -a দিলেই দেখা যায়।

    Directory আসলে কী?

    এখানে একটা সূক্ষ্ম কিন্তু গুরুত্বপূর্ণ কথা আছে। Directory কোনো "বাক্স" নয় যার ভেতরে file গুলো রাখা আছে। Directory নিজেই একটা বিশেষ ধরনের file, যার ভেতরে লেখা আছে একটা তালিকা — কোন নামের সাথে disk-এর কোন জায়গা যুক্ত।

    এই কারণেই একটা অদ্ভুত ব্যাপার ঘটে: একটা file মুছে ফেলার অনুমতি নির্ভর করে directory-র permission-এর উপর, file-এর নিজের permission-এর উপর না। কারণ মোছা মানে হলো directory-র তালিকা থেকে একটা এন্ট্রি বাদ দেওয়া — মানে directory-তে লেখা। Chapter 6-এ এটা আবার আসবে।

    Path — absolute বনাম relative

    Absolute path শুরু হয় / দিয়ে। গোড়া থেকে পুরো ঠিকানা। তুমি কোথায় দাঁড়িয়ে আছো তাতে কিছু যায় আসে না।

    Relative path / দিয়ে শুরু হয় না। এটা তোমার current working directory থেকে হিসাব হয়।

    /
├── etc
│   └── nginx
│       └── nginx.conf
└── home
    └── mostofa
        └── projects
            └── api
                └── index.ts

তুমি দাঁড়িয়ে আছো: /home/mostofa/projects

absolute:  /home/mostofa/projects/api/index.ts
relative:  api/index.ts
relative:  ../          →  /home/mostofa
relative:  ../../       →  /home
    চিহ্নমানে
    /root directory (path-এর শুরুতে থাকলে)
    .এই directory টাই
    ..এক ধাপ উপরের directory
    ~তোমার home directory
    -আগের directory (cd - দিয়ে ফিরে যাওয়া যায়)
    . কেন দরকার হয়

    Current directory-তে থাকা একটা script চালাতে হলে ./script.sh লিখতে হয়, শুধু script.sh লিখলে হয় না। কারণ shell শুধু নাম দেখলে সেটাকে PATH-এ খোঁজে, current directory-তে না — আর নিরাপত্তার কারণে current directory PATH-এ রাখা হয় না। ./ লিখলে shell বুঝে যায় এটা একটা path, নাম না। বিস্তারিত Chapter 8-এ।

    Current working directory

    প্রতিটা process-এর একটা "আমি এখন কোথায় আছি" থাকে — এটাকে বলে current working directory বা cwd। Relative path সবসময় এটার সাপেক্ষে হিসাব হয়। pwd দিয়ে দেখা যায়, cd দিয়ে বদলানো যায়।

    প্রয়োজনীয় command গুলো

    ঘুরে দেখা: pwd, ls, cd

    bash

$ ls                  # এখানে কী আছে
$ ls -l               # বিস্তারিত: permission, owner, size, time
$ ls -la              # hidden file সহ
$ ls -lh              # size মানুষের পড়ার মতো (4.0K, 2.3M)

$ cd /etc             # absolute path
$ cd nginx            # relative — /etc/nginx
$ cd ..               # এক ধাপ উপরে
$ cd ~                # home-এ ফেরত
$ cd                  # খালি cd-ও home-এ নিয়ে যায়
$ cd -                # আগের জায়গায় ফেরত

    বানানো: mkdir, touch

    bash
    $ mkdir demo
$ mkdir -p a/b/c      # -p মানে মাঝের directory গুলোও বানাও
$ touch notes.txt     # খালি file বানায়

    touch-এর আসল কাজ কিন্তু file বানানো না — এর কাজ file-এর timestamp আপডেট করা। File না থাকলে সে খালি একটা বানিয়ে দেয়, তাই সবাই এটাকে "file বানানোর command" হিসেবে ব্যবহার করে।

    সরানো ও কপি: cp, mv

    bash
    $ cp notes.txt backup.txt
$ cp -r demo demo-copy    # directory কপি করতে -r লাগে

$ mv notes.txt notes-old.txt   # নাম বদলানো
$ mv notes-old.txt demo/       # সরানো

    লক্ষ্য করো — rename আর move একই command। কারণ Linux-এর কাছে দুটোই একই কাজ: directory-র তালিকা থেকে একটা এন্ট্রি সরিয়ে আরেক জায়গায় বসানো। Directory যদি "তালিকা রাখা file" হয়, তাহলে এটা যুক্তিসঙ্গত।

    মোছা: rm

    সাবধান

    Terminal-এ rm করলে জিনিসটা Recycle Bin-এ যায় না। সরাসরি চলে যায়, ফেরত আনার কোনো সহজ উপায় নেই। বিশেষ করে rm -rf কোনো প্রশ্ন না করে পুরো directory tree মুছে দেয়।

    নিয়ম করে নাও: rm -rf চাপার আগে আগে ls দিয়ে একই path টা দেখে নাও। আর rm -rf / বা rm -rf ~ জাতীয় কিছু কখনো টাইপ করে "কী হয় দেখি" করতে যেও না।

    bash
    $ rm notes.txt
$ rm -i notes.txt     # জিজ্ঞেস করে নেবে — beginner-দের জন্য ভালো অভ্যাস
$ rmdir demo          # শুধু খালি directory মোছে
$ rm -r demo          # ভেতরের সব সহ
    Hands-on

    একটা sandbox বানিয়ে সব একসাথে দেখে নাও

    bash
    $ cd ~
$ mkdir -p lab/src/utils
$ cd lab
$ touch README.md src/index.ts src/utils/date.ts
$ ls -R                # পুরো tree টা দেখো

$ cd src/utils
$ pwd
$ ls ../               # relative path দিয়ে src দেখা
$ ls ../../            # lab দেখা
$ cat ~/lab/README.md  # absolute path — যেখানেই থাকো কাজ করবে

$ cd ~/lab && rm -r lab-copy 2>/dev/null; cp -r src src-copy
$ ls

    এখন নিজেকে প্রশ্ন করো: src/utils-এ দাঁড়িয়ে ls ../../ কেন lab দেখাচ্ছে? কারণ প্রতিটা .. এক ধাপ করে উপরে তুলছে — utils → src → lab। আর cat ~/lab/README.md যেকোনো জায়গা থেকে কাজ করছে কারণ ওটা absolute path, cwd-এর উপর নির্ভরশীল না।

    যেখানে beginner আটকায়

    "cd করলাম, কিন্তু কিছু হলো না?" — cd সফল হলে কোনো output দেয় না। Linux-এর সাধারণ নিয়ম: কোনো খবর মানেই ভালো খবর। pwd দিয়ে যাচাই করো।

    "স্পেস আছে এমন নাম কাজ করছে না" — cd my folder shell-এর কাছে দুটো আলাদা argument। quote দাও: cd "my folder"।

    "cp দিয়ে folder কপি হচ্ছে না" — -r লাগবে, recursive।

    Recap

    • Directory = একটা বিশেষ file, যার ভেতরে নাম-থেকে-অবস্থান তালিকা।

    • mv দিয়েই rename আর move দুটোই হয় — কারণ ভেতরে দুটোই একই কাজ।
    • rm স্থায়ী। Recycle bin নেই।
    Chapter 05kernel

    Everything is a File

    Linux-এর সবচেয়ে বিখ্যাত কথাটা। এটা যেমন শক্তিশালী একটা ধারণা, তেমনি অর্ধেক সত্যি। দুটোই বোঝা দরকার।

    কথাটার আসল মানে

    এই কথাটার মানে "সব কিছু disk-এ file হিসেবে জমা আছে" — এমন না। আসল মানে হলো:

    মূল কথা

    Linux-এ বেশিরভাগ জিনিসের সাথে কথা বলা যায় একই কয়েকটা system call দিয়ে: open, read, write, close। জিনিসটা text file হোক, keyboard হোক, network connection হোক, বা printer — interface একই।

    মানে এটা একটা common interface-এর গল্প। ঠিক যেমন OOP-তে interface থাকলে আলাদা আলাদা class-কে একইভাবে ব্যবহার করা যায় — Linux-এ "file" হলো সেই interface টা।

    এর ফলে কী সুবিধা হয়

    একই tool দিয়ে সম্পূর্ণ ভিন্ন ভিন্ন জিনিস নিয়ে কাজ করা যায়। cat program টা জানেই না সে কী পড়ছে — সে শুধু "খোলো, পড়ো, লেখো" করে। তাই:

    bash
    $ cat notes.txt          # সাধারণ file
$ cat /proc/cpuinfo      # kernel-এর তৈরি করা তথ্য
$ cat /etc/hostname      # config
$ head -c 20 /dev/urandom | xxd   # hardware-ভিত্তিক random bytes

    চারটা সম্পূর্ণ আলাদা উৎস, একই command। এই consistency-ই Linux-এ pipe (Chapter 9) এত শক্তিশালী হওয়ার মূল কারণ।

    File-এর ধরনগুলো

    ls -l-এর প্রথম character টাই ধরন বলে দেয়:

    চিহ্নধরনকী
    -Regular fileসাধারণ data। text, image, executable।
    dDirectoryনাম-থেকে-অবস্থান তালিকা।
    lSymbolic linkআরেকটা path-এর দিকে নির্দেশ করা shortcut।
    cCharacter deviceএকটা একটা করে byte আসে/যায়। keyboard, terminal।
    bBlock deviceএক গুচ্ছ করে data। disk।
    pNamed pipeদুই process-এর মধ্যে data পাঠানোর নল।
    sSocketprocess-এর মধ্যে বা network-এ যোগাযোগ।

    /dev — device গুলো file হিসেবে

    /dev-এর জিনিসগুলো disk-এ পড়ে থাকা file নয়। এগুলো kernel-এর দেওয়া দরজা। এই দরজায় লিখলে বা পড়লে kernel সেই অনুযায়ী hardware বা internal service-এর সাথে কথা বলে।

    Pathকী করে
    /dev/nullযা লিখবে সব গায়েব। যা পড়তে চাইবে, সাথে সাথে "শেষ" বলে দেবে।
    /dev/zeroঅসীম সংখ্যক 0 byte দেয়।
    /dev/urandomঅসীম random bytes দেয়।
    /dev/sdaএকটা পুরো disk।
    /dev/ttyতোমার এখনকার terminal।

    /dev/null-কে সবাই ব্যবহার করে অপ্রয়োজনীয় output ফেলে দিতে — command 2>/dev/null মানে error গুলো দেখতে চাই না।

    Hands-on

    File interface দিয়ে হার্ডওয়্যারের সাথে কথা বলো

    bash
    $ ls -l /dev/null /dev/urandom /dev/sda 2>/dev/null
# প্রথম character লক্ষ্য করো: c মানে character device, b মানে block

$ echo "এই লেখাটা কোথায় গেল?" > /dev/null
$ cat /dev/null          # কিছুই নেই

$ head -c 16 /dev/urandom | xxd

$ echo "hello" > /dev/tty  # সরাসরি terminal-এ লেখা

$ ls -l /bin              # l দিয়ে শুরু হলে symlink

    খেয়াল করো — echo program টার কোনো ধারণা নেই সে কোথায় লিখছে। সে stdout-এ লেখে, আর shell আগেই ঠিক করে দিয়েছে stdout টা কোথায় যাবে। এই আলাদা থাকাটাই পুরো design-এর সৌন্দর্য।

    Symbolic link

    Symlink হলো একটা ছোট file যার ভেতরে শুধু আরেকটা path লেখা আছে। এটা খুললে kernel তোমাকে ঐ path-এ পাঠিয়ে দেয়।

    bash
    $ cd ~ && echo "asol data" > real.txt
$ ln -s real.txt link.txt
$ ls -l link.txt        # link.txt -> real.txt
$ cat link.txt          # asol data
$ rm real.txt
$ cat link.txt          # এখন ভেঙে গেছে
$ rm link.txt

    এই কারণেই /bin -> usr/bin কাজ করে, আর node_modules/.bin-এর জিনিসগুলোও symlink হিসেবেই থাকে।

    এই কথাটার সীমাবদ্ধতা কী

    "Everything is a file" আসলে পুরোপুরি সত্যি না, আর এটা জেনে রাখা দরকার — নাহলে পরে যখন ব্যতিক্রম দেখবে তখন mental model ভেঙে যাবে।

    • Network socket পুরোপুরি file নয়। এদের নিজস্ব system call লাগে — socket(), bind(), connect()। শুধু open() দিয়ে একটা TCP connection খোলা যায় না।
    • Process নিজে file নয়। /proc-এ তার তথ্য file আকারে দেখা যায় ঠিকই, কিন্তু process নিজে kernel-এর ভেতরের একটা structure।
    • অনেক kernel feature-এর আলাদা API আছে — signal, timer, memory mapping।

    তাই বেশি সঠিক বাক্যটা হলো: "Everything has a file descriptor" — মানে খোলা জিনিসগুলো একটা number দিয়ে চিহ্নিত হয়, এবং তাদের অনেকের সাথেই read/write দিয়ে কাজ চলে।

    File descriptor

    একটা process যখন কিছু খোলে, kernel তাকে একটা number দেয় — file descriptor বা fd। ঐ process ঐ number দিয়েই জিনিসটাকে চেনে। মনে আছে stdin=0, stdout=1, stderr=2? ওগুলো আসলে প্রতিটা process-এর প্রথম তিনটা file descriptor।

    bash
    $ ls -l /proc/self/fd
# 0, 1, 2 — এবং তারা কোথায় নির্দেশ করছে
    যেখানে beginner আটকায়

    "তাহলে সব কিছু কি হার্ডডিস্কে file হিসেবে আছে?" — না। /proc আর /dev-এর জিনিসগুলো memory-তে kernel বানিয়ে দেখায়। কথাটা storage নিয়ে না, interface নিয়ে।

    "symlink কি file-টার কপি?" — না, শুধু একটা path লেখা আছে। আসল file মুছে গেলে symlink ভেঙে যায়।

    Recap
    • "Everything is a file" মানে common interface — open/read/write/close।
    • ধরন: regular, directory, symlink, character device, block device, pipe, socket।
    • /dev-এর file গুলো kernel-এর দরজা, disk-এর জিনিস না।
    • Socket আর process এই নিয়মের বাইরে — কথাটা absolute না।
    • File descriptor = খোলা জিনিসকে চেনার number। 0/1/2 = stdin/stdout/stderr।
    Chapter 06kernel

    Users, Groups এবং Permissions

    "Permission denied" — Linux শেখার সময় সবচেয়ে বেশি দেখা error। এই chapter শেষে এই message টা দেখলে বিরক্ত না হয়ে ঠিক কী ঘটেছে সেটা বুঝতে পারবে।

    Linux multi-user কেন

    Unix-এর জন্ম এমন এক যুগে যখন একটা মেশিন অনেক মানুষ একসাথে ব্যবহার করতো। তাই শুরু থেকেই দরকার ছিল — কে কার file দেখতে পাবে, কে কী বদলাতে পারবে।

    আজকে তোমার laptop-এ তুমি একাই ব্যবহারকারী, কিন্তু ব্যবস্থাটা এখনো ঠিক ততটাই দরকারি — কারণ এখন user মানে শুধু মানুষ না। Nginx চলে www-data user হিসেবে, PostgreSQL চলে postgres হিসেবে। কেন? যাতে কোনো একটা service hack হলেও সে পুরো system-এর কিছু করতে না পারে। এই ধারণাটাকে বলে least privilege।

    User আর Group

    প্রতিটা user-এর একটা number আছে — UID। Kernel আসলে নাম চেনে না, number চেনে। নাম আর number-এর mapping থাকে /etc/passwd file-এ।

    Group হলো user-দের একটা দল। একটা user একাধিক group-এ থাকতে পারে। Group-এর number হলো GID, তালিকা /etc/group-এ।

    Group-এর কাজ কী? ধরো ৫ জন developer-কে একটা project directory-তে access দিতে হবে। প্রত্যেকের জন্য আলাদা করে permission না দিয়ে একটা dev group বানিয়ে directory টা সেই group-কে দিয়ে দাও।

    root user

    root হলো UID 0 — যার জন্য permission check প্রায় পুরোটাই বাদ যায়। root যেকোনো file পড়তে, লিখতে, মুছতে পারে।

    root নিয়ে সাবধানতা

    root হিসেবে কাজ করলে Linux তোমাকে বাধা দেবে না — ভুল command দিলেও না। "are you sure?" জিজ্ঞেস করার কেউ নেই। তাই স্বাভাবিক কাজ সবসময় normal user হিসেবে করবে, আর দরকার হলে sudo ব্যবহার করবে।

    Ownership

    প্রতিটা file-এর দুটো মালিকানা তথ্য থাকে: একজন owner (একটা user) আর একটা group।

    এই দুটোর ভিত্তিতে Linux যেকোনো user-কে তিন শ্রেণিতে ফেলে:

    • user / owner (u) — যার file
    • group (g) — file-এর group-এ যারা আছে
    • others (o) — বাকি সবাই

    গুরুত্বপূর্ণ: Linux প্রথম যেটা মিলে যায় সেটাই প্রয়োগ করে, নিচে আর নামে না। তুমি যদি owner হও, তোমার জন্য owner-এর permission-ই চূড়ান্ত — group-এ বেশি permission থাকলেও তুমি সেটা পাবে না।

    rwx

    অক্ষরFile-এর ক্ষেত্রেDirectory-র ক্ষেত্রে
    r (read)ভেতরের content পড়া যাবেভেতরে কী কী নাম আছে তার তালিকা দেখা যাবে
    w (write)content বদলানো যাবেভেতরে file বানানো / মোছা / নাম বদলানো যাবে
    x (execute)program হিসেবে চালানো যাবেdirectory-র ভেতরে ঢোকা যাবে (cd)
    Directory-র permission গুলো মাথা গুলিয়ে দেয় — একটু মন দিয়ে

    Directory-তে r আছে কিন্তু x নেই → নামগুলো দেখতে পাবে, কিন্তু কোনো file খুলতে পারবে না।

    Directory-তে x আছে কিন্তু r নেই → নাম জানা থাকলে file খুলতে পারবে, কিন্তু ls কাজ করবে না।

    আর সবচেয়ে অদ্ভুত টা: file-টার permission r--r--r-- মানে কেউ লিখতে পারবে না — কিন্তু যদি directory-তে তোমার w থাকে, তুমি file টা মুছে ফেলতে পারবে। কারণ মোছা মানে file-এ লেখা না, directory-র তালিকা থেকে একটা এন্ট্রি বাদ দেওয়া। Chapter 4-এর "directory একটা তালিকা রাখা file" — এই কথাটার সরাসরি ফল।

    Numeric notation

    প্রতিটা permission-কে একটা number দেওয়া আছে: r=4, w=2, x=1। যোগ করলেই এক অঙ্কের number পাওয়া যায়।

    rwx = 4+2+1 = 7      r-x = 4+0+1 = 5
rw- = 4+2+0 = 6      r-- = 4+0+0 = 4
--- = 0+0+0 = 0      -wx = 0+2+1 = 3

তিন অঙ্ক = owner, group, others

  7   5   5      →  rwxr-xr-x
  │   │   └── others: পড়তে ও চালাতে পারবে
  │   └────── group : পড়তে ও চালাতে পারবে
  └────────── owner : সব
    NumberSymbolসাধারণত কোথায়
    644rw-r--r--সাধারণ file। মালিক লিখতে পারে, বাকিরা শুধু পড়ে।
    755rwxr-xr-xProgram আর directory। সবাই ঢুকতে/চালাতে পারে, লিখতে পারে শুধু মালিক।
    600rw-------গোপন file। SSH private key, .env।
    700rwx------ব্যক্তিগত directory। যেমন ~/.ssh।

    chmod — permission বদলানো

    bash
    # numeric — পুরো permission একবারে বসিয়ে দেয়
$ chmod 644 notes.txt
$ chmod 755 deploy.sh

# symbolic — শুধু যেটুকু বদলাতে চাও
$ chmod +x deploy.sh        # সবার জন্য execute যোগ
$ chmod u+x deploy.sh       # শুধু owner-এর জন্য
$ chmod go-w notes.txt      # group আর others থেকে write বাদ
$ chmod -R 755 mydir        # ভেতরের সব কিছুতে
    যা কখনো করবে না

    chmod 777 মানে "পৃথিবীর যে কেউ এটা পড়তে, বদলাতে, চালাতে পারবে"। Stack Overflow-তে অনেকে সমস্যা সমাধানের সহজ উপায় হিসেবে এটা দেয় — এটা সমাধান না, নিরাপত্তা ফুটো করে দেওয়া। আসল সমস্যা প্রায় সবসময়ই ownership ভুল থাকা, permission কম থাকা না। chown দিয়ে ঠিক করো।

    আর sudo chmod -R 777 / জাতীয় কিছু চালালে system কার্যত অকেজো হয়ে যায়।

    chown — মালিকানা বদলানো

    bash
    $ sudo chown mostofa notes.txt          # owner
$ sudo chown mostofa:dev notes.txt      # owner:group
$ sudo chown -R www-data:www-data /var/www

    মালিকানা বদলাতে sudo লাগে — নাহলে যে কেউ নিজের file অন্যকে দিয়ে দায় এড়াতে পারতো।

    sudo আসলে কী

    sudo মানে "superuser do"। এটা একটা command চালায় root-এর ক্ষমতা নিয়ে, তারপর ক্ষমতা ফিরিয়ে দেয়। তুমি root হয়ে যাও না — শুধু ঐ একটা command root হিসেবে চলে।

    sudo apt install nginx
│    └─────────────────┘
│      এই অংশটুকু root হিসেবে চলে
└─ তুমি কিন্তু mostofa-ই আছো

    কে sudo চালাতে পারবে তা ঠিক করা থাকে /etc/sudoers-এ। Ubuntu-তে sudo group-এ থাকলেই হয়। sudo-র প্রতিটা ব্যবহার log হয়, তাই server-এ কে কী করলো সেটা খুঁজে বের করা যায়।

    sudo আর root এক নয়

    sudo = নির্দিষ্ট একটা command root-এর ক্ষমতায় চালানো। root = নিজেই ঐ user হয়ে বসে থাকা (sudo -i দিয়ে হওয়া যায়)।

    একটা ফাঁদ: sudo echo "x" > /etc/config কাজ করে না। কারণ > redirection টা shell করে, আর সেই shell তো root না। echo-টা root হিসেবে চলে ঠিকই, কিন্তু file খোলার কাজটা আগেই তোমার shell করে ফেলে ব্যর্থ হয়। সমাধান: echo "x" | sudo tee /etc/config।

    Hands-on

    Permission নিজের হাতে ভেঙে আবার ঠিক করো

    bash
    $ cd ~ && mkdir -p permlab && cd permlab
$ echo "gopon kotha" > secret.txt
$ ls -l secret.txt

# নিজের read permission কেড়ে নাও
$ chmod 000 secret.txt
$ cat secret.txt          # Permission denied
$ ls -l secret.txt        # কিন্তু নাম-তথ্য এখনো দেখা যাচ্ছে!

$ chmod 600 secret.txt
$ cat secret.txt          # আবার কাজ করছে

    লক্ষ্য করো: chmod 000 করার পরেও ls -l কাজ করছে। কারণ নাম, size, permission — এসব তথ্য directory-তে আছে, file-এর ভেতরে না। File-এর permission শুধু ভেতরের content-কে পাহারা দেয়।

    Executable বানানো

    bash
    $ printf '#!/bin/bash\necho "ami cholchi"\n' > run.sh
$ ./run.sh                # Permission denied
$ ls -l run.sh            # কোনো x নেই
$ chmod +x run.sh
$ ls -l run.sh            # এখন x আছে
$ ./run.sh                # চলছে

$ cd ~ && rm -r permlab

    File-এর content এক বিন্দুও বদলায়নি। শুধু একটা permission bit বদলেছে, আর তাতেই Linux এটাকে "চালানোর জিনিস" হিসেবে মেনে নিয়েছে। এই কারণেই git থেকে clone করা script-এ প্রায়ই chmod +x দিতে হয়।

    Recap
    • User-এর UID, group-এর GID। Kernel নাম না, number চেনে।
    • root = UID 0, permission check প্রায় বাদ যায়।
    • প্রতিটা file-এর owner + group; সবাইকে u/g/o তিন ভাগে ফেলা হয়।
    • Directory-তে x = ঢোকা, r = তালিকা দেখা, w = ভেতরে file বানানো/মোছা।
    • r=4, w=2, x=1। 644 সাধারণ file, 755 program/directory, 600 গোপন।
    • chmod permission, chown ownership, sudo এক command-এর জন্য root ক্ষমতা।
    • 777 কোনো সমাধান না — ownership ঠিক করো।

    Processes

    Filesystem হলো Linux-এর স্থির দিক। Process হলো তার চলমান দিক। এই দুটো বুঝে ফেললে Linux-এর মূল কাঠামোটা দাঁড়িয়ে যায়।

    Program বনাম Process

    এই পার্থক্যটা ছোট মনে হলেও এটাই process বোঝার চাবি।

    ProgramProcess
    Disk-এ পড়ে থাকা একটা fileMemory-তে চলতে থাকা একটা instance
    নিষ্ক্রিয়, কিছু করে নাসক্রিয়, CPU সময় নিচ্ছে
    একটাই থাকেএকই program থেকে অনেকগুলো হতে পারে
    /usr/bin/nodeএখন চলতে থাকা তোমার তিনটা Node server
    Analogy

    Program হলো রান্নার রেসিপি — কাগজে লেখা, একটাই কপি। Process হলো সেই রেসিপি ধরে চুলায় চলতে থাকা রান্না। একই রেসিপি দিয়ে তিনটা চুলায় একসাথে তিনটা রান্না চলতে পারে — প্রতিটা আলাদা, প্রতিটার নিজের হাঁড়ি, নিজের অগ্রগতি।

    Process কী নিয়ে গঠিত

    Kernel প্রতিটা process-এর জন্য কিছু তথ্য রাখে:

    • PID — process ID, একটা unique number
    • PPID — parent process ID, কে একে জন্ম দিয়েছে
    • নিজস্ব memory — অন্য process এতে হাত দিতে পারে না
    • File descriptor table — কোন কোন file/socket খোলা আছে (মনে আছে? 0,1,2)
    • Owner (UID) — কোন user-এর হয়ে চলছে; permission এখান থেকেই যাচাই হয়
    • Current working directory
    • Environment variables — Chapter 8
    • State — চলছে, না ঘুমাচ্ছে, না অপেক্ষা করছে

    লক্ষ্য করো — এই তালিকার কতগুলো জিনিস আগের chapter থেকে চেনা। Process হলো সেই জায়গা যেখানে permission, filesystem, file descriptor সব এসে মেলে।

    Process কীভাবে জন্মায়

    Linux-এ নতুন process বানানোর একটাই মূল উপায়, আর সেটা প্রথমে অদ্ভুত লাগে — একটা process নিজের একটা কপি বানায়।

    bash (PID 2410)
   │
   │  fork()   →  নিজের হুবহু একটা copy বানায়
   ▼
bash-copy (PID 2856)   ← এখনো bash-ই
   │
   │  exec("/usr/bin/ls")  →  নিজের জায়গায় ls কে বসিয়ে দেয়
   ▼
ls (PID 2856)          ← PID একই, কিন্তু ভেতরের program বদলে গেছে
   │
   │  কাজ শেষ, exit(0)
   ▼
bash (PID 2410) আবার prompt দেখায়

    এই দুই-ধাপের নকশাটা কেন? কারণ fork আর exec-এর মাঝখানে একটা ফাঁক থাকে, আর সেই ফাঁকে child process নিজের পরিবেশ সাজিয়ে নিতে পারে — কোন file descriptor কোথায় যাবে, কোন directory-তে থাকবে, কোন user হিসেবে চলবে। Pipe আর redirection (Chapter 9) ঠিক এই ফাঁকটাকেই কাজে লাগায়।

    Parent, child আর process tree

    প্রতিটা process-এরই একটা parent আছে। উপরে উঠতে থাকলে সবার উপরে পাওয়া যায় PID 1 — যেটা init process, আধুনিক Ubuntu-তে systemd। Boot-এর সময় kernel এটাকে চালু করে, বাকি সব process এর বংশধর।

    systemd (PID 1)
├── sshd
│   └── sshd: mostofa
│       └── bash (2410)
│           ├── node (3120)      ← তোমার dev server
│           └── ls (2856)
├── nginx
│   ├── nginx: worker
│   └── nginx: worker
└── postgres

    এই গাছটা কেন গুরুত্বপূর্ণ? কারণ parent মারা গেলে বা terminal বন্ধ করলে child-দের কী হয় সেটা এই সম্পর্কের উপর নির্ভর করে। SSH connection কেটে গেলে চলতে থাকা কাজ কেন বন্ধ হয়ে যায় — এই গাছেই তার উত্তর।

    Foreground আর background

    Command চালালে সাধারণত shell অপেক্ষা করে — এটাই foreground। শেষে & দিলে shell অপেক্ষা করে না, prompt সাথে সাথে ফিরে আসে — এটা background।

    bash
    $ sleep 60          # terminal আটকে গেল
# Ctrl+C  → বন্ধ করে দাও

$ sleep 60 &        # background-এ চলছে, prompt ফিরে এসেছে
$ jobs              # এই shell-এর background কাজের তালিকা
$ fg                # foreground-এ ফিরিয়ে আনা
# Ctrl+Z  → থামিয়ে দাও (মারা না, শুধু বিরতি)
$ bg                # থেমে থাকা কাজকে background-এ চালু করো
    Keyকী হয়
    Ctrl+Cবন্ধ করার অনুরোধ পাঠায় (SIGINT)। বেশিরভাগ program গুছিয়ে বন্ধ হয়।
    Ctrl+Zথামিয়ে দেয় (SIGTSTP)। process মরে না, শুধু বিরতি নেয়।
    Ctrl+D"input শেষ" জানায়। এটা কোনো signal না। তাই shell-এ চাপলে shell বন্ধ হয়ে যায়।

    Process দেখা: ps, top, htop

    bash
    $ ps                    # শুধু এই terminal-এর process
$ ps aux                # system-এর সব process
$ ps aux | grep node    # শুধু node গুলো
$ ps -ef --forest       # গাছ আকারে (Linux)
$ pstree                # আরও পরিষ্কার গাছ

$ top                   # live view; q চেপে বের হও
$ htop                  # সুন্দর version (install করতে হতে পারে)

    ps aux-এর column গুলো: USER (কার হয়ে চলছে), PID, %CPU, %MEM, STAT (অবস্থা), COMMAND। Server-এ কিছু ধীর হয়ে গেলে top খুলে কোন process CPU খাচ্ছে সেটা দেখাই প্রথম কাজ।

    kill — process থামানো

    নামটা ভয়ংকর, কিন্তু kill আসলে signal পাঠায় — মানে একটা ছোট বার্তা। কোন signal পাঠাচ্ছো তার উপর নির্ভর করে কী হবে।

    SignalNumberমানে
    SIGTERM15"দয়া করে গুছিয়ে বন্ধ হও"। default। program চাইলে ধরতে পারে, file save করে, connection বন্ধ করে তারপর বের হয়।
    SIGINT2Ctrl+C যেটা পাঠায়।
    SIGKILL9Kernel সরাসরি মেরে ফেলে। process কিছু করার সুযোগ পায় না।
    bash
    $ kill 3120          # SIGTERM — ভদ্র অনুরোধ
$ kill -9 3120       # SIGKILL — শেষ উপায়
$ pkill -f "node server.js"   # নাম দিয়ে
    kill -9 সবসময় নয়

    অনেকে অভ্যাসবশত সরাসরি -9 দেয়। কিন্তু SIGKILL পেলে process কিছুই গুছিয়ে নিতে পারে না — খোলা file আধা-লেখা থাকতে পারে, database transaction ঝুলে থাকতে পারে, lock file পড়ে থাকতে পারে। আগে সাধারণ kill দাও, কয়েক সেকেন্ড অপেক্ষা করো, তারপরও না মরলে -9।

    Hands-on

    Process-এর জন্ম আর মৃত্যু দেখো

    bash
    $ echo $$                # এই shell-এর PID
$ sleep 300 &
$ jobs
$ ps -f                  # PPID column দেখো

# sleep-এর PPID কি তোমার shell-এর PID-এর সমান?

$ kill %1                # job number দিয়ে মারা
$ jobs                   # আর নেই

    ps -f-এর output-এ sleep-এর PPID আর echo $$-এর number এক হওয়ার কথা। এটাই প্রমাণ যে shell তোমার command গুলোর parent — সে fork করে child বানিয়েছে।

    একই program, আলাদা process

    bash
    $ sleep 200 & sleep 200 & sleep 200 &
$ ps aux | grep "sleep 200" | grep -v grep

    তিনটা আলাদা PID, অথচ disk-এ sleep program টা একটাই। একটা program, তিনটা process — এটাই chapter-এর শুরুর পার্থক্যটার জীবন্ত রূপ। pkill -f "sleep 200" দিয়ে সবগুলো একসাথে সরিয়ে দাও।

    যেখানে beginner আটকায়

    "Terminal বন্ধ করলে আমার server বন্ধ হয়ে যায় কেন?" — কারণ সে তোমার shell-এর child। Shell মরলে child-দের কাছেও বন্ধ হওয়ার সংকেত যায়। স্থায়ীভাবে চালাতে হলে systemd service বানাতে হয় (Chapter 11), অথবা nohup/tmux ব্যবহার করতে হয়।

    "Port already in use — কিন্তু কিছু তো চলছে না" — চলছে, তুমি দেখতে পাচ্ছো না। ss -tlnp | grep 3000 দিয়ে PID বের করে kill করো।

    Environment এবং PATH

    "command not found" আর ".env কাজ করছে না" — developer জীবনের দুটো নিত্যসঙ্গী সমস্যা। দুটোরই মূল এই chapter-এ।

    Environment variable কী

    Environment variable হলো নাম-মান জোড়া কিছু string, যা প্রতিটা process তার সাথে বহন করে। Process চালু হওয়ার সময় kernel এগুলো তাকে ধরিয়ে দেয়।

    এগুলোর কাজ কী? Program-কে তার চারপাশের পরিস্থিতি জানানো — কে চালাচ্ছে, home কোথায়, কোন ভাষা, কোন database-এ connect করতে হবে। মানে configuration যেটা code-এর বাইরে থাকে।

    Variableকী বলে
    $HOMEতোমার home directory। ~ আসলে এটারই মান।
    $USERবর্তমান user-এর নাম।
    $PATHExecutable কোন কোন directory-তে খুঁজতে হবে।
    $PWDCurrent working directory।
    $SHELLLogin shell কোনটা।
    $LANGভাষা ও character encoding।
    bash
    $ echo $HOME
$ echo $USER
$ printenv            # সবগুলো
$ printenv | wc -l    # কয়টা আছে

    Shell variable বনাম environment variable

    এই পার্থক্যটাই export-এর অস্তিত্বের কারণ।

    • Shell variable — শুধু এই shell-এর ভেতরে আছে। Child process এটা দেখতে পায় না।
    • Environment variable — child process-এর কাছেও চলে যায়।

    মনে করো Chapter 7-এর fork/exec — shell যখন fork করে, সে environment-টা copy করে child-কে দেয়। কিন্তু সাধারণ shell variable environment-এর অংশ না, তাই সেটা যায় না। export মানে হলো "এই variable টাকে environment-এ ঢুকিয়ে দাও, যাতে child-রা পায়"।

    Hands-on

    export কেন লাগে, চোখে দেখো

    bash
    $ MY_VAR="hello"
$ echo $MY_VAR            # hello — এই shell দেখতে পাচ্ছে
$ bash -c 'echo "child dekhche: [$MY_VAR]"'
# খালি — child পায়নি

$ export MY_VAR
$ bash -c 'echo "child dekhche: [$MY_VAR]"'
# hello — এখন পেয়েছে

    bash -c '...' একটা নতুন child shell চালু করে। প্রথমবার সে কিছুই পায়নি, export-এর পরে পেয়েছে। এই একটা পরীক্ষাতেই environment-এর পুরো নিয়মটা ধরা পড়ে: environment উপর থেকে নিচে যায়, নিচ থেকে উপরে আসে না।

    এখান থেকেই একটা বিখ্যাত সমস্যার উত্তর

    একটা script-এর ভেতরে cd বা export করলে script শেষ হওয়ার পর তোমার shell-এ তার কোনো প্রভাব থাকে না। কারণ script একটা child process হিসেবে চলে, আর child-এর পরিবর্তন parent-এ ফিরে আসে না।

    এই কারণেই nvm, conda এসব tool source script.sh দিয়ে চালাতে বলে — source নতুন process বানায় না, বর্তমান shell-এর ভেতরেই line গুলো চালায়।

    PATH — সবচেয়ে গুরুত্বপূর্ণ variable

    $PATH হলো colon দিয়ে আলাদা করা কিছু directory-র তালিকা। তুমি যখন node লেখো, shell এই তালিকার directory গুলোতে বাঁ থেকে ডানে খুঁজতে থাকে, আর প্রথম যেখানে পায় সেটাই চালায় — বাকি গুলো আর দেখে না।

    bash
    $ echo $PATH
/home/mostofa/.nvm/versions/node/v20.11.0/bin:/usr/local/bin:/usr/bin:/bin

$ echo $PATH | tr ':' '\n'    # লাইন করে দেখো
    তুমি লিখলে:  node

shell খোঁজে ক্রমানুসারে:
  1. /home/mostofa/.nvm/.../bin/node   ← পাওয়া গেল, এটাই চলবে
  2. /usr/local/bin/node               ← আর দেখাই হলো না
  3. /usr/bin/node
  4. /bin/node

command not found = কোনোটাতেই পাওয়া যায়নি
    এই একটা নিয়ম অনেক রহস্য খুলে দেয়

    "nvm দিয়ে version বদলালাম, কিন্তু node -v পুরনোটাই দেখায়" → nvm আসলে শুধু PATH-এর শুরুতে অন্য একটা directory বসিয়ে দেয়। PATH ঠিকমতো update না হলে shell পুরনোটাই আগে পেয়ে যায়।

    "sudo দিলে command not found কেন?" → নিরাপত্তার জন্য sudo PATH-টা নতুন করে সাজায়, তাই তোমার ব্যক্তিগত directory গুলো বাদ পড়ে যায়।

    Hands-on

    নিজের একটা command বানাও

    bash
    $ mkdir -p ~/bin
$ printf '#!/bin/bash\necho "amar nijer command!"\n' > ~/bin/hello
$ chmod +x ~/bin/hello

$ hello                   # command not found
$ ~/bin/hello             # কাজ করে — কারণ পুরো path দিয়েছি

$ export PATH="$HOME/bin:$PATH"
$ hello                   # এখন কাজ করে
$ which hello

    File টা আগেও ছিল, executable-ও ছিল। শুধু shell জানতো না কোথায় খুঁজতে হবে। PATH-এ directory টা যোগ করার সাথে সাথেই সেটা "command" হয়ে গেল। Command আর file-এর মধ্যে পার্থক্য শুধু এটুকুই — shell তাকে খুঁজে পায় কি না।

    লক্ষ্য করো "$HOME/bin:$PATH" লেখায় পুরনো PATH-টা শেষে জোড়া লাগানো হয়েছে। শুধু export PATH="$HOME/bin" লিখলে বাকি সব command হারিয়ে যেত।

    .bashrc আর shell session

    উপরের export PATH=... শুধু এই terminal-এর জন্য। নতুন terminal খুললেই হারিয়ে যাবে — কারণ সেটা নতুন process, নতুন environment।

    স্থায়ী করতে হলে shell চালু হওয়ার সময় যে file পড়ে, সেখানে লিখতে হবে। Bash-এ সেটা ~/.bashrc।

    bash
    $ echo 'export PATH="$HOME/bin:$PATH"' >> ~/.bashrc
$ source ~/.bashrc      # এখনই কার্যকর করতে
    >> ব্যবহার করো, > নয়

    >> শেষে যোগ করে। > পুরো file মুছে নতুন করে লেখে — একটা > বেশি টাইপ করলে পুরো .bashrc হারিয়ে যাবে।

    Zsh ব্যবহার করলে file টা ~/.zshrc। এই জন্যই "installation guide-এ .bashrc লেখা ছিল, কিন্তু আমার কাজ করছে না" — তুমি হয়তো zsh-এ আছো।

    Development-এ environment variable কেন গুরুত্বপূর্ণ

    • Secret code-এ রাখা যায় না। Database password, API key — এগুলো environment থেকে আসে, তাই git-এ যায় না।
    • একই code সব জায়গায় চলে। DATABASE_URL local-এ এক, production-এ আরেক — code এক থাকে।

    • Twelve-factor app-এর একটা মূল নিয়মই হলো "config থাকবে environment-এ"।

    Chapter 09shell + kernel

    Input, Output এবং Pipes

    Linux-এর সবচেয়ে সুন্দর design সিদ্ধান্তটা এখানে। ছোট ছোট program, যারা একে অন্যের কথা কিছুই জানে না, অথচ জোড়া দিলে জটিল কাজ করে ফেলে।

    আবার সেই তিনটা চ্যানেল

    Chapter 2-এ দেখেছিলে প্রতিটা process তিনটা খোলা চ্যানেল নিয়ে জন্মায়। এখন সেগুলো নিয়ে আসল কাজ করব।

                  ┌──────────────┐
   keyboard ──►│              │──► screen   (stdout, fd 1)
  (stdin, 0)   │   PROCESS    │
               │              │──► screen   (stderr, fd 2)
               └──────────────┘

Program জানেই না ওপাশে কী আছে।
সে শুধু fd 0 থেকে পড়ে, fd 1 আর 2 তে লেখে।

    এই "না জানা"-টাই মূল কথা। grep-কে যদি জিজ্ঞেস করা হয় সে কোথা থেকে data পাচ্ছে, সে বলতে পারবে না। তাই shell চাইলে ওপাশে যা খুশি লাগিয়ে দিতে পারে — file, আরেকটা program, বা কিছুই না।

    মনে আছে Chapter 7-এর fork আর exec-এর মাঝখানের ফাঁক? Redirection ঠিক সেখানেই ঘটে — child process নিজেকে program-এ পরিণত করার আগেই shell তার fd গুলো অন্যদিকে ঘুরিয়ে দেয়।

    Output redirect: > আর >>

    bash
    $ ls -l > list.txt        # file নতুন করে লেখে (আগেরটা মুছে যায়)
$ date >> list.txt        # শেষে যোগ করে
$ cat list.txt
    > নীরবে মুছে দেয়

    command > important.txt চালালে important.txt-এর পুরনো সব content সাথে সাথে চলে যায় — কোনো সতর্কবার্তা ছাড়াই। এমনকি command টা ব্যর্থ হলেও file টা ততক্ষণে খালি হয়ে গেছে, কারণ shell file টা আগে খালি করে, তারপর program চালায়। বিদ্যমান file-এ লেখার সময় >> ভাবো।

    Error আলাদা করে সামলানো

    stdout হলো fd 1, stderr হলো fd 2। সংখ্যাটা >-এর ঠিক আগে বসিয়ে দিলে shell বুঝে যায় কোন চ্যানেলের কথা বলছো।

    bash
    $ ls /etc /nope > out.txt          # শুধু stdout file-এ
$ ls /etc /nope 2> err.txt         # শুধু stderr file-এ
$ ls /etc /nope > out.txt 2> err.txt   # দুটো আলাদা file-এ
$ ls /etc /nope > all.txt 2>&1     # দুটোই এক জায়গায়
$ ls /etc /nope &> all.txt         # উপরেরটারই সংক্ষিপ্ত রূপ (bash)

$ find / -name "*.conf" 2>/dev/null    # error গুলো ফেলে দাও

    2>&1-এর মানে: "fd 2 কে ঐ জায়গায় পাঠাও যেখানে fd 1 এখন যাচ্ছে"। &1-এর & টা না দিলে shell ভাববে 1 নামের একটা file-এর কথা বলছো।

    শেষ example টা খুব কাজে লাগে — find / চালালে অনেক "Permission denied" আসে যেগুলো তোমার দরকার নেই। ওগুলো /dev/null-এ পাঠিয়ে দিলে শুধু আসল result দেখা যায়। মনে আছে Chapter 5-এ /dev/null ছিল kernel-এর একটা দরজা যেখানে সব হারিয়ে যায়?

    Input redirect: <

    bash
    $ wc -l < /etc/passwd     # file-টাকে stdin বানিয়ে দেওয়া
$ wc -l /etc/passwd       # file-টাকে argument হিসেবে দেওয়া

    দুটোর output প্রায় এক, কিন্তু পার্থক্য আছে — প্রথমটায় wc জানেই না file-এর নাম কী, তাই সে শুধু number ছাপে। দ্বিতীয়টায় সে নাম জানে, তাই নাম সহ ছাপে। এটাই stdin আর argument-এর পার্থক্য।

    Pipe — |

    Pipe হলো এই chapter-এর মূল জিনিস। a | b মানে: a-র stdout কে সরাসরি b-র stdin-এ জুড়ে দাও।

    ps aux | grep node | wc -l

┌─────────┐        ┌────────┐        ┌────────┐
│ ps aux  │ stdout │  grep  │ stdout │  wc -l │ stdout
│         │───────►│  node  │───────►│        │───────► screen
└─────────┘  pipe  └────────┘  pipe  └────────┘

তিনটা process একসাথে চলছে।
কেউ কারও কথা জানে না — সবাই শুধু 0 থেকে পড়ে, 1 এ লেখে।
    Pipe file নয়

    Data disk-এ কোথাও জমা হয় না। Kernel memory-তে একটা buffer রাখে, আর তিনটা process একই সময়ে চলে। ps শেষ হওয়ার অপেক্ষা করে grep শুরু হয় না — ps যা যা লিখছে, grep তখনই পড়ছে।

    এই কারণেই বিশাল file-এ pipe চালানো যায় — পুরোটা কখনো memory-তে ধরে রাখা লাগে না।

    Unix philosophy

    Pipe এত ভালো কাজ করে কারণ Unix-এর tool গুলো একটা নির্দিষ্ট দর্শন মেনে বানানো:

    মূল নিয়ম

    "Small tools that do one thing well, and combine them."

    • প্রতিটা program একটা কাজ করে, ভালোভাবে করে।
    • সবাই text নিয়ে কাজ করে — তাই সবাই সবার সাথে জোড়া লাগে।
    • Program গুলো stdin থেকে পড়ে, stdout-এ লেখে — কেউ কারও উপর নির্ভরশীল না।
    • সফল হলে চুপ থাকে। খবর না থাকা মানে ভালো খবর।

    ফলাফল: grep-এর লেখক কখনো ps-এর কথা ভাবেননি, তবু দুটো নিখুঁতভাবে একসাথে কাজ করে। এই ধারণাটা সরাসরি চলে গেছে microservice architecture, Unix-style CLI design, এমনকি functional programming-এর composition-এ।

    Hands-on

    ধাপে ধাপে একটা pipeline বানাও

    প্রতিটা step আলাদা করে চালাও আর দেখো ঠিক কী যোগ হলো।

    bash
    $ cat /etc/passwd
# সব লাইন — অনেক বেশি

$ cut -d: -f7 /etc/passwd
# ৭ম column: প্রতিটা user-এর shell

$ cut -d: -f7 /etc/passwd | sort
# সাজানো — একই জিনিস এখন পাশাপাশি

$ cut -d: -f7 /etc/passwd | sort | uniq -c
# কোন shell কতজন ব্যবহার করে

$ cut -d: -f7 /etc/passwd | sort | uniq -c | sort -rn
# সবচেয়ে বেশি ব্যবহৃতটা উপরে

    পাঁচটা ছোট tool, কেউ কারও কথা জানে না, তবু মিলে একটা পূর্ণাঙ্গ report তৈরি হলো। এটাই Unix philosophy-র বাস্তব রূপ। uniq -c-এর আগে sort কেন লাগলো? কারণ uniq শুধু পাশাপাশি একই লাইন ধরতে পারে — সে পুরো file মনে রাখে না। এটাই "একটা কাজ, ভালোভাবে"।

    Pipe সত্যিই stream কি না দেখো

    bash
    $ yes | head -3
# yes অসীমবার "y" লেখে — কিন্তু ৩টার পর সব থেমে যায়

    yes কখনো থামার কথা না। কিন্তু head ৩ লাইন নিয়ে বন্ধ হয়ে যায়, ফলে pipe-এর ওপাশ বন্ধ হয়ে যায় আর kernel yes-কে থামিয়ে দেয়। যদি pipe একটা file হতো, তাহলে infinite data লিখতে গিয়ে disk ভরে যেত। এটাই প্রমাণ যে pipe একটা live stream।

    দুটো দরকারি জিনিস

    bash
    # tee — মাঝপথে output ধরে রাখা
$ ps aux | tee snapshot.txt | grep node

# sudo-র সাথে file লেখা (Chapter 6-এর সেই সমস্যা)
$ echo "127.0.0.1 myapp.local" | sudo tee -a /etc/hosts

    দ্বিতীয়টা মনে রাখার মতো। sudo echo ... >> /etc/hosts কাজ করে না কারণ redirection টা তোমার নিজের shell করে, আর সে root না। কিন্তু tee একটা আলাদা program — তাকে sudo দিয়ে চালানো যায়।

    যেখানে beginner আটকায়

    "grep কিছু পাচ্ছে না, অথচ error টা screen-এ দেখতে পাচ্ছি" — কারণ error stderr-এ যায়, আর pipe শুধু stdout নেয়। command 2>&1 | grep ... লিখতে হবে।

    ps aux | grep node-এ grep নিজেই দেখা যায় — কারণ grep নিজেও তো একটা process, আর তার command line-এ "node" শব্দটা আছে। | grep -v grep দিয়ে বাদ দাও।

    | আর > গুলিয়ে ফেলা — | আরেকটা program-এর দিকে পাঠায়, > একটা file-এ পাঠায়। ls | file.txt লিখলে shell file.txt নামে একটা command খুঁজবে।

    হাতে-কলমে দেখো

    → Pipe ও Redirection simulator — fd 0, 1, 2 — কোন তীর কোথায় যাচ্ছে চোখে দেখো। make | grep error-এর ফাঁদটাও আছে।

    Recap
    • Program জানে না তার stdin/stdout কোথায় লাগানো — shell সেটা ঠিক করে দেয়।
    • > মুছে লেখে, >> যোগ করে, < file কে stdin বানায়।
    • 2> শুধু error, 2>&1 error কেও stdout-এর সাথে মেলায়।
    • | এক program-এর stdout কে পরেরটার stdin-এ জোড়ে; সবাই একসাথে চলে।
    • Pipe stream, file না — তাই বিশাল বা অসীম data-তেও কাজ করে।
    • Unix philosophy: ছোট tool, একটা কাজ, text দিয়ে জোড়া।

    Packages এবং Software Installation

    Linux-এ software install করতে কোনো website থেকে installer নামাতে হয় না। কেন হয় না, আর তার বদলে কী হয় — সেটাই এই chapter।

    Package কী

    Package হলো একটা compressed file, যার ভেতরে থাকে: program-এর file গুলো, কোন file কোথায় বসবে সেই তথ্য, আর কিছু metadata — নাম, version, আর কোন কোন অন্য package দরকার।

    Ubuntu-তে এদের extension .deb। Red Hat পরিবারে .rpm।

    Dependency

    প্রায় কোনো software একা চলে না। Nginx-এর দরকার SSL library, PostgreSQL-এর দরকার আরও কয়েকটা library। এই "এটা চলার জন্য ওটা লাগবে" সম্পর্কটাই dependency।

    প্রতিটা package নিজের dependency-র তালিকা নিজের ভেতরেই বহন করে। তাই একটা package install করতে গেলে system আপনাআপনি বাকিগুলোও নিয়ে আসে।

    nginx
 ├── libssl3        (নাহলে HTTPS চলবে না)
 ├── libpcre3
 └── nginx-common
      └── ...

একটা install command, পুরো গাছ সামলানো হয়ে যায়।

    Repository

    Repository হলো একটা server, যেখানে হাজার হাজার package সাজানো আছে — সবগুলো ঐ distribution-এর জন্য test করা, আর ডিজিটাল স্বাক্ষর করা।

    এই স্বাক্ষরের ব্যাপারটাই মূল নিরাপত্তা। তোমার system-এর কাছে Ubuntu-র public key আছে, তাই সে যাচাই করতে পারে package টা সত্যিই Ubuntu থেকে এসেছে, মাঝপথে কেউ বদলে দেয়নি।

    তুলনা করে দেখো

    Windows-এ software install মানে সাধারণত: Google-এ খোঁজা → একটা website → .exe নামানো → আশা করা যে এটা আসল। প্রতিটা ধাপে ভুল হওয়ার সুযোগ আছে।

    Linux-এ: sudo apt install nginx। উৎস যাচাই করা, dependency সামলানো, update-ও একই জায়গা থেকে আসবে। npm বা NuGet-এর যে সুবিধাটা তুমি চেনো, Linux সেটা পুরো operating system-এর জন্য করে।

    Package manager

    Package manager হলো সেই program যে এই পুরো ব্যবস্থাটা চালায় — repository-র সাথে কথা বলা, dependency হিসাব করা, file গুলো ঠিক জায়গায় বসানো, কী কী install আছে তার হিসাব রাখা, আর মোছার সময় গুছিয়ে মোছা।

    DistributionPackage managerFormat
    Ubuntu, Debianapt.deb

    Docker-এর Alpine image এত ছোট হওয়ার একটা কারণ এই apk আর তার minimal package গুলো — এই জন্যই Dockerfile-এ apt-get লিখলে Alpine-এ কাজ করে না।

    apt — মূল কাজগুলো

    apt update — তালিকা হালনাগাদ করা

    bash
    $ sudo apt update

    এটা কোনো software update করে না। এটা শুধু repository থেকে "এখন কোন package-এর কোন version পাওয়া যাচ্ছে" — সেই তালিকাটা নামায়।

    নাম দেখে এখানেই সবচেয়ে বেশি ভুল হয়। মনে রাখার সহজ উপায়: update মানে catalog নামানো, upgrade মানে জিনিস নামানো।

    apt install

    bash
    $ sudo apt install htop
$ sudo apt install htop curl git      # একসাথে অনেকগুলো
$ apt show htop                       # install না করে তথ্য দেখা
$ apt search json                     # খোঁজা

    যদি "Unable to locate package" আসে, প্রথম কাজ sudo apt update চালানো — সম্ভবত তোমার catalog টা পুরনো।

    apt remove আর apt purge

    bash
    $ sudo apt remove htop         # program মোছে, config রাখে
$ sudo apt purge htop          # config সহ মোছে
$ sudo apt autoremove          # অনাথ dependency গুলো পরিষ্কার

    remove config রেখে দেয় কেন? কারণ পরে আবার install করলে তোমার সেটিং ফিরে পাওয়া যায়। পুরোপুরি নতুন করে শুরু করতে চাইলে purge।

    apt upgrade

    bash
    $ sudo apt update && sudo apt upgrade

    এই দুটো একসাথে চালানোই স্বাভাবিক নিয়ম — আগে catalog, তারপর আসল update। মাঝের && মানে "প্রথমটা সফল (exit status 0) হলেই দ্বিতীয়টা চালাও"। Chapter 2-এর exit status এখানে কাজে লাগছে।

    Hands-on

    Package manager কী কী করছে দেখো

    bash
    $ sudo apt update
$ apt show tree            # dependency আর size দেখো
$ sudo apt install tree

$ which tree               # কোথায় বসলো?
$ tree -L 2 /usr

$ dpkg -L tree             # এই package ঠিক কোন কোন file বসিয়েছে
$ dpkg -S $(which tree)    # উল্টো প্রশ্ন: এই file কোন package-এর?

    which tree দেখাবে /usr/bin/tree — মানে package manager executable টা PATH-এর ভেতরের একটা directory-তে বসিয়েছে, তাই সাথে সাথেই command হিসেবে কাজ করছে। Chapter 8-এর PATH আর এই chapter এখানে এসে মিলে গেল।

    dpkg -L আর dpkg -S দুটো উল্টো দিকের প্রশ্ন — একটা package থেকে file, আরেকটা file থেকে package। Server-এ "এই অদ্ভুত file টা কোথা থেকে এলো" খুঁজতে দ্বিতীয়টা কাজে লাগে।

    ইন্টারনেট থেকে script চালানোর আগে

    অনেক জায়গায় লেখা থাকে curl ... | sudo bash। এর মানে হলো: একটা অচেনা server থেকে script নামিয়ে সেটা না পড়েই root হিসেবে চালিয়ে দেওয়া। Package manager-এর স্বাক্ষর যাচাইয়ের যে সুবিধা, এতে সেটা পুরোপুরি বাদ পড়ে যায়।

    দরকার হলে আগে curl -fsSL <url> -o setup.sh দিয়ে নামাও, less setup.sh দিয়ে পড়ো, তারপর চালাও।

    যেখানে beginner আটকায়

    apt না apt-get? — হাতে চালানোর জন্য apt, বেশি পরিষ্কার output দেয়। Script-এর ভেতরে apt-get, কারণ তার output-এর গঠন version-এ version-এ বদলায় না।

    "Could not get lock" — আরেকটা apt process চলছে (হয়তো background-এর automatic update)। কয়েক মিনিট অপেক্ষা করো, জোর করে lock file মুছো না।

    npm/pip কি একই জিনিস? — ধারণাটা এক, কিন্তু স্তর আলাদা। apt পুরো system-এর জন্য, npm শুধু তোমার একটা project-এর জন্য। দুটো একে অন্যের সম্পর্কে জানে না।

    Recap
    • Package = program-এর file + metadata + dependency তালিকা।
    • Repository = যাচাই করা, স্বাক্ষরিত package-এর কেন্দ্রীয় ভাণ্ডার।
    • Package manager dependency হিসাব করে, install/remove সামলায়।
    • apt update = catalog নামায়। apt upgrade = আসল software update করে।
    • remove config রাখে, purge রাখে না।
    • Repository-র বাইরে থেকে root হিসেবে script চালানো ঝুঁকিপূর্ণ।
    Chapter 11userland

    Services এবং System Processes

    তোমার terminal বন্ধ থাকলেও server চলে কীভাবে? কে তাকে boot-এর সময় চালু করে, আর crash করলে কে আবার তুলে দেয়?

    Service আর daemon

    Daemon হলো এমন একটা process যেটা পেছনে চলতে থাকে, কোনো terminal-এর সাথে যুক্ত না, আর সাধারণত কোনো একটা request-এর অপেক্ষায় থাকে। Nginx, PostgreSQL, sshd — সবাই daemon। নামের শেষে d থাকাটা তাই একটা পুরনো convention: sshd, systemd, dockerd।

    Service শব্দটা একটু বড় ধারণা — একটা daemon, তাকে কীভাবে চালু করতে হবে, কখন চালু করতে হবে, কার হয়ে চলবে, crash করলে কী করতে হবে — সবটা মিলিয়ে।

    মনে করো Chapter 7-এর process tree। তোমার চালানো node server.js-এর parent তোমার shell। Shell মরলে সে-ও মরে। কিন্তু daemon-এর parent হলো PID 1 — যে কখনো মরে না। এটাই মূল কাঠামোগত পার্থক্য।

    তোমার চালানো server:          Service হিসেবে চালানো server:

systemd (1)                    systemd (1)
└── sshd                       ├── sshd
    └── bash        ← বন্ধ      └── myapp.service
        └── node    ← মরে গেল       └── node   ← বেঁচে থাকে

    systemd কী

    systemd হলো আধুনিক Ubuntu-র init system — kernel boot শেষ করে সবার প্রথম যাকে চালু করে। তার PID 1, আর বাকি সব process তার বংশধর।

    systemd যা করে:

    • Boot-এর সময় ঠিক ক্রমে service গুলো চালু করা (যেমন network আগে, তারপর যে service network লাগে)
    • Crash করলে আবার চালু করা
    • প্রতিটা service কোন user হিসেবে চলবে সেটা নিয়ন্ত্রণ করা
    • সব service-এর log এক জায়গায় জমা করা
    • Service বন্ধ করার সময় তার সব child সহ পরিষ্কার করা

    প্রতিটা service-এর একটা text config file থাকে, নাম শেষ হয় .service দিয়ে। System-এরগুলো /lib/systemd/system/-এ, তোমার নিজেরগুলো /etc/systemd/system/-এ। মনে আছে /etc মানে config? এখানেও সেই নিয়ম।

    systemctl — service নিয়ন্ত্রণ করা

    bash
    $ systemctl status nginx        # এখন কী অবস্থা
$ sudo systemctl start nginx    # এখনই চালু করো
$ sudo systemctl stop nginx     # এখনই বন্ধ করো
$ sudo systemctl restart nginx  # বন্ধ করে আবার চালু
$ sudo systemctl reload nginx   # না থামিয়ে শুধু config নতুন করে পড়ো

$ sudo systemctl enable nginx   # boot-এ চালু হবে
$ sudo systemctl disable nginx  # boot-এ চালু হবে না

$ systemctl list-units --type=service --state=running
    start আর enable সম্পূর্ণ আলাদা

    start = এখন চালু করো। Reboot করলে আর চালু হবে না।

    enable = ভবিষ্যতে boot-এর সময় চালু হবে। কিন্তু এখনই চালু হয় না।

    দুটোই চাইলে: sudo systemctl enable --now nginx। "Server reboot করার পর আমার app আর উঠলো না" — এই সমস্যার উত্তর প্রায় সবসময় এখানে।

    restart আর reload-এর পার্থক্যটাও কাজে লাগে: reload process টা মারে না, শুধু নতুন config পড়তে বলে — তাই চলমান connection গুলো কাটে না। Production-এ nginx config বদলালে reload-ই ব্যবহার করা হয়।

    Log

    Linux-এ log দুই জায়গায় পাওয়া যায়:

    1. journalctl — systemd-র নিজের জমানো log। যেসব service systemd চালায়, তাদের stdout/stderr এখানে চলে আসে।
    2. /var/log/ — অনেক software নিজেই নিজের log file লেখে। যেমন /var/log/nginx/access.log।
    bash
    $ journalctl -u nginx           # শুধু nginx-এর log
$ journalctl -u nginx -n 50     # শেষ ৫০ লাইন
$ journalctl -u nginx -f        # live দেখতে থাকো (Ctrl+C দিয়ে বের হও)
$ journalctl --since "10 min ago"
$ journalctl -p err -b          # এই boot-এর error গুলো

$ tail -f /var/log/syslog       # সাধারণ file হলে tail -f

    লক্ষ্য করো -u nginx-এর -f আর tail -f একই কাজ করে — নতুন লাইন এলে দেখাতে থাকা। Debug করার সময় একটা terminal-এ -f চালু রেখে আরেকটা terminal থেকে request পাঠানো একটা খুব সাধারণ কাজের ধরন।

    Hands-on

    একটা সত্যিকারের service নিয়ে খেলো

    bash
    $ systemctl status ssh          # বা: systemctl status cron
# দেখো: active/inactive, PID, কোন user, কতক্ষণ চলছে

$ systemctl list-units --type=service --state=running | head -20

$ systemctl cat cron            # service file-টা পড়ো

$ journalctl -u cron -n 20 --no-pager

$ ps -ef | head -3              # PID 1 কে দেখো

    systemctl status-এর output-এ যে PID দেখাচ্ছে, সেটা ps aux-এও খুঁজে পাবে। মানে service কোনো জাদু না — এটাও একটা সাধারণ process, শুধু systemd তাকে জন্ম দিয়েছে আর দেখাশোনা করছে।

    systemctl cat cron দিয়ে service file-টা পড়ো — ExecStart লাইনে ঠিক কোন command চলছে সেটা দেখতে পাবে। এটা একদম সাধারণ একটা command line, আর কিছু না।

    যেখানে beginner আটকায়

    "status বলছে active কিন্তু website খুলছে না" — active মানে process চলছে, কিন্তু সে ঠিক কাজ করছে কি না তার নিশ্চয়তা না। Log দেখো, port দেখো (ss -tlnp)।

    "config বদলালাম, কিন্তু কিছু হলো না" — Service config নতুন করে পড়ে না নিজে নিজে। reload বা restart দিতে হবে। আর .service file নিজেই বদলালে আগে sudo systemctl daemon-reload।

    "WSL-এ systemctl কাজ করছে না" — পুরনো WSL setup-এ systemd default-এ চালু থাকে না। এটা তোমার ভুল না।

    Recap
    • Daemon = terminal-বিহীন, পেছনে চলতে থাকা process।
    • Service = daemon + কীভাবে/কখন চালাতে হবে তার নিয়ম।
    • systemd = PID 1, সব process-এর পূর্বপুরুষ, service-এর ব্যবস্থাপক।
    • start এখন, enable boot-এ — দুটো আলাদা।
    • reload না থামিয়ে config পড়ায়, restart থামিয়ে আবার চালায়।
    • Log: systemd-র জন্য journalctl, file-এর জন্য /var/log আর tail -f।

    Basic Networking Concepts

    এই chapter networking-এর গভীরে যাবে না। লক্ষ্য শুধু এটুকু — localhost:3000 লিখলে ঠিক কী ঘটে, সেটা যেন আর রহস্য না থাকে।

    Network কী

    দুটো computer একে অন্যকে data পাঠাতে পারলেই সেটা একটা network। এতে দরকার তিনটা জিনিস: কাকে পাঠাবো তার একটা ঠিকানা, ঐ machine-এর ঠিক কোন program-কে পাঠাবো তার একটা নম্বর, আর data কীভাবে যাবে তার একটা নিয়ম।

    এই তিনটাই হলো IP address, port, আর protocol।

    IP address — machine-এর ঠিকানা

    IP address একটা network-এ একটা machine-কে চিহ্নিত করে। IPv4-এ এটা চারটা সংখ্যা: 192.168.0.105।

    • Public IP — ইন্টারনেটে যেটা দিয়ে তোমাকে চেনা যায়। তোমার AWS server-এর যেটা আছে।
    • Private IP — শুধু local network-এর ভেতরে অর্থবহ। 192.168.x.x, 10.x.x.x — তোমার বাসার router এগুলো দেয়।

    localhost আর 127.0.0.1

    127.0.0.1 একটা বিশেষ IP — এর মানে "এই machine টাই"। এই ঠিকানায় পাঠানো data কোনো network card-এ যায়ই না, physical কোনো তার স্পর্শ করে না। Kernel সরাসরি ভেতরে ভেতরে ঘুরিয়ে দেয়, একটা কাল্পনিক interface-এর মধ্য দিয়ে যার নাম lo (loopback)।

    localhost হলো এই IP-র জন্য একটা নাম, আর সেই mapping টা লেখা আছে /etc/hosts file-এ। মানে এটা DNS-এর ব্যাপারই না — একটা local text file।

    তোমার browser → http://localhost:3000
        │
        │  /etc/hosts দেখে: localhost = 127.0.0.1
        ▼
   ┌─────────────────────────┐
   │  lo interface (kernel)  │  ← কোনো তার নেই, কোনো NIC নেই
   └─────────────────────────┘
        │
        ▼
   port 3000 এ শুনতে থাকা process (তোমার Next.js dev server)
    এই তথ্যটা Docker-এ গিয়ে খুব কাজে দেয়

    Container-এর ভেতরে localhost মানে ঐ container টাই, তোমার laptop না। এই কারণেই container থেকে localhost:5432-এ database খুঁজতে গেলে পাওয়া যায় না। "এই machine টাই" — এখানে "এই machine" কে, সেটাই আসল প্রশ্ন।

    Port — কোন program

    একটা machine-এ অনেক program একসাথে network ব্যবহার করে। IP address বলে কোন machine, আর port বলে ঐ machine-এর কোন program।

    Port একটা সংখ্যা, 1 থেকে 65535। যখন একটা program কোনো port-এ "শুনতে" শুরু করে (listening), kernel তখন থেকে ঐ port-এ আসা সব data ঐ program-কে দেয়।

    Portসাধারণত
    22SSH
    80HTTP
    443HTTPS
    5432PostgreSQL
    3000 / 5173 / 8080Development server

    1024-এর নিচের port গুলো ব্যবহার করতে root ক্ষমতা লাগে — এটা একটা পুরনো নিরাপত্তা নিয়ম, যাতে যে কেউ port 80-এ বসে ওয়েবসাইট সেজে বসতে না পারে। এই কারণেই dev server গুলো 3000, 5173 এসব ব্যবহার করে, আর production-এ nginx (যাকে root চালু করে) 80/443-এ বসে।

    Analogy

    IP address হলো একটা অ্যাপার্টমেন্ট building-এর ঠিকানা। Port হলো ফ্ল্যাট নম্বর। ঠিকানা ছাড়া চিঠি building-এ পৌঁছাবে না, আর ফ্ল্যাট নম্বর ছাড়া সেটা কার কাছে যাবে বোঝা যাবে না।

    TCP আর UDP

    Data পাঠানোর দুটো প্রধান নিয়ম।

    TCPUDP
    Connectionআগে connection তৈরি করেকোনো connection নেই, সরাসরি পাঠায়
    নিশ্চয়তাপৌঁছেছে কিনা যাচাই করে, না পৌঁছালে আবার পাঠায়কোনো যাচাই নেই, হারিয়ে গেলে গেল
    ক্রমযে ক্রমে পাঠানো, সেই ক্রমেই পৌঁছায়ক্রম এলোমেলো হতে পারে
    গতিতুলনামূলক ধীরদ্রুত, কম overhead
    কোথায়HTTP, SSH, databaseDNS, video call, game

    ভাবার সহজ উপায়: TCP হলো registered ডাক — প্রাপ্তি স্বীকার লাগে। UDP হলো সাধারণ পোস্টকার্ড — ছুঁড়ে দিলাম, পৌঁছালে ভালো।

    ভিডিও কল-এ UDP কেন? কারণ ০.৫ সেকেন্ড আগের একটা হারানো frame আবার পাঠিয়ে লাভ নেই — ততক্ষণে সেটা অপ্রাসঙ্গিক। কিন্তু database-এর একটা byte হারিয়ে গেলে সর্বনাশ, তাই TCP।

    DNS

    মানুষ github.com মনে রাখে, computer-এর দরকার 140.82.121.4। DNS (Domain Name System) এই অনুবাদটা করে।

    github.com লিখলে:

1. /etc/hosts এ আছে?          → না
2. আগের ফলাফল cache-এ আছে?     → না
3. DNS server কে জিজ্ঞেস করা    → 140.82.121.4
4. এখন সেই IP-র port 443 এ TCP connection

কোন DNS server? → /etc/resolv.conf এ লেখা আছে

    এই কারণেই "কাজ করছিল, হঠাৎ কাজ করছে না" ধরনের সমস্যায় সবাই বলে "DNS হতে পারে" — ধাপটা একদম শুরুতে, আর এটা ভাঙলে বাকি সব ভেঙে পড়ে।

    HTTP আর HTTPS

    এখন পর্যন্ত যা বললাম তাতে data পৌঁছাতে পারে, কিন্তু সেই data-র মানে কী তা কেউ জানে না। HTTP হলো সেই নিয়ম যা বলে দেয় একটা request দেখতে কেমন হবে আর response দেখতে কেমন হবে।

    HTTP চলে TCP-র উপরে। HTTPS হলো HTTP, কিন্তু মাঝখানে TLS নামে একটা encryption স্তর যোগ করা — তাই মাঝপথে কেউ পড়তে পারে না।

    ┌──────────────────────────┐
│   HTTP     (কী বলছি)      │
├──────────────────────────┤
│   TLS      (গোপন রাখা)    │  ← HTTPS হলে এই স্তরটা থাকে
├──────────────────────────┤
│   TCP      (নিশ্চিত পৌঁছানো) │
├──────────────────────────┤
│   IP       (কোন machine)  │
└──────────────────────────┘

    কাজের command গুলো

    bash
    # ping — ঐ machine পর্যন্ত পৌঁছানো যায় কি না
$ ping -c 3 8.8.8.8          # IP দিয়ে
$ ping -c 3 github.com       # নাম দিয়ে (DNS-ও যাচাই হয়ে যায়)

# ss — কোন port এ কে শুনছে
$ ss -tlnp                   # t=TCP l=listening n=number p=process
$ ss -tlnp | grep 3000

# curl — HTTP request পাঠানো
$ curl https://api.github.com
$ curl -I https://github.com          # শুধু header
$ curl -s http://localhost:3000 | head

# নিজের IP
$ ip addr                             # macOS এ: ifconfig
    সমস্যা খোঁজার একটা কাজে দেওয়া ক্রম

    "আমার API কাজ করছে না" — নিচ থেকে উপরে উঠো, প্রতিটা স্তর আলাদা করে যাচাই করো:

    1. ping ঠিকানা → machine পর্যন্ত পৌঁছানো যাচ্ছে? DNS ঠিক আছে?
    2. ss -tlnp | grep PORT → আদৌ কিছু কি ঐ port-এ শুনছে?
    3. curl -I http://... → HTTP স্তরে সাড়া দিচ্ছে?
    4. journalctl -u service -n 50 → program নিজে কী বলছে?

    এলোমেলোভাবে চেষ্টা না করে এই ক্রমে গেলে প্রতিটা ধাপে একটা করে সম্ভাবনা বাদ যায়।

    Hands-on

    নিজের machine-এ পুরো stack টা দেখো

    bash
    $ cat /etc/hosts             # localhost এর mapping
$ ping -c 2 localhost        # 127.0.0.1, সময় প্রায় ০
$ ping -c 2 8.8.8.8          # অনেক বেশি সময়

$ ss -tlnp                   # এখন কী কী শুনছে

# একটা server চালু করে দেখো (Ctrl+C দিয়ে বন্ধ)
$ python3 -m http.server 8080 &
$ ss -tlnp | grep 8080       # এখন দেখা যাচ্ছে
$ curl -s http://localhost:8080 | head -5
$ kill %1

    localhost-এ ping-এর সময় প্রায় শূন্য কারণ data কোনো তার দিয়ে যাচ্ছেই না — kernel ভেতরেই ঘুরিয়ে দিচ্ছে। 8.8.8.8-এ যেতে অনেক গুণ বেশি সময় লাগছে কারণ সেটা সত্যিই পৃথিবীর অন্য প্রান্তে ঘুরে আসছে।

    আর ss -tlnp-এর output-এ port-এর পাশে PID দেখো — মানে একটা port আসলে একটা process-এর সাথে যুক্ত। "Port already in use" error-এর মানে হলো ঐ port-এ আরেকটা process আগে থেকে বসে আছে; PID বের করে kill করলেই মুক্তি।

    যেখানে beginner আটকায়

    "server চলছে কিন্তু বাইরে থেকে খুলছে না" — সম্ভবত সেটা 127.0.0.1-এ bind করা, 0.0.0.0-এ না। 127.0.0.1 মানে শুধু নিজের ভেতর থেকে আসা connection নেব। ss -tlnp-এর output-এ দেখো address কী দেখাচ্ছে।

    "ping কাজ করছে কিন্তু website খুলছে না" — স্বাভাবিক। ping শুধু machine পর্যন্ত পৌঁছানো যাচাই করে, ঐ machine-এর কোনো program port-এ শুনছে কি না তার সাথে এর সম্পর্ক নেই।

    Recap
    • IP = machine-এর ঠিকানা, port = ঐ machine-এর কোন program।
    • 127.0.0.1 = "এই machine"; data কোনো তার ছোঁয় না।
    • localhost-এর mapping /etc/hosts-এ, DNS-এ না।
    • TCP নিশ্চিত ও ক্রমানুসারে; UDP দ্রুত কিন্তু নিশ্চয়তাহীন।
    • DNS নামকে IP-তে অনুবাদ করে; HTTP চলে TCP-র উপরে, HTTPS = HTTP + TLS।
    • ping পৌঁছানো, ss -tlnp কে শুনছে, curl HTTP স্তর।

    SSH এবং Remote Linux

    এতক্ষণ যা শিখেছো, তার প্রায় সবটাই আসলে remote server-এ কাজে লাগবে। SSH হলো সেখানে পৌঁছানোর দরজা।

    Remote machine মানে কী

    Remote machine বলতে বোঝায় অন্য কোথাও চলতে থাকা একটা computer — AWS-এর EC2, DigitalOcean-এর droplet, অফিসের একটা server। তার কোনো মনিটর নেই, keyboard নেই। শুধু network দিয়ে তার কাছে পৌঁছানো যায়।

    Chapter 1-এ বলেছিলাম Linux পুরোপুরি text দিয়ে চালানো যায় — এখানেই সেই কথাটার আসল মূল্য। GUI না থাকলেও কিছু আটকায় না।

    SSH কী

    SSH (Secure Shell) হলো একটা protocol, যেটা দিয়ে network-এর মধ্য দিয়ে নিরাপদে অন্য machine-এ shell চালানো যায়। "Secure" অংশটা গুরুত্বপূর্ণ — সব কিছু encrypted, তাই মাঝপথে কেউ তোমার command বা password পড়তে পারে না।

    এটা client-server model-এ চলে:

    তোমার laptop                      Server
┌──────────────┐                 ┌────────────────────┐
│ ssh (client) │ ══════════════► │ sshd (daemon)      │ port 22
└──────────────┘   encrypted     │        │           │
                                 │        ▼           │
                                 │  তোমার জন্য একটা    │
                                 │  bash process      │
                                 └────────────────────┘

    Server-এ sshd নামে একটা daemon চলে (মনে আছে Chapter 11? শেষে d), যেটা port 22-এ শোনে। তুমি connect করলে সে যাচাই করে, তারপর তোমার জন্য একটা shell process চালু করে দেয়। তোমার terminal-এ যা টাইপ করো, সেটা encrypted হয়ে ঐ shell-এ যায়, আর output ফিরে আসে।

    মূল কথা

    SSH দিয়ে ঢোকার পর তুমি যা দেখছো, সেটা তোমার terminal window-তে চলতে থাকা server-এর shell। Chapter 2-এর সেই terminal/shell পার্থক্যটা এখানে চোখে ধরা পড়ে — terminal তোমার laptop-এ, shell অন্য মহাদেশে।

    Connect করা

    bash
    $ ssh mostofa@192.168.0.50
$ ssh mostofa@myserver.com
$ ssh -p 2222 mostofa@myserver.com    # অন্য port হলে
$ exit                                # বের হওয়া (Ctrl+D ও কাজ করে)

    প্রথমবার connect করলে একটা fingerprint দেখিয়ে জিজ্ঞেস করবে "এই server-কে চেনো?"। yes বললে সেটা ~/.ssh/known_hosts-এ জমা থাকে। পরের বার fingerprint না মিললে SSH জোরালো সতর্কবার্তা দেবে — এটা তোমাকে বাঁচানোর জন্য, কেউ মাঝখানে বসে server সেজে থাকতে পারে।

    SSH key — password-এর চেয়ে ভালো

    Password দিয়েও ঢোকা যায়, কিন্তু key দিয়ে ঢোকাই স্বাভাবিক নিয়ম। কারণ password অনুমান করা যায়, brute-force করা যায়। Key যায় না।

    Key জোড়ায় জোড়ায় আসে:

    • Private key (~/.ssh/id_ed25519) — কখনো কাউকে দেবে না, কোথাও upload করবে না।
    • Public key (~/.ssh/id_ed25519.pub) — সবাইকে দেওয়া যায়। এটাই server-এ বসাতে হয়।

    Server তোমার public key দিয়ে একটা ধাঁধা তৈরি করে পাঠায়, যেটার উত্তর একমাত্র private key দিয়েই দেওয়া সম্ভব। মজার ব্যাপার হলো — private key কখনো network-এ যায় না। তাই মাঝপথে কেউ শুনলেও কিছু পায় না।

    bash
    $ ssh-keygen -t ed25519 -C "mostofa@laptop"
# Enter চেপে default path নাও; একটা passphrase দেওয়া ভালো

$ ls -l ~/.ssh/
$ cat ~/.ssh/id_ed25519.pub      # এটা শেয়ার করা নিরাপদ

$ ssh-copy-id mostofa@myserver.com   # public key টা server-এ বসিয়ে দেয়
$ ssh mostofa@myserver.com           # এখন আর password লাগবে না
    Private key নিয়ে নিয়ম

    Private key কখনো git-এ commit করবে না, Slack-এ পাঠাবে না, screenshot-এ দেখাবে না। যার কাছে তোমার private key, সে-ই তুমি।

    SSH permission নিয়ে খুব কড়া — permission ঢিলা হলে সে key ব্যবহার করতেই অস্বীকার করবে। এটা Chapter 6-এর সরাসরি প্রয়োগ:

    bash
    $ chmod 700 ~/.ssh
$ chmod 600 ~/.ssh/id_ed25519
$ chmod 644 ~/.ssh/id_ed25519.pub

    700 মানে ঐ directory-তে আর কেউ ঢুকতেই পারবে না, 600 মানে private key শুধু তুমি পড়তে পারবে। GitHub-এ SSH setup করার সময় এই একই key ব্যবস্থা ব্যবহার হয়।

    Local vs remote — গুলিয়ে ফেলা সহজ

    SSH-এ ঢোকার পর terminal দেখতে প্রায় একই রকম, কিন্তু এখন প্রতিটা command অন্য একটা machine-এ চলছে। এখানে একটা ভুল খুব ব্যয়বহুল হতে পারে — ভুল window-তে rm -rf চালানো।

    অভ্যাস করে ফেলো

    কিছু বিপজ্জনক চালানোর আগে hostname বা whoami দিয়ে যাচাই করে নাও তুমি কোথায় আছো। Prompt-এর ভেতরেও এটা লেখা থাকে — mostofa@prod-server:~$। ঐ মাঝের নামটা এক সেকেন্ড পড়ে নেওয়ার অভ্যাসটা মূল্যবান।

    bash
    $ hostname
$ whoami

# file পাঠানো / আনা (দুটোই local terminal থেকে চালাও)
$ scp app.tar.gz mostofa@server:/home/mostofa/
$ scp mostofa@server:/var/log/app.log ./

# SSH না ঢুকে সরাসরি একটা command চালানো
$ ssh mostofa@server "df -h"

    শেষেরটা কাজে লাগে — SSH-এ ঢুকে বসে থাকার দরকার নেই, শুধু একটা command চালিয়ে output নিয়ে বেরিয়ে আসা যায়। CI/CD pipeline-এ deploy ঠিক এভাবেই হয়।

    Hands-on

    Server না থাকলে নিজের machine-এই করো

    bash
    $ ssh-keygen -t ed25519 -f ~/.ssh/test_key -N ""
$ ls -l ~/.ssh/test_key*
# দুটো file: private টা 600, public টা 644 — নিজেই set হয়েছে

$ cat ~/.ssh/test_key.pub
# এক লাইন: টাইপ, key, comment

$ systemctl status ssh 2>/dev/null | head -5
$ ss -tlnp | grep :22        # sshd শুনছে কি না

$ ssh localhost              # sshd চললে নিজের machine-এই ঢুকতে পারবে
$ rm ~/.ssh/test_key*

    ssh localhost কাজ করলে খেয়াল করো — একটা নতুন shell চালু হলো, prompt বদলালো। exit দিলে আবার আগের shell-এ ফিরে এলে। এটা Chapter 7-এর process tree-র একটা জীবন্ত উদাহরণ: bash → ssh → sshd → নতুন bash।

    যেখানে beginner আটকায়

    "Permission denied (publickey)" — server password গ্রহণ করছে না, আর তোমার key-ও সে চেনে না। Key টা ঠিকমতো ssh-copy-id করা হয়েছে কি না দেখো।

    "REMOTE HOST IDENTIFICATION HAS CHANGED" — server-এর fingerprint বদলে গেছে। Server নতুন করে বানানো হলে এটা স্বাভাবিক, কিন্তু না হলে এটা সত্যিকারের সতর্কবার্তা। কারণ না জেনে known_hosts-এর লাইন মুছে দিও না।

    "Connection refused" আর "Connection timed out" এক না" — refused মানে পৌঁছেছে কিন্তু ঐ port-এ কেউ শুনছে না। timeout মানে পৌঁছাতেই পারেনি — সাধারণত firewall বা ভুল ঠিকানা।

    Recap
    • SSH = network-এর মধ্য দিয়ে নিরাপদে remote shell চালানোর protocol।
    • Client ssh, server-এ daemon sshd, port 22।
    • Key জোড়ায় আসে: private কখনো শেয়ার না, public server-এ বসে।
    • Private key কখনো network-এ যায় না।
    • ~/.ssh 700, private key 600 — নাহলে SSH কাজ করবে না।
    • বিপজ্জনক command-এর আগে hostname দিয়ে যাচাই করো।
