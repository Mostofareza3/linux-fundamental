    Linux Simulators

    বইয়ের যে জায়গাগুলোতে পড়ে বোঝা কঠিন — permission-এর অঙ্ক, fork/exec, pipe-এ data কোন পথে যায়, PATH কীভাবে খোঁজে, path কীভাবে resolve হয় — সেগুলো এখানে নিজের হাতে নেড়েচেড়ে দেখা যায়। কোনো কিছু install করতে হবে না, কোনো ভুল করলে কিছু ভাঙবে না।

    কেন এই সিমুলেটরগুলো

    পড়ে বোঝা আর করে বোঝা এক জিনিস না। chmod 750 কেন rwxr-x--- — এটা টেবিল দেখে মুখস্থ করা যায়, কিন্তু যেই মুহূর্তে তুমি নিজে switch টিপে দেখবে সংখ্যাটা বদলাচ্ছে, ঐ মুহূর্তেই জিনিসটা মাথায় বসে যায়।

    প্রতিটা সিমুলেটরের সাথে বইয়ের chapter-এর reference দেওয়া আছে। আটকে গেলে আগে chapter টা পড়ে নিও, তারপর ফিরে এসে হাত চালিও।

    ব্যবহারের নিয়ম

    প্রতিটা সিমুলেটরের শেষে একটা ছোট প্রশ্ন আছে। উত্তর দেওয়ার আগে নিজে থেকে অনুমান করো — কী হবে বলে মনে হচ্ছে? তারপর সিমুলেটরে চালিয়ে মিলিয়ে দেখো। ভুল অনুমান থেকেই আসল শেখাটা হয়।

    সংখ্যাটা আসে কোথা থেকে

    প্রতিটা অক্ষরের একটা মান আছে — r=4, w=2, x=1। একটা শ্রেণির (owner/group/others) জন্য যেগুলো on, সেগুলো যোগ করলেই ঐ শ্রেণির অঙ্ক। উপরের switch গুলো নাড়ালে যোগফলটা কীভাবে বদলায় লক্ষ্য করো।

    rwx = 4+2+1 = 7      r-x = 4+0+1 = 5
rw- = 4+2+0 = 6      r-- = 4+0+0 = 4
--- = 0+0+0 = 0      -wx = 0+2+1 = 3
    Directory-তে অক্ষরগুলোর মানে আলাদা

    উপরের dropdown থেকে Directory বেছে নাও — দেখবে একই rwx-এর ব্যাখ্যা বদলে গেছে। Directory-তে x মানে চালানো না, ভেতরে ঢোকা (cd)। আর r মানে content পড়া না, নামের তালিকা দেখা।

    এই কারণেই r-- directory-তে ls চলে কিন্তু ভেতরের কোনো file খোলা যায় না, আর --x directory-তে নাম জানা থাকলে file খোলা যায় কিন্তু ls চলে না।

    নিজেকে যাচাই করো
    একটা file-এর permission r--r--r-- — কেউ লিখতে পারবে না। কিন্তু file টা যে directory-তে আছে, সেখানে তোমার w permission আছে। তুমি কি file টা মুছে ফেলতে পারবে?

    মোছা মানে file-এ লেখা না। মোছা মানে directory-র তালিকা থেকে একটা এন্ট্রি বাদ দেওয়া — আর সেটা directory-তে লেখার কাজ। তাই যাচাই হয় directory-র w, file-এর না।

    এটাই সেই বিখ্যাত বিভ্রান্তি: "আমি তো write permission দিইনি, তাও file মুছে গেল কীভাবে?" — Chapter 4-এর "directory আসলে একটা তালিকা রাখা file" কথাটার সরাসরি ফল।

    Simulator 02chapter 07

    fork() ও exec() — process কীভাবে জন্মায়

    Linux-এ নতুন process বানানোর নিয়মটা প্রথমে অদ্ভুত লাগে: process নতুন কিছু বানায় না, নিজের একটা কপি বানায়, তারপর সেই কপির ভেতরের program টা বদলে দেয়। ধাপে ধাপে চালিয়ে দেখো।

    process tree 
    
      
    
    
    
  
    

  
    দুই ধাপে ভাগ করা কেন
    
  
    "নতুন program চালাও" — এটা এক ধাপে করে দিলেই তো হতো। কিন্তু Unix ইচ্ছে করে দুই ধাপ রেখেছে, কারণ fork() আর exec()-এর মাঝখানের ঐ ফাঁকটাই সবচেয়ে দামি।
    
  
    ঐ ফাঁকে child process এখনো shell-এর কপি, কিন্তু আলাদা process। সে তখন নিজের পরিবেশ সাজিয়ে নিতে পারে — কোন file descriptor কোথায় যাবে, কোন directory-তে থাকবে, কোন user হিসেবে চলবে। তারপর exec() করলে সেই সাজানো পরিবেশ নিয়েই নতুন program চালু হয়।
    
  
    
    
    এখান থেকেই pipe আর redirection
    
    
    ls > out.txt লিখলে shell কী করে? fork করে, তারপর exec করার আগে child-এর fd 1 কে out.txt-এ ঘুরিয়ে দেয়, তারপর exec করে। ls নিজে কিছুই জানে না — সে বরাবরের মতোই fd 1-এ লিখে যায়, শুধু fd 1 এখন অন্য জায়গায় তাক করা। পরের সিমুলেটরে এটা চোখে দেখা যাবে।
    
  
    

  
    
    
    নিজেকে যাচাই করো
    
    
    
      
    fork()-এর পর child process-এর PID কি parent-এর সমান? আর exec()-এর পর PID টা কি বদলে যায়?
    
      
    
        
        
        
      
    
      
    
        
    fork() একটা নতুন process বানায় — তাই নতুন PID। কিন্তু exec() নতুন process বানায় না, একই process-এর ভেতরের program টা পাল্টে দেয় — খোলসটা একই, ভেতরের জিনিস বদলায়। তাই PID অপরিবর্তিত।
    
        
    উপরের সিমুলেটরে দেখো: PID 2856 fork-এ জন্মালো, exec-এর পর নাম bash থেকে ls হয়ে গেল, কিন্তু 2856-ই রয়ে গেল।
    
      
    
    
    
  
    

    



    
  
    
    
    Simulator 03chapter 09
    
    
    Pipe ও Redirection — data কোন পথে যায়
    
    
    প্রতিটা process তিনটা চ্যানেল নিয়ে জন্মায় — 0 stdin, 1 stdout, 2 stderr। Pipe আর redirection নতুন কিছু আবিষ্কার করে না, শুধু এই তিনটার মুখ ঘুরিয়ে দেয়। নিচে command বেছে নিয়ে চালাও — কোন তীর কোথায় যাচ্ছে দেখো।

    Pipe আসলে কী
    
  
    Pipe কোনো file না, disk-এ কিছু লেখা হয় না। এটা kernel-এর memory-তে থাকা একটা ছোট buffer — একদিক দিয়ে ঢোকে, অন্যদিক দিয়ে বেরোয়। বাঁ পাশের process-এর fd 1 আর ডান পাশের process-এর fd 0 ঐ buffer-টার দুই মুখে বাঁধা থাকে।
    
  
    আরো গুরুত্বপূর্ণ — pipeline-এর সব process একসাথে চলে, একের পর এক না। বাঁ দিকেরটা লিখতে থাকে, ডান দিকেরটা সাথে সাথে পড়তে থাকে। তাই cat huge.log | head -5 পুরো file পড়ে না; head-এর ৫ লাইন হয়ে গেলে সে বন্ধ হয়ে যায়, আর cat-ও তখন থেমে যায়।
    

  
    
    
    যে ফাঁদে সবাই একবার পড়ে
    
    
    | শুধু stdout (fd 1) নিয়ে যায়, stderr (fd 2) নেয় না। তাই make | grep error চালালে error গুলোই বাদ পড়ে যায় — কারণ সেগুলো fd 2 দিয়ে সরাসরি terminal-এ যাচ্ছে, pipe-এ ঢুকছেই না।
    
      
    উপরের list থেকে 2>&1 ওয়ালা উদাহরণটা চালিয়ে দেখো — ঐ লেখাটার মানে "fd 2-কে ঠিক সেখানে পাঠাও যেখানে fd 1 এখন তাক করা আছে"।
    
  
    

  
    
    
    নিজেকে যাচাই করো
    
    
    
      
    command > out.txt 2>&1 আর command 2>&1 > out.txt — এই দুটো কি একই কাজ করে?
    
      
    
        
        
        
      
    
      
    
        
    Shell বাঁ থেকে ডানে এক এক করে করে। প্রথমটায়: আগে fd 1 → file, তারপর fd 2 → "fd 1 যেখানে আছে" মানে file। দুটোই file-এ।
    
        
    দ্বিতীয়টায়: আগে fd 2 → "fd 1 যেখানে আছে" — তখন fd 1 এখনো terminal-এ। তারপর fd 1 → file। ফল: stdout file-এ, stderr terminal-এই রয়ে গেল। 2>&1 একটা copy, কোনো স্থায়ী বাঁধন না — এই একটা কথা মনে রাখলেই ফাঁদটা এড়ানো যায়।
    
      
    
    
    
  
    

    



    
  
    
    
    Simulator 04chapter 08
    
    
    PATH — shell command টা খুঁজে পায় কীভাবে
    
    
    তুমি লিখলে node। Shell কোথা থেকে জানলো সেটা কোন file? সে PATH-এর directory গুলোতে বাঁ থেকে ডানে এক এক করে খোঁজে, আর প্রথম যেটা পায় সেটাই চালায় — বাকিগুলো আর দেখেই না। এই একটা নিয়ম "command not found" আর "ভুল version চলছে" — দুটো রহস্যেরই উত্তর।

    দুটো জিনিস আলাদা করে দেখো
    
  
    উপরে node আর ./myscript.sh — দুটোই চালিয়ে দেখো। পার্থক্যটা মৌলিক:
    
  
      
    
    • নামের ভেতরে / নেই (node) → shell এটাকে "খুঁজে বের করার নাম" ধরে, PATH-এ খোঁজে।
      • 
    
    • নামের ভেতরে / আছে (./myscript.sh, /usr/bin/node) → shell এটাকে সরাসরি path ধরে, PATH-এ খোঁজেই না।
      • 
  
    
  
    
    
    "একই folder-এ script আছে, তবু ./ লিখতে হয় কেন"
    
    
    কারণ Linux-এ current directory (.) PATH-এ থাকে না — ইচ্ছে করেই রাখা হয় না। থাকলে কেউ /tmp-তে ls নামের একটা ক্ষতিকর script রেখে দিলে, তুমি /tmp-তে গিয়ে ls লিখলেই সেটা চলে যেত। তাই নিজের folder-এর script চালাতে হলে স্পষ্ট করে ./ লিখে বলে দিতে হয় — "এইটা, এখান থেকে"।
    
  
    

  
    
    
    নিজেকে যাচাই করো
    
    
    
      
    node --version দেখাচ্ছে v16, কিন্তু তুমি নিশ্চিত v20 install করেছো এবং সেটা /home/mostofa/.nvm/versions/node/v20/bin-এ আছে, যা PATH-এও আছে। সমস্যাটা কী?
    
      
    
        
        
        
      
    
      
    
        
    PATH-এ খোঁজা হয় বাঁ থেকে ডানে, আর প্রথম মিল পেলেই থেমে যায়। দুটো version-ই PATH-এ থাকতে পারে — যেটার directory আগে, সেটাই জিতবে।
    
        
    নিশ্চিত হওয়ার উপায়: which -a node — সবগুলো মিল ক্রম অনুযায়ী দেখাবে। ঠিক করার উপায় নতুন করে install করা না, বরং PATH-এ ক্রমটা ঠিক করা।

    Absolute ও Relative Path
    
    
    একই জায়গায় পৌঁছানোর অনেক রাস্তা আছে। / দিয়ে শুরু হলে সেটা absolute — কোথায় দাঁড়িয়ে আছো তাতে কিছু যায় আসে না। নাহলে সেটা relative — তোমার বর্তমান অবস্থান থেকে হিসাব হয়। cd চালিয়ে গাছে হেঁটে দেখো, প্রতিটা ধাপ কীভাবে resolve হচ্ছে ডান পাশে দেখা যাবে।

    Script-এ relative path লিখলে সেটা script-এর নিজের অবস্থান থেকে না, বরং যে directory থেকে script টা চালানো হয়েছে সেখান থেকে হিসাব হয়। তাই cd ~ && ./project/run.sh চালালে script-এর ভেতরের ./config.json খুঁজবে ~/config.json-এ, ~/project/config.json-এ না। Cron job-এর script হঠাৎ কাজ না করার সবচেয়ে সাধারণ কারণ এটাই।
    
  
    

  
    
    
    নিজেকে যাচাই করো
    
    
    
      
    তুমি আছো /home/mostofa/projects/app-এ। cd ../../notes চালালে কোথায় পৌঁছাবে?
    
      
    
        
        
        
      
    
      
    
        
    প্রতিটা .. এক ধাপ উপরে তোলে। app → projects → mostofa। এবার সেখান থেকে notes — মানে /home/mostofa/notes।
    
        
    উপরের সিমুলেটরে projects/app-এ গিয়ে ../../notes চালাও — ডান পাশে প্রতিটা ধাপ আলাদা করে দেখা যাবে।
