Mastering Linux File Permissions

প্রতিটা file-এর গায়ে ছোট্ট একটা লেবেল সাঁটা থাকে — কে এর মালিক, কোন group-এর, আর কে কী করতে পারবে। এই lab-এ তিনটে হাতিয়ার শিখবে: umask ঠিক করে নতুন file কী নিয়ে জন্মাবে, chmod বদলায় যা আগে থেকেই আছে, আর setfacl এমন কিছু পারে যা সাধারণ মডেল দিয়ে কোনোভাবেই হয় না — একই file-এ একাধিক group-কে আলাদা আলাদা অনুমতি দেওয়া।

এই lab শেষে যা পারবে

  • rwxr-xr---এর মতো permission string দেখেই পড়ে ফেলবে।
  • umask দিয়ে নতুন file-এর default অনুমতি ঠিক করবে।
  • chmod-এর দুই ধরনের লেখা — octal আর symbolic — দুটোই ব্যবহার করবে।
  • setfacl দিয়ে একই folder-এ তিনটে group-কে তিন রকম অনুমতি দেবে।
  • getfacl দিয়ে যাচাই করবে কার কী অনুমতি আছে।
  • সবচেয়ে গুরুত্বপূর্ণ — বুঝবে Linux কোন ক্রমে অনুমতি পরীক্ষা করে, আর কেন মাঝে মাঝে ফল উল্টো হয়।
আগে যা জানা থাকলে সুবিধা

Lab 02 — User & Group Management আর Lab 05 — User Modification। এখানে group বানানো আর usermod -aG ধরে নেওয়া হয়েছে — Lab 05-এ -a বাদ দেওয়ার যে বিপদটার কথা বলেছিলাম, সেটা এখানে ছয়বার লাগবে।

practice machine-এ করো

এই lab-এ ছয়জন user, তিনটে group আর একটা পুরো directory কাঠামো বানানো হবে। কাজটা নিজের VM, WSL, container বা ফেলে দেওয়া যায় এমন VPS-এ করো। শেষে পরিষ্কার করার ধাপ দেওয়া আছে।

Permission string পড়া

ls -l দিলে প্রতিটা লাইনের শুরুতে ১০টা অক্ষরের একটা string থাকে। এটাই পুরো permission-এর গল্প:

পুরো ls -l লাইনটার সাথে মিলিয়ে দেখলে ব্যাপারটা আরও পরিষ্কার হয়:

১০টা অক্ষর ভেঙে দেখা
-rwxr-xr--  1  alice  dev  4096  Mar 10 09:00  deploy.sh
│└─┬┘└─┬┘└─┬┘        │     │
│  │   │   │         │     └─ group-এর নাম
│  │   │   │         └─────── মালিকের নাম
│  │   │   └─ others  r--  বাকি সবাই: শুধু পড়তে পারবে
│  │   └───── group   r-x  dev group: পড়তে ও চালাতে পারবে
│  └───────── owner   rwx  alice: সব পারবে
└──────────── ধরন    -    - = সাধারণ file, d = directory, l = link
অক্ষরFile-এর ক্ষেত্রেDirectory-র ক্ষেত্রে
r (read)ভেতরের লেখা পড়া যাবেভেতরে কী কী আছে তার তালিকা দেখা যাবে
w (write)লেখা বদলানো যাবেভেতরে file বানানো বা মোছা যাবে
x (execute)program হিসেবে চালানো যাবেভেতরে ঢোকা যাবে (cd)
Directory-তে x ছাড়া r প্রায় অর্থহীন

এটা এই lab-এর সবচেয়ে দরকারি ধারণাগুলোর একটা। Directory-তে x না থাকলে তুমি ভেতরে ঢুকতেই পারবে না — তাই ভেতরের কোনো file পড়তেও পারবে না, যদিও ঐ file-এ তোমার read অনুমতি আছে।

r আছে, x নেই — যা হয়
$ ls mydir/          → নামগুলো দেখা যায়
main.c  app.conf

$ cat mydir/main.c   → কিন্তু পড়া যায় না!
cat: mydir/main.c: Permission denied

এজন্যই পুরো lab জুড়ে read-only অনুমতি দিতে গিয়ে আমরা r নয়, rx লিখব। "Read-only" মানে directory-র ক্ষেত্রে r-x।

এতক্ষণ যা যা দেখলে — তিনটে দল, তিন ধরনের অনুমতি, আর সেগুলো মিলে তৈরি হওয়া string — সবটা একসাথে এভাবে সাজানো যায়:

Octal সংখ্যাগুলো কোথা থেকে আসে

chmod 750-এর ঐ তিনটে সংখ্যা আসলে তিনটে দলের জন্য তিনটে হিসেব। প্রতিটা অনুমতির একটা নির্দিষ্ট মান আছে:

যোগ করলেই সংখ্যাটা পাওয়া যায়
r = 4        w = 2        x = 1

rwx  =  4+2+1  =  7          r-x  =  4+0+1  =  5
rw-  =  4+2+0  =  6          r--  =  4+0+0  =  4
---  =  0+0+0  =  0

        chmod  7  5  0
               │  │  └─ others : ---  কিছুই না
               │  └──── group  : r-x  পড়া আর ঢোকা
               └─────── owner  : rwx  সব

তিনটে হাতিয়ার — কে কখন কাজ করে

হাতিয়ারকখন কাজ করেকী করে
umaskFile জন্মানোর মুহূর্তেDefault থেকে কিছু অনুমতি কেটে নেয়
chmodবিদ্যমান file-এowner/group/others — এই তিন দলের অনুমতি বদলায়
setfaclবিদ্যমান file-এতিন দলের বাইরে বাড়তি নিয়ম যোগ করে

এক কথায় — umask হলো কারখানার setting, chmod হলো হাতে করা সমন্বয়, আর setfacl হলো সেই সূক্ষ্ম কাজ যেটা সাধারণ মডেল দিয়ে হয় না।

যে দৃশ্যটা আমরা বানাবো

তুমি Poridhi.io-র system administrator। ProjectX নামে নতুন একটা project শুরু হচ্ছে, তিনটে টিম কাজ করবে — কিন্তু প্রত্যেকের দরকার আলাদা:

টিমGroupযা দরকার
DevelopersdevSource code-এ পূর্ণ অধিকার, config-এ শুধু পড়া
OperationsopsConfig-এ পূর্ণ অধিকার, source code-এ শুধু পড়া
QA Testersqaসব জায়গায় শুধু পড়া, লিখতে পারবে শুধু tests-এ
যা বানাতে যাচ্ছি
ProjectX/
├── src/      dev: rwx   ops: r-x   qa: r-x
├── config/   dev: r-x   ops: rwx   qa: r-x
├── docs/     dev: rwx   ops: r-x   qa: r-x
└── tests/    dev: rwx   ops: r-x   qa: rwx
কেন chmod একা এটা পারে না

প্রতিটা file-এর ঠিক একটা group owner থাকে — একটার বেশি নয়। তাই src/-এর group যদি dev হয়, তাহলে chmod দিয়ে তুমি dev-কে যা খুশি দিতে পারো, কিন্তু ops আর qa দুজনেই পড়ে যাবে "others"-এর দলে — আর তাদের দুজনকে আলাদা করে কিছু বলার কোনো উপায় নেই।

এখানেই ACL (Access Control List) আসে। setfacl ঐ তিন দলের বাইরে যত খুশি নাম ধরে নিয়ম লিখতে দেয়।

অনুশীলন

Part 1 — পরিবেশ তৈরি

ACL package আছে কিনা দেখা

লক্ষ্য: setfacl আর getfacl হাতে পাওয়া।

bash
$ sudo apt update && sudo apt install -y acl
$ which setfacl getfacl
output
/usr/bin/setfacl
/usr/bin/getfacl
দুটো path-ই দেখালে কাজ চলবে। RHEL/Fedora হলে sudo dnf install -y acl।
Filesystem-এও ACL চালু থাকতে হবে

Package থাকাই যথেষ্ট নয় — filesystem-টাও ACL সমর্থন করতে হবে। আধুনিক ext4, xfs, btrfs-এ এটা default-এই চালু। যাচাই করতে:

bash
$ mount | grep " / "

যদি পরে setfacl: Operation not supported আসে, তার মানে ঐ filesystem-এ ACL বন্ধ — তখন sudo mount -o remount,acl / দিয়ে চালু করতে হবে। কিছু container-এ এটা লাগতে পারে।

তিনটে টিম আর ছয়জন user

লক্ষ্য: group বানানো, user বানানো, আর তাদের group-এ বসানো।

bash
$ sudo groupadd dev
$ sudo groupadd ops
$ sudo groupadd qa

এবার ছয়জন user — প্রত্যেকের shell স্পষ্ট করে বলে দিচ্ছি:

bash
$ for u in dev_user1 dev_user2 ops_user1 ops_user2 qa_user1 qa_user2; do
>   sudo useradd -m -s /bin/bash "$u"
> done

একটা একটা করে ছয়বার useradd লিখলেও একই কাজ — for শুধু টাইপ করা বাঁচায়।

এবার group-এ বসাও:

bash
$ sudo usermod -aG dev dev_user1
$ sudo usermod -aG dev dev_user2
$ sudo usermod -aG ops ops_user1
$ sudo usermod -aG ops ops_user2
$ sudo usermod -aG qa  qa_user1
$ sudo usermod -aG qa  qa_user2
Lab 5-এর সেই -a

Lab 05-এ বলেছিলাম -G-র সাথে -a না দিলে আগের সব group মুছে যায়। এখানে ছয়বার লাগছে — প্রতিবারই -aG। অভ্যাসটা এভাবেই গড়ে ওঠে।

যাচাই করো:

bash
$ getent group dev ops qa
$ id dev_user1
output
$ getent group dev ops qa
dev:x:1003:dev_user1,dev_user2
ops:x:1004:ops_user1,ops_user2
qa:x:1005:qa_user1,qa_user2

$ id dev_user1
uid=1003(dev_user1) gid=1003(dev_user1) groups=1003(dev_user1),1003(dev)
প্রত্যেকের primary group নিজের নামে, আর dev/ops/qa হলো supplementary।
Password এখানে লাগছে না

মূল lab-এ প্রত্যেকের password বসানো হয়েছিল। আমরা সেটা বাদ দিচ্ছি, কারণ পরীক্ষা করার সময় su দিয়ে login না করে sudo -u দিয়ে command চালাবো — তাতে password লাগে না। ছয়বার password টাইপ করার ঝামেলাও বাঁচল।

চাইলে sudo passwd dev_user1 দিয়ে বসিয়ে নিতে পারো, কোনো ক্ষতি নেই।

Directory কাঠামো বানানো

লক্ষ্য: চারটে subdirectory, চার রকম প্রয়োজন।

bash
$ sudo mkdir -p /home/poridhian/code/projects/ProjectX/{src,config,docs,tests}
ঐ কোঁকড়া বন্ধনী দুটো

{src,config,docs,tests} — এটাকে বলে brace expansion। Shell এটাকে ভেঙে চারটে আলাদা path বানিয়ে দেয়, অর্থাৎ উপরের এক লাইন আর নিচের চার লাইন হুবহু একই কাজ:

bash — একই জিনিস
$ sudo mkdir -p /home/poridhian/code/projects/ProjectX/src
$ sudo mkdir -p /home/poridhian/code/projects/ProjectX/config
$ sudo mkdir -p /home/poridhian/code/projects/ProjectX/docs
$ sudo mkdir -p /home/poridhian/code/projects/ProjectX/tests

আর -p মানে "মাঝের folder গুলোও বানিয়ে নাও" — /home/poridhian/code/projects/ না থাকলেও এক command-এই পুরো পথটা তৈরি হয়ে যাবে।

যাচাই করো:

bash
$ ls -l /home/poridhian/code/projects/ProjectX/
output
total 16
drwxr-xr-x 2 root root 4096 Mar 02 13:10 config
drwxr-xr-x 2 root root 4096 Mar 02 13:10 docs
drwxr-xr-x 2 root root 4096 Mar 02 13:10 src
drwxr-xr-x 2 root root 4096 Mar 02 13:10 tests
এখন সব root root-এর আর 755 — Part 3-এ এটাই বদলাবো।

Part 2 — umask দিয়ে default ঠিক করা

এখনকার umask দেখা

লক্ষ্য: নতুন file কেন 644 নিয়ে জন্মায়, সেটা বোঝা।

bash
$ umask
output
0022
প্রথম 0-টা special permission-এর জন্য, আপাতত ভুলে যাও। আসল অংশ 022।

umask অনুমতি দেয় না — কেটে নেয়। হিসেবটা এরকম:

হিসেবটা
                    File              Directory
সর্বোচ্চ default      666 (rw-rw-rw-)   777 (rwxrwxrwx)
umask 022 কাটে      -022 (----w--w-)   -022 (----w--w-)
                   ─────              ─────
ফল                  644 (rw-r--r--)   755 (rwxr-xr-x)
File কখনো execute অনুমতি নিয়ে জন্মায় না

খেয়াল করো — directory-র সর্বোচ্চ 777, কিন্তু file-এর 666, 777 নয়। অর্থাৎ umask 000 দিলেও নতুন file-এ x বসবে না।

এটা Linux-এর একটা ইচ্ছাকৃত নিরাপত্তা — কোনো file program হিসেবে চলতে পারবে কিনা, সেটা তোমাকে স্পষ্ট করে chmod +x দিয়ে বলতে হবে। নাহলে কেউ ক্ষতিকর কিছু download করলেই সেটা চালু হওয়ার যোগ্য হয়ে যেত।

নিজে দেখে নাও:

bash
$ touch /tmp/testfile
$ ls -l /tmp/testfile
output
-rw-r--r-- 1 poridhian poridhian 0 Mar 02 13:15 /tmp/testfile
ঠিক 644 — হিসেব মিলে গেছে।

Project-এর জন্য কড়া umask

লক্ষ্য: নতুন file যেন group পড়তে পারে, কিন্তু বাইরের কেউ না।

ProjectX-এর জন্য চাই umask 027:

027 কী করে
                    File              Directory
সর্বোচ্চ default      666               777
umask 027 কাটে      -027              -027
                   ─────              ─────
ফল                  640 (rw-r-----)   750 (rwxr-x---)
                                       others: কিছুই না

টিমের সবাই যাতে এই setting পায়, তার জন্য একটা script বানাই:

bash
$ sudo tee /home/poridhian/code/projects/ProjectX/project_env.sh > /dev/null << 'EOF'
#!/bin/bash
# Set project-specific umask
umask 027
echo "ProjectX environment active"
echo "umask is now: $(umask)"
EOF

$ sudo chmod +x /home/poridhian/code/projects/ProjectX/project_env.sh
ঐ << 'EOF' জিনিসটা

এটাকে বলে heredoc — "এখান থেকে EOF পর্যন্ত সব লেখা ঐ command-এ পাঠাও"। বহু লাইনের file বানানোর সহজ উপায়।

EOF-এর চারপাশের single quote দুটো খুব জরুরি। ওগুলো থাকলে ভেতরের $(umask) এখনই চলে না, file-এ লেখা হিসেবেই বসে — আর চলে পরে, যখন script টা চালাবে। Quote বাদ দিলে $(umask) এখনই চলে গিয়ে file-এ শুধু ফলাফলটা (0022) বসে যেত, আর script টা অর্থহীন হয়ে যেত।

মূল lab-এ cat > file ব্যবহার করা হয়েছে; আমরা sudo tee ব্যবহার করছি — কারণ Lab 04-এ দেখেছ, > চালায় তোমার নিজের shell, root নয়।

এবার script টা চালাও — কিন্তু বিশেষভাবে:

bash
$ source /home/poridhian/code/projects/ProjectX/project_env.sh
output
ProjectX environment active
umask is now: 0027
source আর ./script — দুটো সম্পূর্ণ আলাদা

এখানে ./project_env.sh লিখলে কিছুই কাজ করত না — অথচ output প্রায় একই দেখাত। কারণটা জানা থাকা দরকার:

যা লিখলেযা হয়
./project_env.shনতুন একটা child shell খোলে, সেখানে umask বদলায়, তারপর ঐ shell মরে যায় — সাথে umask-ও
source project_env.shবর্তমান shell-এই লাইনগুলো চালায় — তাই umask টিকে থাকে

source-এর সংক্ষিপ্ত রূপ হলো একটা বিন্দু: . project_env.sh — দুটো একই।

যাচাই করো — নতুন file এখন কী নিয়ে জন্মাচ্ছে:

bash
$ touch /tmp/testfile_027
$ ls -l /tmp/testfile /tmp/testfile_027
output — দুটো পাশাপাশি
-rw-r--r-- 1 poridhian poridhian 0 Mar 02 13:15 /tmp/testfile       ← umask 022
-rw-r----- 1 poridhian poridhian 0 Mar 02 13:22 /tmp/testfile_027  ← umask 027
শেষ তিনটে অক্ষর r-- থেকে --- হয়ে গেছে — others-এর আর কোনো access নেই।
এই setting শুধু এই shell-এ, আর এখনকার জন্য

Terminal বন্ধ করলেই umask আবার 022-তে ফিরে যাবে। স্থায়ী করতে হলে লাইনটা ~/.bashrc-তে বসাতে হয় — বা Lab 04-এর /etc/skel/.bashrc-তে, যাতে প্রত্যেক নতুন user সেটা নিয়েই জন্মায়।

Part 3 — chmod দিয়ে ভিত্তি গড়া

মালিকানা আর ভিত্তি অনুমতি বসানো

লক্ষ্য: ACL-এর আগে সাধারণ মডেল দিয়ে যতটা সম্ভব করা।

bash
$ sudo chown -R dev_user1:dev /home/poridhian/code/projects/ProjectX

dev_user1:dev — colon-এর আগে মালিক, পরে group। -R মানে ভেতরের সবকিছুতেও।

এবার প্রতিটা folder-এর জন্য আলাদা অনুমতি:

bash
$ cd /home/poridhian/code/projects

# মূল folder — others ঢুকতে ও দেখতে পারবে
$ sudo chmod 775 ProjectX

# src আর config — others সম্পূর্ণ বাইরে
$ sudo chmod 770 ProjectX/src
$ sudo chmod 770 ProjectX/config

# docs আর tests — others পড়তে পারবে
$ sudo chmod 775 ProjectX/docs
$ sudo chmod 775 ProjectX/tests
মূল folder-টা 775 কেন, 770 নয়

মনে হতে পারে ProjectX-ও 770 হওয়া উচিত। কিন্তু তাতে ops আর qa-র কেউ ভেতরে ঢুকতেই পারত না — আর তাহলে src/ বা config/-এ যত ACL-ই লেখো, কোনোটাই কাজে লাগত না।

মনে করো Step শুরুর সেই কথাটা — ভেতরের file-এ পৌঁছাতে হলে পথের প্রতিটা directory-তে x লাগে। মূল folder-টা সেই পথ।

যাচাই করো:

bash
$ ls -l /home/poridhian/code/projects/ProjectX/
output
drwxrwx--- 2 dev_user1 dev 4096 Mar 02 13:10 config
drwxrwxr-x 2 dev_user1 dev 4096 Mar 02 13:10 docs
-rwxr-xr-x 1 dev_user1 dev  118 Mar 02 13:20 project_env.sh
drwxrwx--- 2 dev_user1 dev 4096 Mar 02 13:10 src
drwxrwxr-x 2 dev_user1 dev 4096 Mar 02 13:10 tests
src আর config-এর শেষে --- — others সম্পূর্ণ বাইরে। docs আর tests-এ r-x।
Symbolic notation — যখন একটা bit-ই বদলাতে চাও

chmod 750 তিনটে দলের অনুমতিই একসাথে বসিয়ে দেয়। কিন্তু শুধু একটা জিনিস যোগ বা বাদ দিতে চাইলে symbolic লেখা সুবিধার:

bash
$ sudo chmod g+x ProjectX/src        # group-কে x যোগ করো
$ sudo chmod o-w ProjectX/docs       # others থেকে w বাদ দাও
$ sudo chmod o=r ProjectX/docs       # others-এর অনুমতি হুবহু r করো
কেকাজকী
u owner, g group, o others, a সবাই+ যোগ, - বাদ, = হুবহু এটাইr, w, x

পার্থক্যটা মনে রাখার মতো — + আর - বাকি অনুমতিগুলোতে হাত দেয় না, কিন্তু = আর octal সংখ্যা পুরোটা বদলে দেয়।

Part 4 — setfacl দিয়ে সূক্ষ্ম নিয়ন্ত্রণ

তিন group-কে তিন রকম অনুমতি

লক্ষ্য: যেটা chmod দিয়ে কোনোভাবেই হতো না, সেটা করা।

setfacl-এর গঠন
setfacl -m  g:ops:rx  /path/to/dir
        │   │  │   │
        │   │  │   └─ কী অনুমতি (r, w, x)
        │   │  └───── কার নাম (group বা user-এর)
        │   └──────── ধরন: u = user, g = group
        └──────────── -m = modify (নিয়ম যোগ/বদল করো)

src/ — dev-এর জিনিস, বাকিরা শুধু পড়বে:

bash
$ cd /home/poridhian/code/projects/ProjectX

$ sudo setfacl -R -m g:ops:rx src
$ sudo setfacl -R -m g:qa:rx  src

config/ — ops-এর জিনিস, বাকিরা শুধু পড়বে:

bash
$ sudo setfacl -R -m g:ops:rwx config
$ sudo setfacl -R -m g:dev:rx  config
$ sudo setfacl -R -m g:qa:rx   config

tests/ — qa এখানে লিখতে পারবে:

bash
$ sudo setfacl -R -m g:qa:rwx tests
read-only মানে rx, শুধু r নয়

খেয়াল করো সব read-only অনুমতিতে rx লিখেছি। Directory-তে x ছাড়া ভেতরে ঢোকাই যায় না — তাই শুধু r দিলে group-এর লোকেরা file-এর নাম দেখতে পেত, কিন্তু কোনোটা খুলতে পারত না।

এই ভুলটা খুব সাধারণ, আর ধরা কঠিন — কারণ ls কাজ করে, তাই মনে হয় সব ঠিক আছে।

যাচাই করো:

bash
$ getfacl src
output
# file: src
# owner: dev_user1
# group: dev
user::rwx
group::rwx
group:ops:r-x
group:qa:r-x
mask::rwx
other::---
উপরের তিনটে (user::, group::, other::) হলো সাধারণ chmod-এর অনুমতি। মাঝের দুটো — যেখানে নাম লেখা আছে — সেগুলোই setfacl-এর যোগ করা।

ls -l-এও একটা ছোট্ট চিহ্ন দেখা যাবে:

bash
$ ls -l /home/poridhian/code/projects/ProjectX/
output
drwxrwx---+ 2 dev_user1 dev 4096 Mar 02 13:10 config
drwxrwxr-x  2 dev_user1 dev 4096 Mar 02 13:10 docs
drwxrwx---+ 2 dev_user1 dev 4096 Mar 02 13:10 src
drwxrwxr-x+ 2 dev_user1 dev 4096 Mar 02 13:10 tests
শেষের ঐ + চিহ্নটার মানে "এই folder-এ বাড়তি ACL নিয়ম আছে"। docs-এ নেই, কারণ ওতে আমরা কোনো ACL দিইনি।
mask:: লাইনটা কী

getfacl-এর output-এ একটা mask::rwx লাইন দেখেছ। এটা একটা ছাদ — ACL দিয়ে দেওয়া কোনো অনুমতি এর বেশি হতে পারে না।

ধরো mask হলো r-x, আর তুমি g:ops:rwx দিলে। তখন getfacl দেখাবে group:ops:rwx, কিন্তু পাশে লিখবে #effective:r-x — অর্থাৎ w-টা লেখা আছে ঠিকই, কাজ করছে না।

chmod দিয়ে group-এর অনুমতি বদলালে mask-ও বদলে যায় — এজন্যই ACL বসানোর পরে chmod চালালে ACL গুলো নিঃশব্দে অকেজো হয়ে যেতে পারে। ক্রমটা তাই সবসময় chmod আগে, setfacl পরে।

Part 5 — পরীক্ষা: তত্ত্ব বনাম বাস্তব

Test file বানানো

লক্ষ্য: প্রতিটা folder-এ একটা করে file — আর প্রথম ধাক্কাটা খাওয়া।

সোজা উপায়ে চেষ্টা করো:

bash
$ echo "// Main application logic" > ProjectX/src/main.c
output — আটকে যাবে
bash: ProjectX/src/main.c: Permission denied
এটাই আশা করা হচ্ছিল। কেন, সেটা নিজে একবার ভেবে দেখো।
কেন আটকালো

src/-এর অনুমতি drwxrwx---, মালিক dev_user1:dev। তুমি চালাচ্ছো poridhian হিসেবে — তুমি মালিকও নও, dev group-এও নও। তাই তুমি "others", আর others-এর জন্য লেখা আছে ---।

অর্থাৎ permission মডেল ঠিকঠাক কাজ করছে। এটা সমস্যা নয়, এটাই প্রমাণ।

তাহলে dev_user1 হয়ে বানাও:

bash
$ sudo -u dev_user1 bash -c 'echo "// Main application logic" > /home/poridhian/code/projects/ProjectX/src/main.c'
$ sudo -u dev_user1 bash -c 'echo "db_host=db-01" > /home/poridhian/code/projects/ProjectX/config/app.conf'
$ sudo -u dev_user1 bash -c 'echo "# Documentation" > /home/poridhian/code/projects/ProjectX/docs/README.md'
$ sudo -u dev_user1 bash -c 'echo "test_case_1: pass" > /home/poridhian/code/projects/ProjectX/tests/test1.txt'
ঐ bash -c মোড়কটা কেন লাগছে

Lab 04-এ দেখেছ > চিহ্নটা command-এর কাজ নয়, shell-এর কাজ। এখানেও একই ব্যাপার:

পার্থক্যটা
sudo -u dev_user1 echo "..." > file
└─ echo চলে dev_user1 হয়ে, কিন্তু > চালায় তোমার shell → denied

sudo -u dev_user1 bash -c 'echo "..." > file'
└─ পুরো bash টাই dev_user1 হয়ে চলে, তাই >-ও তার হয়ে → সফল

Single quote দুটোও জরুরি — নাহলে > তোমার shell আগেই দেখে ফেলত।

যাচাই করো:

bash
$ ls -l ProjectX/src/ ProjectX/config/
output
ProjectX/src/:
-rw-r--r-- 1 dev_user1 dev_user1 26 Mar 02 13:45 main.c

ProjectX/config/:
-rw-r--r-- 1 dev_user1 dev_user1 14 Mar 02 13:45 app.conf
দুটো জিনিস খুব ভালো করে খেয়াল করো — file গুলোর শেষে কোনো + চিহ্ন নেই, আর group হলো dev_user1, dev নয়। পরের step-এ এই দুটোই সব ওলটপালট করে দেবে।

পরীক্ষা — আর তিনটে অপ্রত্যাশিত ফল

লক্ষ্য: নিয়ম যা বলছে আর বাস্তবে যা ঘটছে — পার্থক্যটা ধরা।

এবার আসল মজা। প্রতিটা command চালানোর আগে নিজে একবার অনুমান করো কী হবে, তারপর মিলিয়ে দেখো।

Developer হিসেবে:

bash
# ১ — src পড়া (dev-এর নিজের জায়গা)
$ sudo -u dev_user1 cat ProjectX/src/main.c

# ২ — config পড়া (ACL-এ rx দেওয়া আছে)
$ sudo -u dev_user1 cat ProjectX/config/app.conf

# ৩ — config-এ লেখা (ACL বলছে read-only!)
$ sudo -u dev_user1 bash -c 'echo "new_setting=true" >> /home/poridhian/code/projects/ProjectX/config/app.conf'
output
১ → // Main application logic          ✓ যেমন ভেবেছিলে
২ → db_host=db-01                      ✓ যেমন ভেবেছিলে
৩ → (কোনো error নেই — লেখা হয়ে গেল!)      ✗ এটা তো হওয়ার কথা ছিল না
৩ নম্বর — ACL বলছে read-only, তবু লেখা হলো কেন

কারণ app.conf file-টা dev_user1 নিজেই বানিয়েছে (Step 8-এ)। সে ঐ file-এর মালিক।

আর Linux অনুমতি পরীক্ষা করে একটা নির্দিষ্ট ক্রমে — মালিক সবার আগে। তুমি মালিক হলে তোমার owner-অনুমতি (rw-) দিয়েই কাজ হয়ে যায়, কোনো ACL-এর দিকে তাকানোই হয় না।

ACL-এ g:dev:rx লেখা আছে ঠিকই, কিন্তু সেটা প্রযোজ্য হতো dev_user2-র মতো কারো ক্ষেত্রে — যে dev group-এ আছে কিন্তু file-এর মালিক নয়।

Operations হিসেবে:

bash
# ১ — src পড়া (ACL-এ rx আছে)
$ sudo -u ops_user1 cat ProjectX/src/main.c

# ২ — src-এ লেখা (read-only হওয়ার কথা)
$ sudo -u ops_user1 bash -c 'echo "// ops edit" >> /home/poridhian/code/projects/ProjectX/src/main.c'

# ৩ — config-এ লেখা (ACL-এ rwx দেওয়া আছে!)
$ sudo -u ops_user1 bash -c 'echo "db_port=5432" >> /home/poridhian/code/projects/ProjectX/config/app.conf'
output
১ → // Main application logic          ✓ যেমন ভেবেছিলে
২ → Permission denied                  ✓ যেমন ভেবেছিলে
৩ → Permission denied                  ✗ ops-এর তো rwx আছে!
৩ নম্বর — ACL-এ rwx আছে, তবু আটকালো কেন

এবার উল্টো কারণ। setfacl -R চালানো হয়েছিল Step 7-এ — আর app.conf জন্মেছে Step 8-এ, তার পরে।

-R মানে "এই মুহূর্তে ভেতরে যা যা আছে, সবগুলোতে নিয়মটা বসাও"। ভবিষ্যতে যা জন্মাবে, তাদের জন্য কিছুই বলা হয়নি। তাই app.conf-এ কোনো ACL-ই নেই — Step 8-এর output-এ + চিহ্ন না থাকাটাই ছিল তার ইঙ্গিত।

ACL না থাকায় ops_user1 পড়ে গেল সাধারণ মডেলের হিসেবে: file-এর মালিক dev_user1, group dev_user1, অনুমতি 644। ops সেখানে "others" — আর others-এর আছে শুধু r--।

মনে রেখো: ACL folder-এ বসানো আর ভেতরের file-এ বসানো — দুটো আলাদা জিনিস।

দুটোই tests/-এ লেখা, তবু একটা আটকালো আরেকটা চলল। কারণ দুটো সম্পূর্ণ আলাদা কাজ:

>> test1.txtবিদ্যমান file-এর ভেতরে লেখাfile-এর write অনুমতি → qa-র নেই
> test2.txtনতুন file বানানোdirectory-র write অনুমতি → ACL-এ আছে ✓

এটাই সেই কথাটার সবচেয়ে পরিষ্কার উদাহরণ — file বানানো বা মোছা directory-র অনুমতির ব্যাপার, file-এর নিজের নয়।

এর একটা অদ্ভুত পরিণতিও আছে: directory-তে w থাকলে তুমি এমন file-ও মুছে দিতে পারো যেটা পড়ার অনুমতিও তোমার নেই। file-টা মোছা হচ্ছে না — directory থেকে তার নামটা মোছা হচ্ছে।

নতুন file-এর মালিক qa_user1 — কারণ সে-ই বানিয়েছে।

সমস্যাটার সমাধান — default ACL

লক্ষ্য: ভবিষ্যতে জন্মানো file-ও যাতে নিয়ম মেনে চলে।

Step 9-এ দেখলে মূল সমস্যাটা — setfacl -R শুধু বর্তমান file গুলোতে নিয়ম বসায়। এর সমাধান হলো default ACL, যেটা লেখা হয় -d দিয়ে:

bash
# এখনকার file গুলোর জন্য (আগের মতোই)
$ sudo setfacl -R -m g:ops:rwx config

# ভবিষ্যতে যা জন্মাবে তাদের জন্য
$ sudo setfacl -R -d -m g:ops:rwx config
$ sudo setfacl -R -d -m g:dev:rx  config
$ sudo setfacl -R -d -m g:qa:rx   config
-d মানে "উত্তরাধিকার"

Default ACL কোনো অনুমতি দেয় না — এটা একটা ছাঁচ, যা এই directory-তে নতুন জন্মানো প্রতিটা file আর folder পেয়ে যায়। Lab 04-এর /etc/skel/-এর সাথে মিল আছে, তবে পার্থক্যও আছে: /etc/skel/ একবার copy করে ছেড়ে দেয়, আর default ACL প্রতিবার নতুন file জন্মানোর সময় নিজে থেকেই প্রয়োগ হয়।

এজন্যই সাধারণত দুটোই লাগে — -m বর্তমানের জন্য, -d -m ভবিষ্যতের জন্য।

এবার পরীক্ষা করো — নতুন file বানিয়ে:

bash
$ sudo -u dev_user1 bash -c 'echo "cache_size=256" > /home/poridhian/code/projects/ProjectX/config/cache.conf'
$ ls -l ProjectX/config/
output
-rw-r--r--  1 dev_user1 dev_user1 14 Mar 02 13:45 app.conf
-rw-rw----+ 1 dev_user1 dev_user1 15 Mar 02 14:15 cache.conf
নতুন file-টার শেষে + চিহ্ন! পুরোনো app.conf-এ এখনো নেই।

এখন ops লিখতে পারবে:

bash
$ sudo -u ops_user1 bash -c 'echo "cache_ttl=3600" >> /home/poridhian/code/projects/ProjectX/config/cache.conf'
$ cat ProjectX/config/cache.conf
output
cache_size=256
cache_ttl=3600
এবার সফল — কারণ cache.conf জন্মানোর সময়েই default ACL থেকে g:ops:rwx পেয়ে গেছে।

পুরোনো file-টাও ঠিক করে নাও:

bash
$ sudo setfacl -m g:ops:rw ProjectX/config/app.conf
$ sudo -u ops_user1 bash -c 'echo "db_port=5432" >> /home/poridhian/code/projects/ProjectX/config/app.conf'
$ cat ProjectX/config/app.conf
output
db_host=db-01
new_setting=true
db_port=5432
Step 9-এ যেটা আটকে গিয়েছিল, এখন চলছে। File-এ x দিইনি — ওটা directory-র জন্য, সাধারণ file-এ দরকার নেই।

পুরো ব্যাপারটা এক নজরে

এই lab-এর তিনটে "উল্টো ফল"-ই আসলে একটা জিনিস থেকে এসেছে — Linux অনুমতি পরীক্ষা করে একটা নির্দিষ্ট ক্রমে, আর প্রথম যেটা মিলে যায়, সেখানেই থেমে যায়:

অনুমতি পরীক্ষার ক্রম
কেউ একটা file ছুঁতে চাইল
          │

          ▼

দুটো কথা মাথায় গেঁথে নাও — মালিকানা ACL-এর আগে, আর ACL file-এ থাকতে হয়, শুধু folder-এ থাকলে হয় না। এই দুটো জানলে এই lab-এর তিনটে বিস্ময়ই আর বিস্ময় থাকে না।

স্তরে স্তরে কাজ করার ধারা
স্তরহাতিয়ারকী ঠিক করে

ক্রমটা এলোমেলো করা যায় না — বিশেষ করে chmod সবসময় setfacl-এর আগে, কারণ chmod mask বদলে দিয়ে ACL গুলো নিঃশব্দে অকেজো করে দিতে পারে।

নিজে করো — Challenge

  1. docs/-এ এমন ব্যবস্থা করো যাতে তিনটে group-ই লিখতে পারে, কিন্তু বাইরের কেউ পড়তেও না পারে। তারপর তিনজন user দিয়ে পরীক্ষা করো।
  2. src/-এ default ACL বসাও, তারপর dev_user2 দিয়ে একটা নতুন file বানিয়ে getfacl দিয়ে দেখো নিয়মগুলো এসেছে কিনা।
  3. একজন বাইরের auditor এলো — audit_user। তাকে কোনো group-এ না ঢুকিয়ে পুরো ProjectX-এ শুধু-পড়ার অনুমতি দাও। (ইঙ্গিত: setfacl-এ g:-র বদলে u:)
  4. কোনো একটা group-এর ACL সম্পূর্ণ তুলে নাও। (ইঙ্গিত: -x)
সমাধান দেখো
bash — solution
# ১ — docs-এ তিন group-ই লিখবে, others কিছুই না
$ cd /home/poridhian/code/projects/ProjectX

$ sudo chmod 770 docs                      # আগে others-কে বের করো
$ sudo setfacl -R -m g:ops:rwx docs
$ sudo setfacl -R -m g:qa:rwx  docs
$ sudo setfacl -R -d -m g:ops:rwx docs     # ভবিষ্যতের জন্যও
$ sudo setfacl -R -d -m g:qa:rwx  docs

$ sudo -u ops_user1 bash -c 'echo "ops note" > /home/poridhian/code/projects/ProjectX/docs/ops.md'
$ sudo -u qa_user1  bash -c 'echo "qa note"  > /home/poridhian/code/projects/ProjectX/docs/qa.md'
$ ls -l docs/

chmod 770 আগে চালানোটা জরুরি — setfacl-এর পরে চালালে mask বদলে গিয়ে ACL গুলো অকেজো হয়ে যেত। dev-কে আলাদা করে ACL দিতে হয়নি, কারণ folder-এর group owner-ই dev।

bash — solution
# ২ — src-এ default ACL
$ sudo setfacl -R -d -m g:ops:rx src
$ sudo setfacl -R -d -m g:qa:rx  src

$ sudo -u dev_user2 bash -c 'echo "// helper" > /home/poridhian/code/projects/ProjectX/src/util.c'
$ getfacl src/util.c
output
# file: src/util.c
# owner: dev_user2
# group: dev
user::rw-
group:ops:r-x            #effective:r--
group:qa:r-x             #effective:r--
mask::r--
other::---

নিয়মগুলো এসেছে। #effective:r-- লেখাটা খেয়াল করো — x চাওয়া হয়েছিল কিন্তু mask r-- হওয়ায় সেটা কাজ করছে না। সাধারণ file-এ x-এর দরকারও নেই, তাই এখানে সমস্যা নয়। এটাই mask লাইনটার কাজ চোখে দেখা।

bash — solution
# ৩ — auditor, কোনো group ছাড়াই
$ sudo useradd -m -s /bin/bash audit_user

$ sudo setfacl -R -m u:audit_user:rX .
$ sudo setfacl -R -d -m u:audit_user:rX .

$ sudo -u audit_user cat src/main.c
// Main application logic
$ sudo -u audit_user bash -c 'echo "x" >> src/main.c'
bash: src/main.c: Permission denied

দুটো জিনিস এখানে নতুন। u: দিয়ে group নয়, একজন নির্দিষ্ট user-কে অনুমতি দেওয়া হচ্ছে — যেটা সাধারণ মডেলে একদমই সম্ভব নয়।

আর বড় হাতের X (ছোট x নয়) মানে — "directory-তে x দাও, কিন্তু সাধারণ file-এ দিও না"। -R-এর সাথে এটা খুবই কাজের, নাহলে প্রতিটা .c file-ও চালানোর যোগ্য হয়ে যেত।

bash — solution
# ৪ — ACL তুলে নেওয়া
$ sudo setfacl -R -x g:qa src           # শুধু qa-র নিয়মটা
$ getfacl src | grep qa
(কিছুই নেই)

$ sudo setfacl -R -b docs               # সব ACL একসাথে মুছে দাও
$ ls -ld docs
drwxrwx--- 2 dev_user1 dev 4096 Mar 02 14:30 docs   # + চিহ্ন উধাও

-x একটা নির্দিষ্ট নিয়ম তোলে (অনুমতি লেখার দরকার নেই, শুধু কার নিয়ম সেটা বললেই হয়), আর -b সব ACL মুছে file-টাকে সাধারণ মডেলে ফিরিয়ে আনে।

আটকে গেলে

সমস্যাকী হয়েছে / কী করবে
setfacl: Operation not supportedFilesystem-এ ACL বন্ধ। sudo mount -o remount,acl / চালাও।
setfacl: command not foundsudo apt install -y acl (বা dnf install acl)।
ACL দিয়েছি তবু Permission deniedতিনটে সম্ভাবনা: (১) file-টা ACL বসানোর পরে জন্মেছে — -d লাগবে; (২) পরে chmod চালিয়ে mask নষ্ট করেছ; (৩) পথের কোনো directory-তে x নেই।
getfacl-এ #effective: লেখা দেখাচ্ছেmask ঐ অনুমতিটা আটকে রাখছে। sudo setfacl -m m::rwx <path> দিয়ে mask বাড়াও।
ব্যবহারকারী ls পারছে কিন্তু file পড়তে পারছে নাDirectory-তে r আছে, x নেই। r-এর বদলে rx দাও।
umask বদলালাম, তবু file আগের মতোই./script.sh দিয়ে চালিয়েছ। source script.sh ব্যবহার করো।
sudo -u user echo ... > file denied> চালাচ্ছে তোমার shell। bash -c '...' দিয়ে মুড়ে দাও।
ACL বসানোর পর chmod চালিয়ে সব ভেঙে গেছেgetfacl দিয়ে দেখো mask কমে গেছে কিনা। ক্রমটা সবসময় chmod আগে, setfacl পরে।

তিনটে হাতিয়ার তিনটে আলাদা মুহূর্তে কাজ করে — umask জন্মের সময়, chmod তিন দলের জন্য, আর setfacl নাম ধরে ধরে। একটার কাজ আরেকটা দিয়ে হয় না, তাই বাস্তবে তিনটেই স্তরে স্তরে ব্যবহার করতে হয়।

তবে এই lab-এর আসল শিক্ষা নিয়ম লেখা নয় — যাচাই করা। তিনবার আমরা দেখলাম নিয়ম এক কথা বলছে আর বাস্তব আরেক। প্রতিবারই কারণটা ছিল যুক্তিসঙ্গত: মালিকানা ACL-এর আগে আসে, আর ACL file-এ থাকতে হয় — শুধু folder-এ থাকলে হয় না।

তাই নিয়ম বসিয়ে সন্তুষ্ট হয়ো না। sudo -u দিয়ে সত্যিকারের user হয়ে চেষ্টা করে দেখো — অনুমতি ঠিক আছে কিনা সেটা ঐ পরীক্ষাটাই বলে, getfacl-এর output নয়।
