Linux Performance Analysis

"Server টা slow" — এই একটা বাক্য শুনে কাজ শুরু করতে হয়। কিন্তু slow মানে কী? CPU শেষ, না RAM শেষ, না disk আটকে আছে, না network? এই lab-এ তুমি শিখবে কীভাবে এই প্রশ্নটার উত্তর আন্দাজে নয়, মেপে বের করতে হয়। আর শুধু tool চালিয়ে নয় — নিজের হাতে system টাকে চাপে ফেলে, তারপর সংখ্যাগুলো কীভাবে বদলায় সেটা দেখে।

এই lab শেষে যা পারবে

  • চারটে subsystem — CPU, memory, disk, network — আলাদা করে মাপতে পারবে।
  • vmstat, mpstat, pidstat, iostat, sar পড়তে পারবে।
  • নিজে চাপ তৈরি করে দেখবে কোন সংখ্যাটা কেমন বদলায়।
  • OOM killer নিজের চোখে দেখবে আর log-এ তার প্রমাণ খুঁজে বের করবে।
  • সবচেয়ে জরুরি — bottleneck কোথায় সেটা ৬০ সেকেন্ডে বলে দিতে পারবে।
আগে যা জানা থাকলে সুবিধা

বইয়ের Chapter 07 — Processes। সেখানে ps, top, kill আর load average পড়ার নিয়মটা আছে। এই lab সেখান থেকেই শুরু করে পরের ধাপে যায় — কোন process CPU খাচ্ছে সেটা নয়, বরং সমস্যাটা আদৌ CPU-র কিনা সেটা বের করা।

এই lab ইচ্ছে করে system-কে চাপে ফেলবে

আমরা CPU ১০০% করব, RAM ভরে OOM killer ডেকে আনব, disk আটকে দেব। কাজটা নিজের VM, container বা Poridhi Labs VM-এ করো — production server-এ কখনোই নয়। প্রতিটা stress command-এ --timeout দেওয়া আছে, তাই নিজে থেকেই থেমে যাবে।

যে প্রশ্নটার উত্তর খুঁজছি

Performance-এর কাজটা আসলে একটা বাদ দেওয়ার খেলা। চারটে জায়গায় সমস্যা হতে পারে, আর প্রতিটার জন্য আলাদা tool আছে:

একটা tool একাধিক জায়গায় কাজে লাগে

ছবিতে খেয়াল করো vmstat তিনবার এসেছে, iostat দুবার। এটা ভুল নয় — এই tool গুলো একসাথে কয়েকটা জিনিস দেখায়। vmstat-এর নামে "vm" (virtual memory) থাকলেও সে CPU, memory আর I/O — তিনটেরই খবর দেয়।

এজন্যই ৬০ সেকেন্ডের প্রথম command হিসেবে vmstat এত কাজের — এক নজরেই বোঝা যায় কোন দিকে তদন্ত এগোতে হবে।

Netflix-এর performance team-এর একটা বিখ্যাত তালিকা আছে — অচেনা slow server-এ বসে প্রথম ৬০ সেকেন্ডে যা চালানো উচিত। আমরা সেটার মূল অংশটা দেখব।

0.24, 0.31, 0.52   ← ১৫ মিনিট সবচেয়ে বেশি = ঝড় কেটে গেছে

রাত ৩টার alert-এ উঠে যদি দেখো ১৫ মিনিটের সংখ্যাটা সবচেয়ে বড়, তাহলে বুঝবে সমস্যাটা শেষ হয়ে গেছে — এখন তদন্ত করতে হবে log ঘেঁটে, top দেখে নয়।

Linux-এ load average শুধু CPU-র হিসেব নয়

এটা Linux-এর একটা নিজস্ব ব্যাপার, আর এখানেই বেশিরভাগ মানুষ ভুল করে। অন্য Unix-এ load মানে শুধু CPU-র জন্য অপেক্ষা। কিন্তু Linux গোনে CPU-র জন্য অপেক্ষারত + disk-এর জন্য আটকে থাকা (D state) — দুটোই।

মানে হলো, load 8 দেখেও CPU পুরো খালি থাকতে পারে — যদি সব process disk-এর জন্য বসে থাকে। তাই load average দেখে কখনো "CPU-র সমস্যা" সিদ্ধান্তে যেয়ো না। ওটা শুধু বলে "কিছু একটা জমছে"। কী জমছে, সেটা বলবে পরের command গুলো।

এবার dmesg | tail — kernel নিজে কী বলছে:

output — শান্ত system
[    3.881092] systemd[1]: Started Journal Service.
[    4.120441] EXT4-fs (vda1): mounted filesystem with ordered data mode
[   12.339018] eth0: Link is Up - 1Gbps/Full
এখানে শুধু boot-এর সাধারণ বার্তা — কোনো সমস্যা নেই।

কিন্তু যদি এরকম কিছু দেখো, তাহলে আর কিছু দেখার দরকারই নেই:

OOM killer, TCP-র memory শেষ, filesystem-এর error — তিনটেই গুরুতর।
dmesg সবার আগে চালানোর কারণ

বাকি সব tool সংখ্যা দেয়, যেগুলো তোমাকে ব্যাখ্যা করতে হয়। কিন্তু dmesg দেয় বাক্য — kernel সরাসরি বলে দেয় কী সমস্যা হয়েছে। সমস্যাটা যদি এখানেই লেখা থাকে, তাহলে বাকি তদন্তের দরকারই নেই।

নতুন system-এ dmesg -T চালাও — তাতে ঐ [91234.5]-এর বদলে আসল তারিখ-সময় দেখাবে।

Part 2 — CPU

vmstat — এক নজরে সবকিছু

লক্ষ্য: একটা command থেকে CPU, memory আর I/O তিনটেরই খবর নেওয়া।

bash
$ vmstat 1
output
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 0  0      0 3125644  98304 412008    0    0     3    18   52  104  1  1 98  0  0
 0  0      0 3125388  98304 412008    0    0     0     0   61  118  0  1 99  0  0
প্রথম লাইনটা বাদ দাও — ওটা boot থেকে এ পর্যন্ত গড়। আসল তথ্য দ্বিতীয় লাইন থেকে।
ঘরমানেকখন চিন্তার
rCPU-র জন্য অপেক্ষারত processcore সংখ্যার বেশি হলে CPU-তে জট
bI/O-র জন্য আটকে থাকা processধারাবাহিকভাবে শূন্যের বেশি হলে disk-এ সমস্যা
freeখালি RAM (KB)খুব কম — তবে নিচের note দেখো
si / soSwap ভেতরে / বাইরেশূন্যের বেশি হলেই RAM শেষ
usUser CPU %বেশি = application-এর কাজ
sySystem (kernel) CPU %২০%-এর বেশি = kernel-এ অস্বাভাবিক চাপ
waI/O-র অপেক্ষায় CPU %বেশি = disk বা network আটকাচ্ছে
stHypervisor কেড়ে নিয়েছেVM-এ শূন্যের বেশি = host-এ ভিড়
free কম দেখেই ভয় পেয়ো না

Linux খালি RAM-কে অপচয় মনে করে — তাই যতটা পারে file cache দিয়ে ভরে রাখে। free কম কিন্তু cache বেশি মানে system সুস্থ, কারণ cache দরকার হলেই ছেড়ে দেওয়া যায়।

RAM সত্যিই শেষ হয়েছে কিনা বোঝার আসল সূচক free নয় — si আর so। ওগুলো শূন্যের বেশি মানে system RAM-এর অভাবে disk-কে RAM হিসেবে ব্যবহার করছে, যেটা হাজার গুণ ধীর।

us বনাম sy — দুটো আলাদা রোগ

us বেশি মানে তোমার application নিজে হিসেব করছে — স্বাভাবিক, যদি সে হিসেবের কাজই করে থাকে।

কিন্তু sy বেশি মানে kernel অস্বাভাবিক খাটছে। সাধারণ কারণ — অতিরিক্ত system call, ছোট ছোট অজস্র I/O, বা context switch-এর ঝড়। Scenario 3-এ আমরা ইচ্ছে করে এটা ঘটাবো।

এখানে প্রতিটা stress-ng-cpu single-threaded, তাই কেউ ১০০% ছাড়ায়নি। কিন্তু একটা Java বা nginx process-এ ৩৫০% দেখলে অবাক হয়ো না।

চাপ থামার পরে uptime দেখো:

১ মিনিটের সংখ্যাটা সবচেয়ে বড় — Step 2-এর নিয়ম মতো এর মানে চাপটা সদ্য ছিল। আর load কমতে সময় লাগে, সাথে সাথে শূন্য হয় না।

খেয়াল করো কী করলাম — mpstat দিয়ে জানলাম CPU-ই সমস্যা আর %usr-এ চাপ; তারপর pidstat দিয়ে জানলাম কোন process। মোটা দাগ থেকে সূক্ষ্ম দিকে — performance তদন্তের পুরো কাজটাই এই ছাঁচে চলে।

Part 3 — Memory আর OOM killer

free -m পড়া

লক্ষ্য: "খালি RAM" আর "পাওয়া যাবে এমন RAM" — পার্থক্যটা বোঝা।

bash
$ free -m
output
               total   used   free  shared  buff/cache  available
Mem:            3936    612    489      12        2835       3021
Swap:           2047      0   2047

Chapter 07-এ নিয়মটা পড়েছ — free নয়, available দেখো। উপরের output-এ free মাত্র 489 MB কিন্তু available 3021 MB, আর system একদম সুস্থ, কারণ buff/cache-এর 2835 MB দরকার হলেই ছেড়ে দেওয়া যায়।

তাহলে RAM সত্যিই শেষ হয়েছে কিনা বুঝব কীভাবে

এখানেই free -m-এর সীমা। সে একটা স্থিরচিত্র দেখায় — এই মুহূর্তে কত আছে। কিন্তু available কমে আসাটা নিজে থেকে সংকট নয়; সংকট হলো system যখন RAM জোগাড় করতে পরিশ্রম শুরু করে।

সেই পরিশ্রমটা free-তে দেখা যায় না, দেখা যায় vmstat-এর si/so ঘরে — অর্থাৎ প্রতি সেকেন্ডে কতটা swap-এ আসা-যাওয়া হচ্ছে।

দেখছমানে
available কম, si/so শূন্যঠিক আছে — cache ভরা, চাইলেই ছাড়বে
available কম, si/so শূন্যের বেশিএখন সমস্যা — disk-কে RAM বানিয়ে চালাচ্ছে

এজন্যই memory-র তদন্তে free -m শেষ কথা নয়, শুরুর কথা। পরের step-এ দুটোই পাশাপাশি চালিয়ে পার্থক্যটা দেখব।

Swap ব্যবহার হওয়া মানেই সমস্যা নয়

Swap: used শূন্যের বেশি দেখলেই আতঙ্কিত হয়ো না। Linux অনেক সময় বহুক্ষণ ধরে অব্যবহৃত page গুলো আগেভাগেই swap-এ পাঠিয়ে RAM খালি রাখে — এটা বুদ্ধিমানের কাজ।

আসল সমস্যা হলো swap-এ ক্রমাগত আসা-যাওয়া, যেটা vmstat-এর si/so ঘরে ধরা পড়ে। Swap-এ কিছু জমে থাকা এক জিনিস, আর প্রতি সেকেন্ডে swap-এ লেখালেখি হওয়া সম্পূর্ণ আরেক জিনিস।

Scenario 2 — RAM ভরে OOM killer ডেকে আনা

লক্ষ্য: RAM শেষ হলে kernel কী করে, নিজের চোখে দেখা।

Terminal 1-এ নজর রাখো:

bash — terminal 1
$ vmstat 1

Terminal 2 — প্রথমে ভদ্রভাবে, ৮০% RAM:

bash — terminal 2
$ stress-ng --vm 1 --vm-bytes 80% --vm-keep --timeout 45s
output — vmstat-এ যা দেখবে
 r  b   swpd    free   buff  cache   si   so    bi    bo  us sy id wa
 1  0      0  512440  98304 412008    0    0     0     0  25  3 72  0
 1  0  24576  198220  98304 180044   0  412     0   103  28  9 63  0
 1  0  98304   88156  42108  92016 196  884    49   221  31 14 55  0
free নামছে, cache-ও কমছে (kernel cache ছেড়ে দিয়ে জায়গা করছে), আর si/so শূন্য থেকে উঠে আসছে — এটাই RAM ফুরানোর আসল লক্ষণ।

এবার সীমা ছাড়িয়ে যাও — দুটো process, প্রত্যেকে ৯৫%:

bash — terminal 2
$ stress-ng --vm 2 --vm-bytes 95% --timeout 60s
output — stress-ng নিজেই বলবে
stress-ng: info:  [9102] dispatching hogs: 2 vm
stress-ng: error: [9104] stress-ng-vm: gave up trying to allocate
stress-ng: info:  [9102] unsuccessful run completed
দুটো process মিলে ১৯০% RAM চাইছে, যেটা দেওয়া অসম্ভব। কেউ একজন মারা পড়বে।

এবার প্রমাণ খোঁজো — kernel-এর log-এ:

bash
$ sudo dmesg -T | grep -i -A2 "out of memory"
output — OOM killer-এর স্বাক্ষর
[Mon Mar  2 14:41:07 2026] Out of memory: Killed process 9104 (stress-ng-vm)
  total-vm:3985412kB, anon-rss:3812008kB, file-rss:0kB, shmem-rss:0kB,
  UID:1000 pgtables:7648kB oom_score_adj:0
[Mon Mar  2 14:41:07 2026] oom_reaper: reaped process 9104 (stress-ng-vm),
  now anon-rss:0kB, file-rss:0kB, shmem-rss:0kB
anon-rss:3812008kB — ঐ process ৩.৮ GB দখল করেছিল। oom_reaper এসে সেটা পুরো ছাড়িয়ে নিয়েছে।
OOM killer কাকে মারবে সেটা ঠিক করে কীভাবে

সে সবচেয়ে বড় process-কে মারে না, আর যে RAM চেয়েছে তাকেও না। প্রতিটা process-এর একটা oom_score থাকে — মূলত কে কত RAM দখল করে আছে তার উপর ভিত্তি করে। সবচেয়ে বেশি score যার, সে যায়।

bash
# কোন process সবচেয়ে ঝুঁকিতে
$ for p in /proc/[0-9]*; do
>   printf "%s %s\n" "$(cat $p/oom_score 2>/dev/null)" "$(cat $p/comm 2>/dev/null)"
> done | sort -rn | head -5

এর বাস্তব ফল নিষ্ঠুর — তোমার database সবচেয়ে বেশি RAM নেয় বলে সে-ই সবার আগে মরে, যদিও দোষটা ছিল অন্য কোনো process-এর। জরুরি service-কে বাঁচাতে তার oom_score_adj কমিয়ে রাখা যায় (-1000 মানে কখনো মারবে না)।

Application "কারণ ছাড়াই" মরে গেলে এখানেই দেখো

OOM killer-এর মৃত্যুদণ্ড application-এর নিজের log-এ কোনো চিহ্ন রাখে না — সে SIGKILL পায়, তাই কিছু লেখার সুযোগই পায় না। Container হঠাৎ restart নিলে বা service রাতে মরে গেলে সবার আগে dmesg | grep -i "out of memory" চালাও।

Part 4 — Disk আর Network

Scenario 3 — Disk-এ চাপ

লক্ষ্য: iostat পড়া, আর "ব্যস্ত" বনাম "ধীর" পার্থক্য করা।

Terminal 1-এ:

bash — terminal 1
$ iostat -xz 2

Terminal 2-এ চাপ দাও:

bash — terminal 2
$ stress-ng --io 4 --timeout 60s --metrics-brief
output — চাপের সময়
avg-cpu:  %user   %nice %system %iowait  %steal   %idle
           1.25    0.00   38.40    9.85    0.00   50.50

Device    r/s     w/s   rkB/s    wkB/s  r_await  w_await  aqu-sz  %util
vda      0.00  1842.50    0.00   7370.0     0.00     0.52    0.96  99.60
তিনটে জিনিস একসাথে ঘটছে — %util প্রায় ১০০, %system অস্বাভাবিক বেশি, আর w/s বিশাল কিন্তু wkB/s তুলনায় ছোট।
ঘরমানেকখন চিন্তার
r/s, w/sসেকেন্ডে কতবার পড়া/লেখাসংখ্যাটা বড় হলেই খারাপ নয়
rkB/s, wkB/sসেকেন্ডে কত KBdisk-এর সীমার কাছে গেলে
r_await, w_awaitগড়ে কত ms অপেক্ষাসবচেয়ে জরুরি ঘর — SSD-তে ১০ms+ মানে সমস্যা
aqu-szঅপেক্ষমাণ অনুরোধের সারিবড় = জট লেগেছে
%utildisk কত শতাংশ সময় ব্যস্ত১০০ = ব্যস্ত, কিন্তু নিচের note দেখো
%util ১০০% মানে disk শেষ নয়

এটা পুরোনো ঘোরানো disk-এর যুগের হিসেব, যখন disk একসাথে একটাই কাজ করতে পারত। আধুনিক SSD আর NVMe সমান্তরালে বহু অনুরোধ সামলায় — তাই %util ১০০% দেখেও তার আরও অনেক ক্ষমতা বাকি থাকতে পারে।

Disk সত্যিই আটকে আছে কিনা বোঝার আসল সূচক w_await/r_await — অর্থাৎ অপেক্ষার সময়। উপরের output-এ w_await মাত্র 0.52ms, অর্থাৎ disk দ্রুতই সাড়া দিচ্ছে। সে ব্যস্ত, কিন্তু কাবু হয়নি।

এখানে আসল দোষী disk নয়

%system ৩৮% দেখেছ? stress-ng --io অজস্র ছোট ছোট লেখা পাঠাচ্ছে — তাই প্রতি সেকেন্ডে ১৮০০+ operation, অথচ মোট data মাত্র ৭ MB/s।

এখানে সময়টা নষ্ট হচ্ছে disk-এ নয়, kernel-এ — প্রতিটা অনুরোধ সামলানোর খরচে। বাস্তবে এই ছাঁচটা দেখলে বুঝবে application ছোট ছোট write করছে, আর সমাধান হলো সেগুলো জড়ো করে (buffer) একসাথে পাঠানো — বড় disk কেনা নয়।

কোন process দায়ী, দেখতে:

bash
$ sudo apt install -y iotop
$ sudo iotop -o
-o দিলে শুধু যারা সত্যিই I/O করছে তাদের দেখায় — বাকি শত শত নিষ্ক্রিয় process লুকিয়ে থাকে।

Scenario 4 — Network

লক্ষ্য: throughput মাপা, আর retransmission-এর মানে বোঝা।

Terminal 1-এ:

bash — terminal 1
$ sar -n DEV 1

Terminal 2-এ একটা server চালু করো, Terminal 3-এ তার দিকে traffic পাঠাও:

bash — terminal 2
$ iperf3 -s -p 5001
bash — terminal 3
$ iperf3 -c localhost -p 5001 -t 30 -P 4
output — sar -n DEV 1
02:55:14 PM  IFACE  rxpck/s  txpck/s   rxkB/s    txkB/s
02:55:15 PM     lo  82441    82441 3925180  3925180
02:55:15 PM   eth0      2.00     1.00      0.18     0.14
lo (loopback) দিয়ে ৩.৯ GB/s — কারণ data কখনো নেটওয়ার্ক card-এ যাচ্ছেই না, শুধু RAM-এর ভেতরে ঘুরছে।
localhost দিয়ে network-এর গতি মাপা যায় না

উপরের সংখ্যাটা তোমার network-এর ক্ষমতা নয় — ওটা RAM-এর গতি। আসল network মাপতে iperf3 -c <অন্য machine-এর IP> লাগবে।

তুলনার জন্য মনে রাখো: 1 Gbps ≈ 125,000 kB/s, আর 10 Gbps ≈ 1,250,000 kB/s। sar-এর সংখ্যাটা এর কাছাকাছি গেলে বুঝবে তার সীমায় পৌঁছেছ।

এবার TCP-র স্বাস্থ্য দেখো:

bash
$ sar -n TCP,ETCP 1
output
02:56:20 PM  active/s passive/s    iseg/s    oseg/s
02:56:21 PM     4.00      4.00  41220.00  41219.00

02:56:20 PM  atmptf/s  estres/s  retrans/s  isegerr/s
02:56:21 PM      0.00      0.00       0.00       0.00
ঘরমানেকখন চিন্তার
active/sনিজে থেকে করা connectionহঠাৎ বেড়ে গেলে
passive/sবাইরে থেকে আসা connectionখুব বেশি = ভিড় বা আক্রমণ
retrans/sআবার পাঠাতে হয়েছেশূন্যের বেশি হলেই খোঁজ নাও
retrans/s কেন সবচেয়ে জরুরি ঘর

Retransmission মানে পাঠানো data পৌঁছায়নি, তাই আবার পাঠাতে হয়েছে। TCP এটা নিজে সামলে নেয়, তাই application কোনো error দেখে না — শুধু সবকিছু ধীর হয়ে যায়।

এজন্যই "কারণ ছাড়াই application slow" জাতীয় সমস্যায় এই ঘরটা সোনার খনি। শূন্যের বেশি মানে কোথাও packet হারাচ্ছে — কেবল, switch, বা মাঝের কোনো firewall।

কে কোন port-এ বসে আছে:

bash
$ ss -tulnp | head
-p দিয়ে process-এর নাম দেখতে sudo লাগবে, নাহলে শুধু port দেখাবে।

পুরো ব্যাপারটা এক নজরে

এই lab-এর আসল ফসল কোনো একটা command নয় — এই সিদ্ধান্তের গাছটা। "Server slow" শুনলে এই পথে হাঁটো:

Bottleneck খোঁজার পথ
"Server slow"
     │
     ▼
dmesg -T | tail  ── kernel কিছু বলছে? ──→ OOM / I/O error → সেটাই উত্তর
     │ চুপ
     ▼
vmstat 1  ─── একটাই command, চার দিকে ইঙ্গিত
     │
     ├─ r > core সংখ্যা ────────→ CPU-তে জট
     │                              mpstat -P ALL 1 (সব core, না একটা?)
     │                              pidstat 1      (কোন process?)
     │
     ├─ si/so > 0 ──────────────→ RAM শেষ, swap চলছে
     │                              free -m  (available দেখো, free নয়)
     │                              dmesg | grep -i "out of memory"
     │
     ├─ wa বেশি, b > 0 ─────────→ I/O-তে আটকে
     │                              iostat -xz 1 (await দেখো, %util নয়)
     │                              iotop -o      (কোন process?)
     │
     └─ সব স্বাভাবিক, তবু slow ──→ network দেখো
                                    sar -n DEV 1       (throughput)
                                    sar -n TCP,ETCP 1  (retrans/s > 0?)
তিনটে ভুল যা এই lab-এ ভাঙা হলো
যা মনে হয়আসলে
load average বেশি = CPU-র সমস্যাLinux-এ disk-এ আটকে থাকা process-ও গোনা হয়
free কম = RAM শেষavailable দেখো; আসল লক্ষণ si/so
%util ১০০% = disk শেষSSD-তে অর্থহীন; await দেখো

তিনটেরই মূল কথা এক — একটা সংখ্যা দেখে সিদ্ধান্ত নিয়ো না। প্রতিটা উপসর্গের পাশে আরেকটা সংখ্যা দিয়ে মিলিয়ে নাও।

নিজে করো — Challenge

  1. একটা একক CPU-খেকো process চালাও (stress-ng --cpu 1), তারপর mpstat -P ALL 1 দেখে বলো কোন core-এ পড়েছে। কিছুক্ষণ পরে আবার দেখো — সে কি একই core-এ আছে?
  2. fio দিয়ে disk-এর আসল গতি মাপো, তারপর iostat-এ await কত ওঠে দেখো। (ইঙ্গিত: fio --name=t --rw=randwrite --size=256M --bs=4k)
  3. একটা process-কে OOM killer-এর হাত থেকে বাঁচাও, তারপর RAM ভরে প্রমাণ করো সে বেঁচে গেছে। (ইঙ্গিত: oom_score_adj)
  4. sar-এর জমানো তথ্য থেকে আজ সবচেয়ে ব্যস্ত সময়টা বের করো। (ইঙ্গিত: sar -u)
সমাধান দেখো
bash — solution
# ১ — এক core-এ চাপ
$ stress-ng --cpu 1 --timeout 60s &
$ mpstat -P ALL 2
output
CPU   %usr  %sys  %idle

  0   0.50  0.00  99.50

কিছুক্ষণ পরে দেখলে process-টা প্রায়ই অন্য core-এ সরে গেছে — kernel-এর scheduler তাপ আর ভার সামলাতে process সরিয়ে নেয়। এজন্যই mpstat -P ALL-এ একটা core স্থায়ীভাবে ১০০% দেখলে সেটা অস্বাভাবিক; সাধারণত চাপ ঘুরে বেড়ায়।

আটকে গেলে

সমস্যাকী হয়েছে / কী করবে
mpstat: command not foundsudo apt install -y sysstat — mpstat, pidstat, iostat, sar সবই ঐ package-এ।
sar বলছে "Cannot open /var/log/sysstat/..."এখনো কোনো তথ্য জমেনি। sudo systemctl enable --now sysstat চালিয়ে ১০ মিনিট অপেক্ষা করো।
vmstat-এর প্রথম লাইনটা অদ্ভুতওটা boot থেকে এ পর্যন্ত গড় — সবসময় বাদ দাও, দ্বিতীয় লাইন থেকে পড়ো।
Container-এ সংখ্যাগুলো পুরো host-এর মতো/proc host-এর সাথে ভাগ করা। Container-এর নিজের হিসেব /sys/fs/cgroup/-এ, বা systemd-cgtop ব্যবহার করো।
OOM killer ডাকতে পারছি নাswap বড় হলে system আগে swap ব্যবহার করবে। sudo swapoff -a দিয়ে বন্ধ করে আবার চেষ্টা করো (পরে swapon -a)।
iostat-এ কোনো device দেখাচ্ছে না-z নিষ্ক্রিয় device লুকায়। কিছু VM-এ disk-এর নাম vda/xvda — lsblk দিয়ে দেখো।
%steal শূন্যের বেশিতোমার দোষ নয় — hypervisor CPU কেড়ে নিচ্ছে, host-এ ভিড়। Cloud provider-কে জানাও বা instance বদলাও।
stress-ng চাপ দিচ্ছে না মনে হচ্ছে--timeout শেষ হয়ে গেছে কিনা দেখো। --metrics-brief শেষে হিসেব ছাপে, তখন বোঝা যায় সে কাজ করেছিল।

Performance-এর কাজটা tool মুখস্থ করা নয় — বাদ দেওয়ার খেলা। চারটে জায়গা: CPU, memory, disk, network। প্রতিটার জন্য একটা প্রশ্ন আর একটা command। vmstat 1 দিয়ে শুরু করলে প্রথম ইঙ্গিতটা এক নজরেই পাওয়া যায়, তারপর সেই দিকেই গভীরে যাও।

আর সবচেয়ে জরুরি অভ্যাসটা হলো — সংকটের সময় নয়, শান্ত সময়ে এই সংখ্যাগুলো দেখে রাখা। তোমার system স্বাভাবিক অবস্থায় কেমন দেখায় সেটা জানা না থাকলে, অস্বাভাবিক অবস্থাটা চিনবে কী দিয়ে?
