Lab 08 chapter 11 ≈ 59 মিনিট

System Logging and Monitoring

রাত ১১টা ৫৩ মিনিটে একটা service চুপ হয়ে গেছে। কোনো alert আসেনি, কেউ কিছু টের পায়নি। সকালে তুমি বসেছ — হাতে শুধু কিছু log file। এই lab-এ তুমি সেই log থেকে ঘটনাটা ধাপে ধাপে পুনর্গঠন করবে: কখন শুরু হয়েছিল, কী ভেঙেছিল, আর সবচেয়ে গুরুত্বপূর্ণ — আগে থেকে ধরা যেত কিনা।

এই lab শেষে যা পারবে

  • log কোথা থেকে আসে আর কোথায় জমা হয় — পুরো পথটা চিনবে।
  • grep-এর -A/-B দিয়ে error-এর আশপাশ পড়ে timeline বানাতে পারবে।
  • logger দিয়ে নিজের script থেকে system log-এ লিখতে পারবে।
  • logrotate দিয়ে log file-কে disk খেয়ে ফেলা থেকে আটকাতে পারবে।
  • সবচেয়ে জরুরি — একটা incident-এ কোন প্রশ্নটা আগে করতে হয় সেটা জানবে।
আগে যা জানা থাকলে সুবিধা

বইয়ের Chapter 11 — Services এবং System Processes। সেখানে journalctl-এর flag গুলো আছে — -u, -f, -n, -p, -b, --since। এই lab সেগুলো আবার শেখাবে না, ব্যবহার করবে। আর grep-এর flag লাগলে Command Reference-এর Text processing অংশটা খোলা রাখো।

ঘটনাটা

AppTrack একটা ছোট API server — কোন user কী করছে সেটা হিসেব রাখে। সে systemd service হিসেবে চলে আর নিজের log লেখে /var/log/apptrack/apptrack.log-এ।

কাল রাতে সে থেমে গেছে। কোনো error message আসেনি, user-রা শুধু দেখেছে কিছু হচ্ছে না। তিনটে প্রশ্নের উত্তর দিতে হবে:

  1. কখন বন্ধ হলো?
  2. বন্ধ হওয়ার ঠিক আগে কী হচ্ছিল?
  3. পরেরবার আগে থেকে জানব কীভাবে?
তিন নম্বর প্রশ্নটাই আসল

প্রথম দুটোর উত্তর log-এ লেখাই আছে — খুঁজে বের করা শুধু কৌশলের ব্যাপার। কিন্তু তৃতীয়টার উত্তর বেরোয় তখনই, যখন তুমি দেখো crash-এর কত আগে থেকে লক্ষণ দেখা যাচ্ছিল। এই lab-এর শেষে তুমি নিজেই সংখ্যাটা বের করবে — আর সেটা দেখে অবাক হবে।

Log কোথা থেকে আসে, কোথায় যায়

তদন্তে নামার আগে মানচিত্রটা দেখে নাও। Linux-এ log একটা জায়গায় থাকে না — চারটে উৎস থেকে এসে দুটো ব্যবস্থার হাত ঘুরে দুই রকম জায়গায় জমা হয়:

স্তরকীপড়ার tool
KernelRing buffer — kernel নিজে যা বলেdmesg, journalctl -k
journald/var/log/journal/ — binary, indexedjournalctl
rsyslog/var/log/*.log — সাধারণ textgrep, tail, cat
Applicationনিজের file, যেমন /var/log/nginx/grep, tail
Binary বনাম text — পার্থক্যটা কাজের

journald-র file গুলো binary, তাই cat দিয়ে পড়া যায় না — journalctl লাগে। বিনিময়ে সে প্রতিটা বার্তার সাথে service-এর নাম, PID, user, boot-এর ID — সব আলাদা ঘরে জমা রাখে। তাই journalctl -u nginx -p err -b-র মতো ছাঁকনি সাথে সাথে কাজ করে, পুরো file না পড়েই।

আর /var/log/-র text file-এ ঐ কাঠামো নেই — সেখানে grep ছাড়া উপায় নেই। এই lab-এ দুটোই করব, কারণ বাস্তবে দুটোই দরকার হয়।

Part 1 — জায়গাটা চেনা

/var/log-এ কী কী আছে

লক্ষ্য: তোমার system-এ আসলে কোন log গুলো আছে সেটা দেখে নেওয়া।

bash
$ ls -lh /var/log/
output

তোমার তালিকা হুবহু এক হবে না — distro আর configuration ভেদে বদলায়।
Fileকী থাকে
syslogবেশিরভাগ service-এর সাধারণ বার্তা
auth.loglogin, sudo, SSH — কে ঢুকল, কে চেষ্টা করে ব্যর্থ হলো

wtmp / btmpসফল / ব্যর্থ login-এর ইতিহাস — binary
wtmp-তে cat চালিয়ো না

ওগুলো text নয়, binary — cat করলে terminal-এ আবর্জনা ছাপবে, আর মাঝে control character থাকলে terminal-ই এলোমেলো হয়ে যেতে পারে (reset দিয়ে ঠিক করতে হয়)। এদের নিজস্ব reader আছে:

bash
$ last           # wtmp — কে কখন ঢুকেছিল
$ lastb          # btmp — ব্যর্থ চেষ্টা (sudo লাগে)
$ lastlog        # প্রতি user-এর শেষ login

কোন .log file গুলো সত্যিই আছে:

bash
$ sudo find /var/log -type f -name "*.log" 2>/dev/null
2>/dev/null এখানে কেন

/var/log-এর কিছু ফোল্ডারে সাধারণ user-এর ঢোকার অনুমতি নেই, তাই find "Permission denied" ছাপতে থাকে আর আসল ফলাফল তার মধ্যে হারিয়ে যায়। 2>/dev/null শুধু error স্রোতটা ফেলে দেয়, ফলাফল ঠিকই আসে।

খেয়াল করো sudo দেওয়ার পরেও এটা লিখলাম — অভ্যাস হিসেবে ভালো, কারণ sudo ছাড়া চালালেও command টা তখন কাজ করে।

কিছুই না পেলে ঘাবড়িয়ো না

Container বা ছোট cloud image-এ প্রায়ই syslog, auth.log, kern.log কিছুই থাকে না — কারণ rsyslog install-ই করা নেই, সব যায় শুধু journal-এ। সেটা ভাঙা system নয়, আজকাল এটাই স্বাভাবিক। journalctl তখনো কাজ করবে।

<< 'EOF'-এ quote গুলো কেন

Heredoc-এর শুরুতে EOF লিখলে shell ভেতরের $ আর ` গুলোকে ব্যাখ্যা করার চেষ্টা করে। আমাদের log-এ user_id=? আর SELECT * আছে — quote না দিলে * বা কোনো $ shell খেয়ে ফেলত, আর log-এর লাইন বদলে যেত।

<< 'EOF' — quote সহ — মানে "ভেতরের কিছুতেই হাত দিয়ো না, হুবহু পাঠাও"। Config file বা script লেখার সময় এটাই নিরাপদ ধরন।

sudo tee, sudo > নয়

sudo echo ... > /var/log/... কাজ করবে না — redirect টা করে তোমার shell, সে sudo-র ক্ষমতা পায় না, তাই "Permission denied"। tee নিজেই root হিসেবে চলে বলে সে লিখতে পারে।

আর > /dev/null শেষে দেওয়া হয়েছে কারণ tee যা লেখে সেটা screen-এও ছাপে — ২৯ লাইন দুবার দেখার দরকার নেই।

logger — নিজের বার্তা system log-এ পাঠানো

লক্ষ্য: journal-এ AppTrack-এর crash-এর নথি বসানো, আর logger চেনা।

আসল service crash করলে systemd সেটা journal-এ লিখে রাখে। আমাদের নকল service-এর হয়ে সেই কাজটা করব logger দিয়ে — যেটা command line থেকে system log-এ লেখার সরকারি উপায়:

bash
$ sudo logger -t apptrack -p daemon.err  "AppTrack service crashed — exit code 137 (OOM kill)"
$ sudo logger -t apptrack -p daemon.warn "AppTrack: memory limit exceeded before shutdown"
$ sudo logger -t apptrack -p daemon.info "AppTrack: service restart scheduled in 30 seconds"
অংশমানে
-t apptracktag — কে লিখছে। এটা দিয়েই পরে ছেঁকে নেওয়া যাবে
-p daemon.errfacility.level — কোন ধরনের, কতটা গুরুতর
শেষের লেখাটাবার্তা নিজেই
logger-এর আসল কাজ script-এ

Cron-এ চলা backup script যদি echo দিয়ে কিছু ছাপে, সেটা কোথায় যায়? কোথাও না — cron-এর output সাধারণত হারিয়ে যায় বা mail-এ আটকে থাকে। logger দিয়ে লিখলে সেটা journal-এ যায়, আর তখন journalctl -t backup দিয়ে মাসখানেকের ইতিহাসও দেখা যায়:

bash
# script-এর ভেতরে এভাবে
if tar -czf /backup/db.tar.gz /data; then
    logger -t backup -p daemon.info "backup ok ($(du -h /backup/db.tar.gz | cut -f1))"
else
    logger -t backup -p daemon.err "backup FAILED (exit=$?)"
fi

এক লাইনে যোগ করা যায়, আর তারপর থেকে তোমার script-ও system-এর বাকি সবার মতোই journalctl-এ খুঁজে পাওয়া যায়।

Facility কী, level কী

daemon.err-এ দুটো আলাদা জিনিস। Facility (daemon) বলে কে লিখছে — auth, cron, mail, kern, daemon, বা local0–local7 (নিজের application-এর জন্য এগুলোই রাখা আছে)। Level (err) বলে কতটা জরুরি।

Facility-র কাজটা পুরনো rsyslog-এ ছিল আলাদা file-এ পাঠানো — auth-এর সব কিছু auth.log-এ। journald-তে সেটা কম জরুরি, কিন্তু level এখনো গুরুত্বপূর্ণ, কারণ journalctl -p ওটা ধরেই ছাঁকে।

Part 3 — তদন্ত

শেষ থেকে শুরু করা

লক্ষ্য: প্রথম প্রশ্নের উত্তর — কখন আর কীভাবে থামল।

২৯ লাইন পুরোটা পড়ে ফেলা যায়। কিন্তু অভ্যাসটা এখনই ঠিক করে নাও — বাস্তবে log file ২৯ লাইন হয় না, হয় ২৯ লাখ লাইন। তাই cat দিয়ে শুরু কোরো না, শেষ থেকে শুরু করো:

bash
$ tail -6 /var/log/apptrack/apptrack.log
output
2026-03-10 23:53:29 [ERROR] Cache write failure: Redis connection refused (ECONNREFUSED)
2026-03-10 23:53:31 [CRITICAL] Memory usage at 99% — emergency shutdown initiated
2026-03-10 23:53:31 [CRITICAL] Flushing in-flight requests (in-flight=1204)
2026-03-10 23:53:32 [CRITICAL] Flush incomplete — 847 requests lost

প্রথম প্রশ্নের উত্তর পাওয়া গেল — 23:53:32, আর ৮৪৭টা request হারিয়েছে।
Log সবসময় শেষে লেখা হয়

নতুন লাইন file-এর শেষে যোগ হয়, তাই সাম্প্রতিকতম ঘটনা সবসময় নিচে। Crash-এর তদন্তে তাই tail-ই প্রথম command। head লাগে অন্য প্রশ্নে — "service টা ঠিকমতো চালু হয়েছিল তো?"

Exit code 137 — সংখ্যাটা কথা বলছে

শেষ লাইনের exit code: 137 আসলে একটা সংকেত। বইয়ের Chapter 02-এ দেখেছ exit code 0 মানে সফল, আর Chapter 07-এ দেখেছ kill -9 মানে SIGKILL। এই দুটো এখানে এসে মেলে:

নিয়মটা
Signal-এ মারা পড়লে   exit code = 128 + signal number

137 = 128 + 9   → SIGKILL   ← কেউ জোর করে মেরেছে
143 = 128 + 15  → SIGTERM   ← ভদ্রভাবে থামতে বলা হয়েছিল
139 = 128 + 11  → SIGSEGV   ← memory-র ভুল, program-এর bug
130 = 128 + 2   → SIGINT    ← তুমি Ctrl+C চেপেছ
মনে রাখার দরকার নেই — kill -l চালালে পুরো তালিকা পাওয়া যায়।
137 দেখলে কী ভাববে

SIGKILL ধরা যায় না, ঠেকানো যায় না — process কিছু বলার সুযোগই পায় না। তাই প্রশ্নটা হয়ে যায়: কে মারল? তিনটে সম্ভাবনা:

  1. OOM killer — RAM ফুরিয়েছে, kernel সবচেয়ে বড় process-টাকে মেরেছে
  2. কোনো মানুষ — কেউ kill -9 চালিয়েছে
  3. Container runtime — memory limit ছাড়িয়েছে, Docker/Kubernetes মেরেছে

আমাদের log-এ ঠিক আগের লাইনেই লেখা Memory usage at 99% — তাই এটা এক নম্বর। Kubernetes-এ pod-এর status OOMKilled দেখলে সেটাও একই ঘটনা।

আর সাধারণ crash-এ (bug, unhandled exception) exit code সাধারণত 1 বা 2 হয়, 137 নয়। এই পার্থক্যটাই তদন্তের দিক ঠিক করে দেয়।

এক্ষেত্রে log-এ লেখা থাকাটাই ব্যতিক্রম

AppTrack নিজেই লিখতে পেরেছে কারণ সে নিজে থেকে বন্ধ হয়েছিল (emergency shutdown) — OOM killer তাকে ধরার আগেই। কিন্তু সত্যিকারের SIGKILL-এ application কিছু লেখার সুযোগ পায় না, তাই তার log হঠাৎ মাঝপথে থেমে যায়।

তখন প্রমাণ খুঁজতে হয় বাইরে — dmesg-এ। সেটা Lab 07-এ বিস্তারিত করা আছে; এখানে শুধু মনে রাখো, application-এর log হঠাৎ থেমে যাওয়া নিজেই একটা সূত্র।

Error-এর আশপাশ পড়া

লক্ষ্য: দ্বিতীয় প্রশ্নের উত্তর — ভাঙার ঠিক আগে কী হচ্ছিল।

কী ভেঙেছে সেটা জানা গেছে। কিন্তু কেন ভাঙল? একটা error লাইন একা কিছু বলে না — তার আশপাশটাই গল্প বলে:

একই লাইন দুবার — ওটাও খবর

খেয়াল করো Redis connection refused লাইনটা হুবহু দুবার এসেছে, একই সেকেন্ডে। Log-এ একই বার্তা বারবার এলে সেটা সাধারণত retry — application হাল ছাড়েনি, বারবার চেষ্টা করছে।

এজন্যই sort | uniq -c দিয়ে গোনার সময় সাবধান: ১০০০টা একই রকম লাইন মানে ১০০০টা আলাদা সমস্যা নয়, হয়তো একটাই সমস্যা যেটা ১০০০ বার চেষ্টা করেছে।

কোন সংখ্যাটা কারণ, কোনটা ফল

এখানেই বেশিরভাগ তদন্ত ভুল পথে যায়। Log-এ সবচেয়ে চোখে পড়ে Redis connection refused — তাই মনে হয় "Redis-টা ঠিক করলেই হবে"। কিন্তু সময় মিলিয়ে দেখো: Redis ব্যর্থ হয়েছে 23:53:29-এ, আর memory ৮১% ছাড়িয়েছে 23:51:07-এ — প্রায় আড়াই মিনিট আগে।

মানে Redis ভেঙেছে কারণ system-এ memory ছিল না, উল্টোটা নয়। সময়ের ক্রমই কার্যকারণ ঠিক করে দেয় — যেটা আগে ঘটেছে সেটাই সন্দেহভাজন।

একটা লাইন বাদ পড়ছে না তো

grep "ERROR" চালালে শুধু ERROR লাইনগুলো আসে — কিন্তু আমাদের গল্পের সবচেয়ে জরুরি লাইনটা (Memory usage at 94%) আসলে WARN। শুধু ERROR খুঁজলে ঐ সূত্রটা হারিয়ে যেত।

তাই তদন্তে দুটো ধাপ: প্রথমে grep দিয়ে কোথায় সমস্যা বুঝে নাও, তারপর -B/-A দিয়ে ঐ জায়গার আশপাশটা পুরো পড়ো। ছাঁকনি যত সরু, সূত্র হারানোর ঝুঁকি তত বেশি।

কতক্ষণ আগে থেকে জানা যেত

লক্ষ্য: তৃতীয় প্রশ্নের উত্তর — এটাই lab-এর আসল কথা।

এবার সব সতর্কবার্তা একসাথে দেখো:

এটাই তৃতীয় প্রশ্নের উত্তর, আর এটাই এই lab-এর মূল কথা: log থাকা আর log দেখা এক জিনিস নয়। যে log কেউ পড়ে না, সেটা শুধু ময়নাতদন্তের কাজে লাগে — প্রাণ বাঁচানোর কাজে নয়।

একটা সংখ্যা একা কিছু বলে না — "৮টা error" বেশি না কম? বোঝার উপায় হলো স্বাভাবিক সময়ের সাথে মেলানো। রোজকার log-এ যদি ১-২টা error থাকে, আর আজ ৮টা, তাহলে সেটাই খবর।

Journal-এ দেখা — আর সময় নিয়ে একটা ফাঁদ

লক্ষ্য: journalctl-এ নিজের বসানো বার্তা খুঁজে বের করা।

Step 3-এ logger দিয়ে যা পাঠিয়েছিলে, সেগুলো tag দিয়ে ছেঁকে নাও:

bash
$ sudo journalctl -t apptrack --no-pager
output
Sep 19 14:31:02 devbox apptrack[4821]: AppTrack service crashed — exit code 137 (OOM kill)
Sep 19 14:31:02 devbox apptrack[4822]: AppTrack: memory limit exceeded before shutdown
Sep 19 14:31:02 devbox apptrack[4823]: AppTrack: service restart scheduled in 30 seconds
তারিখটা আজকের — 2026-03-10 নয়।
দুই রকম সময়, আর এটা গুলিয়ে ফেললে তদন্ত ভুল হবে

apptrack.log-এর ভেতরের 2026-03-10 তারিখগুলো আমরা নিজেরাই text হিসেবে লিখেছি — ওগুলো শুধু অক্ষর, system-এর কাছে কোনো মানে নেই।

কিন্তু journal প্রতিটা বার্তার সাথে আসল system time বসায় — তুমি command টা যখন চালিয়েছ। তাই --since "2026-03-10" দিয়ে খুঁজলে কিছুই পাবে না।

বাস্তবেও এই ফাঁদটা আছে: application তার নিজের timestamp লেখে (হয়তো UTC-তে, হয়তো অন্য timezone-এ), আর journal লেখে system-এর সময়। দুটো log মেলানোর আগে দুই পক্ষ একই ঘড়ি দেখছে কিনা মিলিয়ে নাও।

তাই এখানে আপেক্ষিক সময় ব্যবহার করো:

bash
$ sudo journalctl -t apptrack --since "15 minutes ago" --no-pager
$ sudo journalctl -t apptrack -p err --no-pager    # শুধু err আর তার উপরে
output — দ্বিতীয়টা
Sep 19 14:31:02 devbox apptrack[4821]: AppTrack service crashed — exit code 137 (OOM kill)
তিনটের মধ্যে একটাই — বাকি দুটো warn আর info, err-এর নিচে।

আটটা মাত্রা

-p err যে "err আর তার চেয়ে গুরুতর" বোঝায়, তার কারণ level গুলো আসলে ০ থেকে ৭ পর্যন্ত সংখ্যা — ছোট মানে বেশি জরুরি:

#নামকখন
0emergSystem আর ব্যবহারযোগ্য নয়
1alertএখনই কাউকে ডাকতে হবে
2critগুরুতর — hardware বা মূল service ভেঙেছে
3errকিছু একটা ব্যর্থ হয়েছে
4warningএখনো ভাঙেনি, কিন্তু ভাঙতে পারে
5noticeস্বাভাবিক, তবে লক্ষ করার মতো
6infoসাধারণ খবর
7debugdeveloper-এর জন্য খুঁটিনাটি
বাস্তবে তিনটেই কাজে লাগে

আটটার মধ্যে err, warning আর info দিয়েই ৯৯% কাজ চলে। emerg/alert প্রায় ব্যবহারই হয় না।

আসল কাজের জায়গা: journalctl -p warning -b — এই boot-এ যা কিছু অন্তত সতর্কবার্তা। নতুন server হাতে পেলে এটাই প্রথম চালানোর মতো command, কারণ এক নজরেই বোঝা যায় কী কী নিয়ে অভিযোগ জমছে।

Journal কত জায়গা খাচ্ছে:

bash
$ journalctl --disk-usage
output
Archived and active journals take up 184.0M in the file system.
Reboot দিলে journal থাকবে কিনা

এটা নির্ভর করে /var/log/journal/ ফোল্ডারটা আছে কিনা তার উপর। থাকলে journal disk-এ জমে, reboot-এর পরেও থাকে (journalctl -b -1 দিয়ে আগের boot দেখা যায়)। না থাকলে সব যায় /run/log/journal/-এ, যেটা RAM — reboot দিলেই সব মুছে যায়।

bash
$ ls -d /var/log/journal 2>/dev/null && echo "স্থায়ী" || echo "RAM-এ, reboot-এ মুছে যাবে"

# স্থায়ী করতে হলে
$ sudo mkdir -p /var/log/journal && sudo systemctl restart systemd-journald

হঠাৎ reboot হওয়া server-এ কারণ খুঁজতে গিয়ে "কিছুই নেই" দেখলে সবার আগে এটা মিলিয়ে দেখো — log হারায়নি, সে কখনো disk-এ লেখাই হয়নি।

Part 4 — Log যেন disk না খায়

সমস্যাটা আগে বুঝে নাও

লক্ষ্য: rotation কেন দরকার সেটা সংখ্যায় দেখা।

AppTrack রাতে ৩ ঘণ্টায় ২৯ লাইন লিখেছে। ব্যস্ত production server-এ hisebটা অন্যরকম — একটা মাঝারি nginx দিনে কয়েক লাখ লাইন লেখে। হিসেব করো:

অঙ্কটা
প্রতি লাইন ≈ 150 bytes
দিনে 500,000 লাইন   →  75 MB / দিন
এক বছর              →  27 GB   ← একটা file-এ
২৭ GB-র একটা file — grep চালাতে মিনিট লাগবে, আর disk ভরে গেলে service নিজেই বন্ধ।
Disk ভরলে যা হয়

Log file disk ভরিয়ে ফেললে শুধু log লেখা বন্ধ হয় না — যে service লিখছিল সে নিজেই ভেঙে পড়ে, database লিখতে না পেরে read-only হয়ে যায়, আর নতুন করে কিছু লেখার জায়গা না থাকায় তুমি ssh দিয়ে ঢুকেও কাজ করতে পারো না।

রাত ৩টার সবচেয়ে সাধারণ production incident গুলোর একটা এটাই, আর কারণটা প্রায় সবসময় একই — কেউ rotation বসাতে ভুলে গিয়েছিল।

সমাধান logrotate — যে নিয়ম করে log file কেটে আলাদা করে, পুরনোগুলো compress করে, আর একটা সীমার পরে মুছে ফেলে।

bash
$ which logrotate || sudo apt install -y logrotate
$ logrotate --version
এটা কোনো daemon নয়

logrotate সারাক্ষণ চলে না — সে দিনে একবার চলে, systemd-র একটা timer তাকে ডেকে আনে। দেখতে পারো:

bash
$ systemctl list-timers logrotate.timer

এজন্যই daily লেখার মানে "ঠিক ২৪ ঘণ্টা পরপর" নয় — মানে হলো "যখন timer টা চলবে, তখন যদি শেষ rotation একদিনের বেশি আগে হয়ে থাকে, তাহলে করবে"।

AppTrack-এর জন্য নিয়ম লেখা

লক্ষ্য: একটা rotation config বানিয়ে চালিয়ে দেখা।

প্রথমে দেখো মূল নিয়মগুলো কী:

bash
$ grep -v '^\s*#' /etc/logrotate.conf | grep -v '^$'
output
weekly
su root adm
rotate 4
create
include /etc/logrotate.d
শেষ লাইনটাই মূল কথা — প্রতিটা application-এর নিজের নিয়ম বসে /etc/logrotate.d/-তে।

এবার AppTrack-এর নিয়ম:

bash
$ sudo tee /etc/logrotate.d/apptrack > /dev/null << 'EOF'
/var/log/apptrack/apptrack.log {
    daily
    rotate 7
    compress
    delaycompress
    missingok
    notifempty
    create 0640 root adm
}
EOF
নিয়মমানে
dailyদিনে একবার কাটো
rotate 7৭টা পুরনো কপি রাখো, তারপর সবচেয়ে পুরনোটা মুছে দাও
compressপুরনোগুলো gzip করো — ১০ ভাগের ১ ভাগ জায়গা নেয়
delaycompressসবচেয়ে নতুন কপিটা compress কোরো না (কারণ নিচে)
missingokFile না থাকলে চুপ করে থাকো, error দিয়ো না
notifemptyFile খালি হলে কাটার দরকার নেই
create 0640 root admনতুন file এই permission আর মালিকানা নিয়ে বানাও
delaycompress কেন লাগে

Rotation-এর সময় file-টার নাম বদলে যায় (apptrack.log → apptrack.log.1), কিন্তু service তখনো পুরনো file-টাই ধরে বসে আছে — সে নাম নয়, file-এর ভেতরের পরিচয় (inode) ধরে লেখে। তাই কয়েক সেকেন্ড সে নাম-বদলানো file-এই লিখতে থাকে।

ঐ মুহূর্তে যদি compress করে ফেলা হয়, সেই শেষ কয়েকটা লাইন হারিয়ে যায়। delaycompress বলে — "এবার থাক, পরেরবার compress কোরো"। তখন service-টা নতুন file ধরে ফেলেছে, পুরনোটায় আর কেউ লিখছে না।

বইয়ের tail -F এখানে এসে বোঝা যায়

Chapter 04-এ পড়েছ tail -F rotation সামলাতে পারে, -f পারে না। কারণটা এখন স্পষ্ট: -f ঐ inode ধরে রাখে, তাই rotation-এর পরে সে পুরনো, নাম-বদলানো file-এ তাকিয়ে থাকে আর কিছুই দেখে না। -F নাম ধরে রাখে — file নতুন হলে সে নতুনটায় চলে যায়।

রাতে tail -f চালিয়ে রেখে সকালে "কিছুই তো আসছে না" দেখলে এই কারণেই।

চালানোর আগে যাচাই করো:

bash
$ sudo logrotate --debug /etc/logrotate.d/apptrack
output
WARNING: logrotate in debug mode does nothing except printing debug messages!
reading config file /etc/logrotate.d/apptrack
Handling 1 logs
rotating pattern: /var/log/apptrack/apptrack.log  after 1 days (7 rotations)
empty log files are not rotated, old logs are removed
considering log /var/log/apptrack/apptrack.log
  Now: 2026-09-19 14:35
  Last rotated at 2026-09-19 14:02
  log does not need rotating (log has already been rotated)
--debug কিছুই বদলায় না — শুধু বলে সে কী করত।
"does not need rotating" এখানে স্বাভাবিক

File টা এইমাত্র বানানো, তাই logrotate ধরে নিচ্ছে সদ্য rotate হয়েছে। এটা ভুল নয়। জোর করে করাতে --force লাগবে — যেটা পরের ধাপে।

--debug অভ্যাস করে নাও: নতুন config লিখে সরাসরি চালিয়ো না, আগে এটা দিয়ে দেখো সে কোন file গুলো ধরছে। ভুল করে *.log লিখে ফেললে এখানেই ধরা পড়বে।

নিজের চোখে rotation দেখা

লক্ষ্য: কেটে দেখা, আর কাটার পরে কী অবস্থা হয় বোঝা।

bash
$ sudo logrotate --force /etc/logrotate.d/apptrack
$ ls -lh /var/log/apptrack/
output
-rw-r----- 1 root adm    0 Sep 19 14:36 apptrack.log
-rw-r----- 1 root adm 2.4K Sep 19 14:02 apptrack.log.1
নতুনটা খালি (0 byte), পুরনো ২৯ লাইন চলে গেছে .1-এ।

আরেকবার চালালে ছবিটা পরিষ্কার হয়:

bash
$ echo "2026-03-11 02:47:13 [INFO]  AppTrack restarted" | sudo tee -a /var/log/apptrack/apptrack.log
$ sudo logrotate --force /etc/logrotate.d/apptrack
$ ls -lh /var/log/apptrack/
output
-rw-r----- 1 root adm    0 Sep 19 14:38 apptrack.log
-rw-r----- 1 root adm   58 Sep 19 14:37 apptrack.log.1
-rw-r----- 1 root adm  680 Sep 19 14:02 apptrack.log.2.gz   ← এটা এখন compressed
delaycompress-এর ফল — .1 এখনো সাধারণ text, .2 gzip হয়ে গেছে। 2.4K থেকে 680 bytes।
Compressed log পড়তে খুলতে হয় না

gunzip করে, খুঁজে, আবার মুছে ফেলার দরকার নেই — z দিয়ে শুরু হওয়া সংস্করণ গুলো সরাসরি পড়ে:

bash
$ zgrep "CRITICAL" /var/log/apptrack/apptrack.log.2.gz
$ zcat /var/log/apptrack/apptrack.log.2.gz | tail -3

পুরনো incident খুঁজতে গেলে প্রায় সবসময়ই .gz ঘাঁটতে হয়, তাই zgrep হাতে রাখা ভালো। একসাথে সব দিন খুঁজতে: zgrep "ERROR" /var/log/apptrack/*.gz।

আসল service হলে আরেকটা ধাপ লাগত

উপরের config-এ একটা জিনিস ইচ্ছে করে বাদ দিয়েছি। আসল AppTrack চললে rotation-এর পরে তাকে বলতে হতো "নতুন file ধরো" — নাহলে সে ঐ নাম-বদলানো পুরনো file-এই লিখে যেত, আর apptrack.log চিরকাল খালি থাকত।

bash
    postrotate
        systemctl kill --kill-who=main --signal=USR1 apptrack.service
    endscript

আমাদের কোনো apptrack.service নেই, তাই এটা বাদ রেখেছি — থাকলে logrotate প্রতিবার error দিত।

বিকল্প উপায় copytruncate — file-টা copy করে মূলটা খালি করে দেয়, service-কে কিছু বলতে হয় না। সহজ, কিন্তু copy আর truncate-এর মাঝের ভগ্নাংশ সেকেন্ডে লেখা লাইনগুলো হারায়। যে service signal বোঝে তার জন্য postrotate, যে বোঝে না তার জন্য copytruncate।

নিজে করো

  1. Crash-এর ঠিক আগের ৩ মিনিটের সব লাইন বের করো — WARN, ERROR, CRITICAL সব মিলিয়ে, সময়ের ক্রমে। (ইঙ্গিত: grep -E)
  2. প্রতি মিনিটে কতগুলো করে সমস্যার লাইন ছিল গুনে বের করো — সংখ্যাটা কি স্থির, নাকি বাড়ছে? (ইঙ্গিত: cut দিয়ে সময়টা কেটে sort | uniq -c)
  3. একটা script লেখো যেটা log-এ ERROR গুনে দশটার বেশি হলে logger দিয়ে alert পাঠায়।
  4. Rotation চলাকালীন tail -f আর tail -F-এর পার্থক্যটা নিজের চোখে দেখো।
সমাধান দেখো
bash — solution
# ১ — শেষ ৩ মিনিটের সব গোলমাল
$ zgrep -E "23:5[123]:" /var/log/apptrack/*.gz | grep -E "WARN|ERROR|CRITICAL"

Rotation করে ফেলেছি বলে মূল file এখন খালি — তাই .gz থেকে পড়তে হচ্ছে। এটাই বাস্তব অভিজ্ঞতা: যখন দরকার পড়ে তখন log প্রায়ই rotate হয়ে গেছে।

-E দিলে 23:5[123]: কাজ করে — মানে 23:51, 23:52 বা 23:53। -E ছাড়া [123]-কে সে আক্ষরিক অক্ষর ধরত।

bash — solution
# ২ — ঘণ্টাপ্রতি গোলমাল
$ zcat /var/log/apptrack/*.gz \
  | grep -E "WARN|ERROR|CRITICAL" \
  | cut -c12-13 \
  | sort | uniq -c
output
     19 23

সব ১৯টাই ২৩টার ঘরে — এক ঘণ্টার মধ্যেই সব ঘটেছে। কিন্তু এই ফলাফলটা অকেজো, কারণ ছাঁকনিটা যা মাপতে চাইছি তার চেয়ে মোটা। ঘণ্টার বদলে মিনিট নাও:

bash — solution
$ zcat /var/log/apptrack/*.gz \
  | grep -E "WARN|ERROR|CRITICAL" \
  | cut -c12-16 \
  | sort | uniq -c
output
      2 23:45
      3 23:51
      3 23:52
     11 23:53   ← শেষ মিনিটে অর্ধেকের বেশি

এবার ছবিটা স্পষ্ট — ২, ৩, ৩, তারপর হঠাৎ ১১। এই ত্বরণটাই ধসের স্বাক্ষর। স্থির হারে error এলে সেটা সাধারণত দীর্ঘদিনের চেনা সমস্যা; কিন্তু হার বাড়তে থাকলে বুঝতে হবে কিছু একটা ভেঙে পড়ছে।

cut -c12-16 মানে প্রতি লাইনের ১২-১৬ নম্বর অক্ষর, যেখানে HH:MM বসে। সব লাইনের গঠন এক হলে cut সবচেয়ে সহজ উপায় — awk-এর দরকারই নেই।

bash — solution
# ৩ — গুনে alert পাঠানোর script
$ cat << 'EOF' > ~/check-apptrack.sh
#!/bin/bash
LOG=/var/log/apptrack/apptrack.log
LIMIT=10
COUNT=$(grep -c "ERROR" "$LOG" 2>/dev/null || echo 0)

if [ "$COUNT" -gt "$LIMIT" ]; then
    logger -t apptrack-monitor -p daemon.err \
        "ERROR সংখ্যা বেশি: $COUNT (সীমা $LIMIT)"
fi
EOF
$ chmod +x ~/check-apptrack.sh
$ ~/check-apptrack.sh
$ sudo journalctl -t apptrack-monitor --no-pager

দুটো জিনিস খেয়াল করো। || echo 0 আছে কারণ file না থাকলে grep -c কিছুই ফেরত দেয় না, আর তখন [ "" -gt 10 ] লিখে script ভেঙে যেত। আর "$COUNT" quote-এর ভেতরে — খালি হলেও তখন অন্তত বোধগম্য error দেবে।

এটাকে cron-এ বসিয়ে দিলেই সেই আট মিনিটের সুযোগটা কাজে লাগানো যায়। তবে বাস্তবে সীমা স্থির না রেখে স্বাভাবিকের তুলনায় লাফ দেখা হয় — রোজ ৫০টা error হওয়া system-এ LIMIT=10 প্রতি মিনিটে alert পাঠাবে, আর তখন কেউ আর alert-এ পাত্তা দেবে না।

bash — solution
# ৪ — terminal 1
$ tail -f /var/log/apptrack/apptrack.log

# terminal 2
$ echo "test 1" | sudo tee -a /var/log/apptrack/apptrack.log   # দেখা যাবে
$ sudo logrotate --force /etc/logrotate.d/apptrack
$ echo "test 2" | sudo tee -a /var/log/apptrack/apptrack.log   # আর দেখা যাবে না

tail -f rotation-এর পরে চুপ হয়ে যায় — সে পুরনো inode ধরে বসে আছে। -F দিয়ে একই পরীক্ষা করলে test 2 ঠিকই দেখাবে, আর সাথে একটা লাইনও ছাপবে:

output — tail -F
tail: '/var/log/apptrack/apptrack.log' has been replaced;  following new file
test 2

Server-এ log দেখতে বসলে -F ব্যবহার করো, -f নয়। পার্থক্যটা ঠিক ঐ সময়েই ধরা পড়ে যখন তুমি সবচেয়ে মনোযোগ দিয়ে তাকিয়ে আছ।

আটকে গেলে

সমস্যাকী হয়েছে / কী করবে
journalctl -t apptrack খালিlogger command গুলো sudo ছাড়া চালিয়েছিলে? তাহলে tag user-এর নামে বসেছে। journalctl -t $(whoami) দেখো।
--since "2026-03-10" কিছুই দেয় নাওটা log-এর ভেতরের লেখা তারিখ, journal-এর নয়। আপেক্ষিক সময় ব্যবহার করো।
Reboot-এর পরে journal ফাঁকা/var/log/journal/ নেই — সব RAM-এ ছিল। Step 7-এর নিয়মে স্থায়ী করো।

Rotation-এর পরে apptrack.log চিরকাল খালিService পুরনো file ধরে আছে। postrotate-এ signal পাঠাও বা copytruncate দাও।

sudo echo "x" > /var/log/... — Permission deniedRedirect করে তোমার shell, sudo নয়। sudo tee -a ব্যবহার করো।
Disk ভরে গেছে, জায়গা লাগবে এখনইjournalctl --vacuum-size=200M — journal ছেঁটে সাথে সাথে জায়গা খালি করে।

মূল কথা

Log পড়ার কাজটা command মুখস্থ করা নয় — সময়ের ক্রম সাজানো। যে ঘটনা আগে ঘটেছে সেটাই সন্দেহভাজন; যেটা পরে, সেটা সাধারণত ফল। তাই grep-এ এক লাইন পেলে থেমো না, -B/-A দিয়ে আশপাশটা পড়ো।

আর AppTrack-এর আসল শিক্ষাটা হলো — সে আট মিনিট ধরে বলছিল যে সে মরতে চলেছে। Log ছিল, লেখা ছিল, সব ঠিকঠাক জমা হয়েছিল। শুধু কেউ দেখছিল না। তাই log ব্যবস্থার শেষ ধাপটা file নয়, rotation-ও নয় — কেউ বা কিছু একটা যেন ঐ WARN গুলো দেখে, সেই ব্যবস্থাটা।
