Managing Sudo Access for System Administration

Production server-এ সবাইকে root-এর password দিয়ে দেওয়া মানে বিপদ ডেকে আনা। বদলে যার যতটুকু দরকার, ঠিক ততটুকু ক্ষমতা দেওয়া হয় sudo দিয়ে। এই lab-এ তুমি একজন পূর্ণ ক্ষমতার admin বানাবে, আর একজনকে দেবে শুধু একটা service restart করার অনুমতি — তার বেশি কিছু না।

এই lab শেষে যা পারবে

  • একটা group-কে পুরো sudo access দেবে।
  • কোনো user-কে শুধু নির্দিষ্ট কয়েকটা command চালানোর অনুমতি দেবে।
  • visudo দিয়ে নিরাপদে sudo-র নিয়ম লিখবে।
  • যাচাই করবে কে কী পারছে আর কী পারছে না।
  • একটা service সত্যিই restart হয়েছে কিনা দুই উপায়ে প্রমাণ করবে।
সাবধানতা

এই lab /etc/sudoers ছোঁয় — এখানে ভুল করলে পুরো system-এ sudo নষ্ট হয়ে যেতে পারে, কেউ আর root হতে পারবে না। তাই কাজটা নিজের practice VM, WSL, বা ফেলে দেওয়া যায় এমন VPS-এ করো। আর file সবসময় visudo দিয়ে খুলবে — কেন, সেটা Step 2-এ বলা আছে।

আগে যা জানা থাকলে সুবিধা

Lab 02 — User & Group Management। এখানে user আর group বানানোর কাজটা ঐ lab-এর উপর দাঁড়িয়ে আছে, তাই ওটা আগে করে নিলে সবচেয়ে ভালো।

যে দৃশ্যটা আমরা বানাবো

ধরো তুমি একটা কোম্পানির system administrator। কোম্পানির নিয়ম — root-এর password কাউকে দেওয়া যাবে না, বরং যার যে কাজ, তাকে ঠিক সেই কাজের অনুমতি দিতে হবে। দুজন লোক আছে:

যা বানাতে যাচ্ছি
group: superadmin  →  %superadmin ALL=(ALL) ALL
│                     যা খুশি, সব করতে পারবে
└── rootuser          (এই group-এর সদস্য)

serviceop              →  serviceop ALL=SERVICE
                          শুধু sshd restart / reload — আর কিছু না

sudo আসলে কী করে

কোনো command-এর আগে sudo লিখলে সেটা root-এর ক্ষমতা নিয়ে চলে। কিন্তু ভেতরে ঠিক কী ঘটে, সেটা জানা থাকলে এই lab-এর প্রতিটা ধাপ পরিষ্কার লাগবে:

  1. /etc/sudoers আর /etc/sudoers.d/-এর সব file পড়ে দেখে — এই user-এর এই command চালানোর অনুমতি আছে কিনা।
  2. অনুমতি না থাকলে ওখানেই থেমে যায়, আর log-এ লিখে রাখে।
  3. দরকার হলে password চায় — খেয়াল করো, root-এর password না, user-এর নিজের password।
  4. একটা নতুন child process বানায়।
  5. সেই child process-এ command টা root-এর ক্ষমতা নিয়ে চলে।
  6. কাজ শেষে ক্ষমতাটা ফিরিয়ে নেয় — user আবার সাধারণ user।
sudo মানে "root-এর password জানা" নয়

এখানেই sudo-র আসল সৌন্দর্য। su দিয়ে root হতে গেলে root-এর password লাগে — অর্থাৎ সেটা যাকে দেবে, সে সবকিছুই পারবে, আর password টা ছড়িয়ে পড়বে।

আর sudo-তে user নিজের password দেয়। কে কী পারবে সেটা ঠিক করা থাকে /etc/sudoers-এ। কেউ কোম্পানি ছেড়ে দিলে শুধু তার account বন্ধ করলেই হলো — root-এর password বদলাতে হয় না।

নিয়মের লাইনটা কীভাবে পড়তে হয়

Sudoers file-এর প্রতিটা নিয়ম একই ছাঁচে লেখা। একবার ছাঁচটা বুঝলে বাকি সব সহজ:

নিয়মের গঠন
%superadmin   ALL   =   (ALL)      ALL
     │         │         │          │
     │         │         │          └─ কোন command চালাতে পারবে
     │         │         └──────────── কার হয়ে চালাতে পারবে
     │         └────────────────────── কোন machine থেকে
     └──────────────────────────────── কার জন্য এই নিয়ম
                                       (% থাকলে group, নাহলে user)
লাইনমানে
%superadmin ALL=(ALL) ALLsuperadmin group-এর সবাই, যেকোনো machine থেকে, যেকোনো user হয়ে, যেকোনো command
serviceop ALL=SERVICEserviceop user শুধু SERVICE তালিকার command গুলো চালাতে পারবে

অনুশীলন

Group আর user বানানো

লক্ষ্য: superadmin group, আর দুজন user — rootuser ও serviceop।

bash
$ sudo groupadd superadmin

এবার দুজন user:

bash
$ sudo useradd -m serviceop
$ sudo useradd -G superadmin -m rootuser

ব্যাখ্যা:

Flagকী করে
-muser-এর home directory বানিয়ে দেয় (/home/serviceop)
-G superadminrootuser-কে superadmin group-এ supplementary সদস্য করে
Lab 2-এর সাথে মিলিয়ে নাও

Lab 2-এ বিদ্যমান user-কে group-এ ঢোকাতে usermod -aG লেগেছিল। এখানে user বানানোর সময়েই group ঠিক করে দিচ্ছি, তাই useradd -G। কাজ একই — দুটোই supplementary group।

এবার দুজনের password দাও:

bash
$ sudo passwd serviceop
$ sudo passwd rootuser
output
New password:
Retype new password:
passwd: password updated successfully
টাইপ করার সময় screen-এ কিছুই দেখা যাবে না — কোনো তারা চিহ্নও না। এটা স্বাভাবিক, ভয় পেয়ো না।
Password কেন লাগছে

কারণ sudo user-এর নিজের password চায়। Password ছাড়া account-এ sudo কাজ করবে না — এটা Lab 2-এর সেই passwordless account error-এরই আরেক রূপ।

যাচাই করো:

bash
$ id rootuser
$ getent group superadmin
output
$ id rootuser
uid=1002(rootuser) gid=1003(rootuser) groups=1003(rootuser),1002(superadmin)

$ getent group superadmin
superadmin:x:1002:rootuser

superadmin group-কে পুরো sudo access দেওয়া

লক্ষ্য: /etc/sudoers-এ group-এর জন্য নিয়ম লেখা।

bash
$ sudo visudo

Editor খুলবে। নিচের লাইনটা যোগ করো:

/etc/sudoers
%superadmin ALL=(ALL) ALL

Save করে বেরিয়ে এসো। nano হলে Ctrl+O → Enter → Ctrl+X; vi হলে Esc → :wq → Enter।

কখনো সরাসরি nano /etc/sudoers করবে না

visudo save করার আগে file-এর বানান পরীক্ষা করে। ভুল থাকলে সে বলে দেয় আর save করতে দেয় না:

visudo — ভুল ধরা পড়লে
>>> /etc/sudoers: syntax error near line 28 <<<
What now?

এখানে e চেপে আবার edit করতে ফিরে যাও। সরাসরি nano দিয়ে খুলে ভুল লিখে save করে ফেললে sudo পুরো নষ্ট হয়ে যাবে — আর তখন সেটা ঠিক করার জন্যও sudo লাগত, যেটা তুমি এইমাত্র হারিয়েছ।

যাচাই করো — নিয়মটা ঠিকঠাক বসেছে কিনা:

bash
$ sudo grep superadmin /etc/sudoers
output
%superadmin ALL=(ALL) ALL

rootuser-এর ক্ষমতা পরীক্ষা

লক্ষ্য: প্রমাণ করা যে sudo ছাড়া পারে না, sudo দিয়ে পারে।

bash
$ sudo su - rootuser

এখন তুমি rootuser হয়ে আছো। প্রথমে sudo ছাড়া system-এর password file পড়ার চেষ্টা করো:

bash — rootuser হিসেবে
$ cat /etc/shadow
output — আটকে যাবে
cat: /etc/shadow: Permission denied
এটাই আশা করা হচ্ছিল। /etc/shadow-এ সবার password-এর hash থাকে, তাই সাধারণ user সেটা পড়তে পারে না।

এবার sudo দিয়ে একই কাজ:

bash — rootuser হিসেবে
$ sudo cat /etc/shadow
output — এবার কাজ করবে
[sudo] password for rootuser:
root:$y$j9T$vX...:20138:0:99999:7:::
daemon:*:20138:0:99999:7:::
...
serviceop:$y$j9T$Kd...:20338:0:99999:7:::
rootuser:$y$j9T$Qm...:20338:0:99999:7:::
এখানে rootuser-এর নিজের password চাওয়া হচ্ছে — root-এর না।

দুটো output পাশাপাশি রাখলেই sudo-র পুরো ব্যাপারটা পরিষ্কার: একই user, একই command — শুধু sudo শব্দটা যোগ করায় ফল বদলে গেল। কারণ %superadmin ALL=(ALL) ALL নিয়মটা তাকে অনুমতি দিয়েছে।

কাজ শেষে নিজের account-এ ফিরে এসো:

bash
$ exit
নিজে কী কী পারি, দেখার সহজ উপায়
bash
$ sudo -l

এটা দেখিয়ে দেয় বর্তমান user ঠিক কোন কোন command sudo দিয়ে চালাতে পারবে। Step 5-এ এটা আবার কাজে লাগবে।

serviceop-এর জন্য সীমিত অনুমতি

লক্ষ্য: শুধু sshd restart আর reload — তার বেশি কিছু নয়।

এবার মূল কাজ। serviceop-কে আমরা /etc/sudoers-এ না লিখে আলাদা একটা file-এ লিখব:

bash
$ sudo visudo -f /etc/sudoers.d/serviceop

ভেতরে এই দুটো লাইন লেখো:

/etc/sudoers.d/serviceop
Cmnd_Alias  SERVICE = /bin/systemctl restart sshd.service, /bin/systemctl reload sshd.service

serviceop ALL=SERVICE

ব্যাখ্যা — দুটো লাইন দুটো কাজ করছে:

  • Cmnd_Alias SERVICE = ... — কয়েকটা command-কে একসাথে SERVICE নাম দিয়ে ডাকার ব্যবস্থা। এটা শুধু একটা ডাকনাম, নিজে কোনো অনুমতি দেয় না।
  • serviceop ALL=SERVICE — এই লাইনটাই আসল অনুমতি দিচ্ছে: serviceop শুধু ঐ তালিকার command গুলো চালাতে পারবে।
আলাদা file কেন, /etc/sudoers-এ না লিখে

/etc/sudoers.d/-এর ভেতরের প্রতিটা file-ও sudo পড়ে, ঠিক যেন মূল file-এরই অংশ। আলাদা রাখার সুবিধা তিনটে — এক, কারো অনুমতি তুলে নিতে হলে শুধু তার file টা মুছে দিলেই হলো; দুই, মূল /etc/sudoers ঘাঁটাঘাঁটি করতে হয় না, তাই ভুল করে সব নষ্ট করার ভয় কম; তিন, কোন নিয়ম কার জন্য সেটা file-এর নাম দেখেই বোঝা যায়।

Path টা হুবহু মিলতে হবে

Cmnd_Alias-এ command-এর পুরো path লিখতে হয়। তোমার system-এ systemctl কোথায় আছে সেটা আগে দেখে নাও:

bash
$ which systemctl

যদি /usr/bin/systemctl আসে, তাহলে উপরের লাইনে /bin/systemctl-এর বদলে সেটাই লেখো — নাহলে নিয়মটা মিলবে না আর অনুমতিও কাজ করবে না। (অনেক আধুনিক distro-তে /bin আসলে /usr/bin-এর দিকেই ইশারা করে, তাই দুটোই কাজ করতে পারে।)

serviceop যা পারে, আর যা পারে না

লক্ষ্য: সীমানাটা দুই দিক থেকেই পরীক্ষা করা।

bash
$ sudo su - serviceop

প্রথমে দেখে নাও সে কী কী পারে:

bash — serviceop হিসেবে
$ sudo -l
output
User serviceop may run the following commands on this host:
    (root) /bin/systemctl restart sshd.service,
           /bin/systemctl reload sshd.service
তালিকাটা ছোট — ঠিক যতটুকু দিয়েছি, ততটুকুই।

যা পারার কথা — restart:

bash — serviceop হিসেবে
$ sudo systemctl restart sshd.service
output — সফল
[sudo] password for serviceop:
(কোনো output নেই — মানে কাজ হয়ে গেছে)
Unix-এর নিয়ম — কাজ ঠিকঠাক হলে সাধারণত কিছুই বলে না। চুপ থাকা মানেই সফল।

যা পারার কথা না — status দেখা:

bash — serviceop হিসেবে
$ sudo systemctl status sshd.service
output — আটকে যাবে
Sorry, user serviceop is not allowed to execute
'/bin/systemctl status sshd.service' as root on labserver.
এটাই lab-এর সবচেয়ে গুরুত্বপূর্ণ output। restart চলল, কিন্তু status চলল না।
এটাই principle of least privilege

খেয়াল করো — দুটোই systemctl, দুটোই একই service-এর উপর। তবু একটা চলল, আরেকটা চলল না। কারণ sudo শুধু "কোন program" দেখে না, দেখে পুরো command line-টা তালিকার সাথে মেলে কিনা।

এই নীতিটাকে বলে principle of least privilege — কাজ চালানোর জন্য যতটুকু ন্যূনতম ক্ষমতা দরকার, ঠিক ততটুকুই দেওয়া। serviceop-এর account কেউ দখল করে নিলেও সে ঐ দুটো command ছাড়া আর কিছুই করতে পারবে না।

Service সত্যিই restart হয়েছে কিনা প্রমাণ করা

লক্ষ্য: "কিছুই দেখাল না" — তাহলে কাজটা হলো কীভাবে বুঝব?

Step 5-এ restart করার পরে কোনো output আসেনি। তাহলে সত্যিই কিছু হয়েছে কিনা বুঝব কীভাবে? দুটো উপায় আছে।

উপায় ১ — Process ID বদলেছে কিনা দেখা

প্রতিটা চলন্ত process-এর একটা নম্বর থাকে, PID। Service restart হওয়া মানে পুরোনো process মরে গিয়ে নতুন একটা চালু হওয়া — তাই নম্বরটাও বদলে যাবে।

bash
# আগে দেখে নাও
$ pidof sshd

# restart করো
$ sudo systemctl restart sshd.service

# আবার দেখো
$ pidof sshd
output
restart-এর আগে →  812
restart-এর পরে →  1547
নম্বর বদলে গেছে — অর্থাৎ পুরোনোটা বন্ধ হয়ে নতুন process চালু হয়েছে। এটাই প্রমাণ।

উপায় ২ — কতক্ষণ ধরে চলছে দেখা

নতুন process মানে তার বয়সও নতুন। etime (elapsed time) দিয়ে সেটা দেখা যায়:

bash
$ ps -eo pid,etime,cmd | grep sshd
output
  PID     ELAPSED CMD
 1547       00:40 sshd: /usr/sbin/sshd -D [listener]
 1602       00:00 grep --color=auto sshd
00:40 মানে process টা মাত্র ৪০ সেকেন্ড ধরে চলছে — অর্থাৎ ৪০ সেকেন্ড আগে restart হয়েছে।

ব্যাখ্যা: ps -eo pid,etime,cmd — -e মানে সব process, -o দিয়ে ঠিক কোন কোন ঘর দেখতে চাই সেটা বলা। শেষের grep sshd দিয়ে শুধু sshd-র লাইনগুলো ছেঁকে নিচ্ছি।

Output-এ grep নিজেই কেন আসছে?

দ্বিতীয় লাইনটা grep --color=auto sshd — এটা তোমার নিজের grep command! ps চলার সময় grep-ও একটা process হিসেবে চলছিল, আর তার নিজের লেখার মধ্যেও "sshd" শব্দটা আছে, তাই সে নিজেকেই ধরে ফেলেছে।

এড়াতে চাইলে grep [s]shd লিখতে পারো — তখন pattern টা আর নিজের সাথে মেলে না।

নিজে করো — Challenge

  1. serviceop-কে systemctl status sshd.service চালানোরও অনুমতি দাও, তারপর sudo -l দিয়ে মিলিয়ে দেখো।
  2. rootuser-কে superadmin group থেকে সরিয়ে দাও, তারপর দেখো sudo cat /etc/shadow এখনো চলে কিনা।
  3. এমন একটা নিয়ম লেখো যাতে serviceop nginx restart করতে পারে কিন্তু password টাইপ করতে না হয়। (ইঙ্গিত: NOPASSWD)
সমাধান দেখো
bash — solution
# ১ — SERVICE তালিকায় status যোগ করো
$ sudo visudo -f /etc/sudoers.d/serviceop
/etc/sudoers.d/serviceop
Cmnd_Alias  SERVICE = /bin/systemctl restart sshd.service, \
                      /bin/systemctl reload sshd.service, \
                      /bin/systemctl status sshd.service

serviceop ALL=SERVICE

লাইন লম্বা হলে শেষে \ দিয়ে পরের লাইনে টানা যায়। এবার sudo -l দিলে তিনটে command-ই দেখাবে।

bash — solution
# ২ — group থেকে সরানো
$ sudo gpasswd -d rootuser superadmin
$ sudo su - rootuser
$ sudo cat /etc/shadow
Sorry, user rootuser is not allowed to execute '/bin/cat /etc/shadow' as root.

অনুমতিটা ছিল group-এর, ব্যক্তির নয়। Group থেকে বেরোনো মাত্রই ক্ষমতা চলে গেল — এটাই group দিয়ে access দেওয়ার সুবিধা।

/etc/sudoers.d/serviceop — NOPASSWD
Cmnd_Alias  WEB = /bin/systemctl restart nginx.service

serviceop ALL=SERVICE, NOPASSWD: WEB

NOPASSWD: শুধু তার পরের অংশের জন্য খাটে। তাই SERVICE-এর জন্য password লাগবে, কিন্তু WEB-এর জন্য লাগবে না। Automation script-এ এটা কাজে লাগে, তবে যতটা সম্ভব কম ব্যবহার করাই ভালো।

খেয়াল রেখো — WEB-এর লাইনটা আগের SERVICE লাইনের সাথেই একই file-এ থাকবে। শুধু এই দুটো লাইন আলাদা file-এ রাখলে sudo বলবে Cmnd_Alias "SERVICE" referenced but not defined, কারণ তখন SERVICE-এর সংজ্ঞাটাই কোথাও নেই।

আটকে গেলে

সমস্যাকী হয়েছে / কী করবে
serviceop is not allowed — অথচ অনুমতি দিয়েছিPath মিলছে না। which systemctl দিয়ে দেখো — /bin না /usr/bin? sudoers-এ হুবহু সেটাই লেখো।
sshd.service not foundকিছু distro-তে নাম ssh.service। systemctl list-units --type=service | grep ssh দিয়ে আসল নাম দেখো।
Container / WSL-এ systemctl চলে নাওখানে systemd থাকে না। sshd-র বদলে অন্য কোনো command দিয়ে অনুশীলন করো — যেমন /bin/systemctl-এর জায়গায় /usr/bin/apt update।
visudo: command not foundsudo apt install sudo দিয়ে install করো।
syntax error near line Ne চেপে edit-এ ফিরে ঐ লাইনটা ঠিক করো। কখনোই ভুল রেখে save করবে না।
sudo পুরো নষ্ট হয়ে গেছেVM হলে recovery/single-user mode-এ boot করে ঠিক করতে হবে। এজন্যই visudo ব্যবহার করা জরুরি।

পরিষ্কার করে ফেলা (ঐচ্ছিক)

# serviceop-এর sudo নিয়ম মুছে দাও
$ sudo rm /etc/sudoers.d/serviceop

# user দুজন মুছে দাও (home directory সহ)
$ sudo userdel -r serviceop
$ sudo userdel -r rootuser

$ sudo groupdel superadmin

# /etc/sudoers থেকে %superadmin লাইনটা হাতে মুছে দাও
$ sudo visudo
শুধু নিজের practice machine-এ

userdel -r home directory সহ সব মুছে দেয়, ফেরানোর উপায় নেই। আর /etc/sudoers edit করার সময় শুধু নিজের যোগ করা লাইনটাই মুছবে — আগে থেকে থাকা লাইনে হাত দিলে system-এর sudo নষ্ট হয়ে যাবে।

মূল কথা

Root-এর password ছড়িয়ে দেওয়ার বদলে sudo দিয়ে যার যতটুকু দরকার ততটুকু ক্ষমতা দেওয়া যায়। Group-কে অনুমতি দিলে সেটা সবার জন্য একসাথে খাটে; Cmnd_Alias দিয়ে নির্দিষ্ট কয়েকটা command-এই আটকে রাখা যায়। আর visudo ছাড়া sudoers file কখনো ছোঁবে না — এই একটা অভ্যাসই একদিন তোমার server বাঁচিয়ে দেবে।
